# 程式驗證

> 隸屬：[邏輯學] › [邏輯與電腦]　·　狀態：初稿

> 對應維基百科：[中文維基百科：程式驗證](https://zh.wikipedia.org/wiki/%E5%BD%A2%E5%BC%8F%E9%AA%8C%E8%AF%81)　·　[English Wikipedia: Formal verification](https://en.wikipedia.org/wiki/Formal_verification)

程式驗證是把程式的行為表述為數學命題並證明之。它是形式化驗證中最貼近日常軟體的一支：面對的不是晶體管線或作業系統核心，而是演算法、資料結構與併發控制。

其技術核心是 **Hoare 邏輯**——以「前置條件、程式、後置條件」三元組描述程式行為，並以模態算子表達「只要終止，後置條件必然成立」。

## 一、Hoare 邏輯

最基本的形式：

$$
\{Q\} \; C \; \{R\}
$$

讀作：若執行前 $Q$ 成立，且程式 $C$ 終止，則執行後 $R$ 成立。

**範例（整數平方根）**：給定程式

```text
x := 0;
while (x * x <= n) { x := x + 1 }
```

可證明後置條件 $x^2 > n$ 且 $(x-1)^2 \leq n$ 。證明的核心是一個**迴圈不變量**：每次迭代前後皆滿足 $(x-1)^2 \leq n \wedge x^2 > n$ 的對應版本——不變量正是迴圈證明的關鍵概念。

## 二、工具的分工

| 工具 | 檢查的性質 | 說明 |
| --- | --- | --- |
| 型別檢查器 | 型別安全、資源安全 | 全自動 |
| 斷言檢查 | 局部不變量 | 半自動，斷言需人手寫 |
| 靜態分析 | 資料流與別名分析 | 全自動但保守 |
| 符號執行 | 路徑條件 | 半自動 |
| 定理證明 | 功能正確性 | 半自動，成本高 |

**範例（符號執行）**：以 SMT 求解器為引擎，把程式路徑轉為邏輯公式並求解。例如在 `if (x != 0) { y = 1 / x; }` 中，符號執行會產生條件 $x \neq 0$ ，從而把除零錯誤排除在路徑之外。

## 三、弱化與強化

驗證的實務難題是：**後置條件往往無法完全證明**。此時有兩種策略：

1. **弱化後置條件**：把難以證明的部分改成較弱但仍足以支撐呼叫端需求者。
2. **強化前置條件**：要求呼叫者提供更多前提，以換取可證性。

**範例**：欲證明「回傳值總是正數」，若函式在輸入為負時回傳 0，則該命題為假。此時可把後置條件弱化為「回傳值非負」，或把前置條件強化為「輸入為正」——兩者都是工程上合理的折衷。

## 四、與併發及現代語言

| 面向 | 做法 |
| --- | --- |
| 資料競爭 | 共享狀態不變式、happens-before 關係 |
| 死鎖 | 鎖順序規則、資源順序圖 |
| 原子性 | 交易語意與隔離性 |
| 記憶安全 | 分離邏輯、借用檢查 |

**範例（分離邏輯）**：傳統 Hoare 邏輯難以描述堆積記憶體，分離邏輯以「堆積分離」假設（兩區塊不共享儲存）擴充了斷言語言，使串接式的資料結構操作得以被簡潔地證明。

## 五、實務現況

1. **全自動驗證仍不可行**：功能正確性的證明成本高，多數專案只覆蓋部分。
2. **工具鏈整合**：VS Code、IDE 中的即時診斷讓驗證進入日常流程。
3. **規格先行**：驗證迫使團隊先把「什麼叫做對」寫清楚。
4. **與測試互補**：測試發現規格錯誤，驗證保證實作符合規格。

**範例**：一個實務團隊的做法是——核心演算法用定理證明器驗證、外圍邏輯用單元測試覆蓋、介面以型別與斷言保護。這是現實成本下的合理分工。

## 六、與相鄰分類的關聯

- [形式化驗證]：上位的工程框架。
- [型別系統]：最自動化的驗證手段。
- [定理證明器]：互動式證明的工具。
- [模態算子]：Hoare 邏輯以 $\Box$ 表述「終止則必然成立」。
- [SAT求解] 與 [SMT]：符號執行的底層。

## 七、容易混淆之處

- 程式驗證證明的是**規格**被滿足，不是程式「沒有任何問題」。
- 未被驗證的部分不等於有錯，只是尚未被證明。
