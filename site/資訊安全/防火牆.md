# 防火牆

> 隸屬：[資訊安全] › [防禦機制]　·　狀態：初稿

> 對應維基百科：[中文維基百科：防火墙](https://zh.wikipedia.org/wiki/%E9%98%B2%E7%81%AB%E5%A2%99)　·　[English Wikipedia: Firewall (computing)](https://en.wikipedia.org/wiki/Firewall_%28computing%29)

防火牆是位於網路邊界或區段之間的**流量過濾與隔離裝置或功能**，它依一組規則決定哪些連線允許通過、哪些拒絕或需要額外處理。防火牆是網路安全最古老的機制，也是最常被誤解的機制。

防火牆的演進史就是一部**信任模型史**：從最初的封鎖式過濾（只允許已列舉的服務），到狀態式檢查（追蹤連線狀態），到應用層閘道（理解 HTTP、DNS 等協定內容），再到以身分為核心的雲端防火牆與軟體定義邊界。每一步演進都在解決上一代的核心不足。

## 技術與理論的關聯

- **兩種基本模型**：封鎖式（deny by default 之外的所有允許）與允許式（預設全部允許，只封鎖列舉者）。實務上以允許式較常見，但資安原則偏好封鎖式——這正是 [最小權限] 在網路層的投影。
- **封包過濾與狀態檢查**：封包過濾只看每個封包的標頭；狀態檢查維護連線狀態表，允許回應封包只在其對應的請求存在時通過，使偽造來源的回應被阻擋。
- **代理式与应用層閘道**：在應用層終結並重新建立連線，可過濾內容並隱蔽內部結構，但增加延遲並需為每種應用配置代理。
- **隱蔽內部結構**：過濾掉不允許的服務，使掃描者無法得知內部有什麼——這降低了攻擊面資訊，但無法阻止已建立的合法連線被利用。
- **位址轉換與分段的關係**：網際網路位址轉換讓多台內部主機共用一個外部位址，隱蔽了內部結構並減少可攻擊的目標數量。
- **與 [演算法] 的關聯**：規則比對與串流重組的正確性依賴狀態追蹤；歷史上多起防火牆繞過事件都源於狀態機實作與規格不一致，因此防火牆本身曾是需要被小心驗證的解析器，這也說明其規則比對的正確性是 [演算法] 問題。

## 範例

**範例：從封鎖式過濾到以身分為核心的邊界。**

1. **第一代（封包過濾）**：規則形如「允許 TCP 目的埠 443、22 與 53，其餘拒絕」。優點是簡單、效能高；缺點是無法追蹤連線狀態，且允許的服務一旦被利用即全開。
2. **第二代（狀態式檢查）**：維護五tuple 連線表，回應封包必須對應既有請求才放行。這阻擋了最原始的 IP 偽造回應攻擊。
3. **第三代（應用層閘道）**：以 HTTP 代理解析網址，可依網址類別封鎖並記錄；但代理自身成為高價值目標，且大型網站難以全部代理。
4. **第四代（下一代防火牆）**：解析應用層協定與使用者身分，將「哪個應用、哪個使用者、哪個網段」的組合納入決策，流量與端點遙測資料互相補充。
5. **第五代（雲端與軟體定義邊界）**：在雲端環境中，虛擬網路防火牆直接綁定工作負載標籤，工作負載新建時規則自動套用——這解决了傳統邊界防火牆「不知道雲端裡有什麼」的問題。
6. **真實世界的教訓**：某公司以傳統邊界防火牆為主，雲端工作負載則未設任何控制；攻擊者自外部網站取得有效憑證後，直接對雲端 API 發動橫向呼叫，全程未觸及邊界防火牆。這說明防火牆守的是**位置**，而攻擊者如今不依賴位置。

## 前因後果

- **前因**：1970 年代分時系統與早期網路的隔離需求催生了封包過濾器；1990 年代連線數暴增使狀態檢查成為必要，也帶來連線表耗盡這類新的阻斷服務風險。
- **後果**：防火牆成為網路安全的基礎設施與強制合規項目（如電信業的網路分級），並推動軟體定義邊界、雲端安全網路等新形態。
- **互相驅動**：[入侵偵測] 補上防火牆看不見的允許流量；[零信任] 質疑「邊界即信任」的假設；[中間人] 攻擊則提醒邊界內部的連線同樣需要驗證。

## 與相鄰分類的關聯

- 與 [入侵偵測] 的關係：防火牆預防已知的連線，入侵偵測觀察已允許連線中的異常。
- 與 [端點防護] 的關係：邊界被繞過或內部遭橫向移動時，端點是最後一道現場。
- 與 [零信任] 的關係：零信任把「邊界信任」整體廢除，防火牆退居為網段隔離工具而非信任來源。
- 在 [資訊安全] 與 [防禦機制] 體系中，防火牆是**縱深防禦**中最外層的控制，代表成本最低但也最容易被繞過的一環。

## 容易混淆之處

- **防火牆不等於防毒**：防火牆管連線，防毒管端點上的程式行為。
- **防火牆不保護已允許的連線**：一旦某人取得合法憑證並從內部發動連線，防火牆幾乎無能為力。
- **「更嚴格的規則」不等於更安全**：過度嚴格會把使用者逼向未受控的通道，反而增加風險。
- **NAT 不等於防火牆**：位址轉換只是讓內部位址不可見，並不過濾流量。
- **雲端防火牆不等於虛擬私有雲**：虛擬私有雲主要解決位址隔離，並不自動提供完整的流量過濾。
- **規則越多不一定越安全**：規則數量暴增會造成衝突與難以維護，實際生效的規則可能與想像不同。
- **邊界防火牆無法保護物聯網與遠端裝置**：這些裝置的連線來自不可控的網路，只能靠裝置端控制與憑證。

## 技術要點

- 預設拒絕所有對外連線，再逐一開放必要服務與目的端。
- 對外連線以目的端點白名單為主，避免使用者可直接指定任意位址與埠。
- 啟用狀態檢查與連線逾時，並對連線表設定上限以防耗盡。
- 部署應用層識別，至少能辨識 HTTP、DNS 與加密流量的特徵並做記錄。
- 把日誌集中送至獨立的日誌系統，避免攻擊者可修改本機日誌。
- 規則變更需經審查並保留版本記錄，與變更管理流程整合。

## 常見的論爭

- **深度封包檢測與隱私**：加密流量普及使內容檢測能力下降，深度檢測誘餌代理的隱私代價是否可接受仍有爭論。
- **集中式與分散式控制**：把所有規則集中管理易於稽核，但集中故障與集中攻擊的風險也同時放大。
- **雲端環境中邊界是否還存在**：工作負載動態化使固定邊界難以維持，供應商與用戶對「誰負責過濾」的責任劃分仍在演變。

## 實務補充

防火牆維運中最容易被低估的是**規則的可見性**。團隊往往知道有哪些規則，卻不知道每條規則實際上匹配了多少流量、在正常情況下從未被使用過。啟用規則命中記錄並定期檢視「零命中規則」，是把防火牆從靜態設定轉為可治理資產的第一步；同理，「命中量異常偏高的規則」往往指出內部存在未被記錄的依賴。

另一個常見問題是**多套防火牆各自為政**：雲端、機房與分公司各有一套規則，沒有人能回答「從 A 到 B 到底要穿過幾道牆、每一道允許什麼」。以拓樦視圖統一呈現路徑上的控制點，並讓變更同步套用，往往比再加一道防火牆更能降低風險。
