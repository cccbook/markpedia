# 阻斷服務

> 隸屬：[資訊安全] › [網路攻擊]　·　狀態：初稿

> 對應維基百科：[中文維基百科：阻斷服務攻擊](https://zh.wikipedia.org/wiki/%E9%98%BB%E6%96%B7%E6%9C%8D%E5%8B%99%E6%94%BB%E6%93%8A)　·　[English Wikipedia: Denial-of-service attack](https://en.wikipedia.org/wiki/Denial-of-service_attack)

阻斷服務攻擊的目的**不是竊取資料，而是讓服務不可用**。它以低成本製造出對正常使用者而言不可用的情境：耗盡頻寬、耗盡連線數、耗盡計算資源，或利用軟體在異常輸入下的資源洩漏。

它的特殊之處在於**攻擊者不需要突破任何安全控制**——不需要猜密碼、不需要找漏洞、不需要偽造身分。這使它成為可用性這一維度的最纯粹威脅，也使它的防禦不能仰賴「阻擋惡意流量」而必須仰賴「容量與降級設計」。

## 技術與理論的關聯

- **分散式改變了成本結構**：把流量來源分散到大量被入侵主機（botnet），使攻擊邊際成本降至極低，防守方的邊際成本卻隨流量線性上升——這是典型的**反射型不對稱**。
- **放大攻擊的數學**：反射（DNS 反射、HTTP 放大）讓攻擊者以小流量換取大回應，若放大倍率為 $A$ ，則攻擊流量約為目標流量的 $1/A$ ；這是 DNS 反射攻擊能以小資源打垮大站點的原因。
- **資源耗盡有數學模型**：佇列長度、連線表大小、檔案描述元數都構成容量上限；當到達率 $\lambda$ 超過處理率 $\mu$ 時，佇列長度會趨於發散——阻斷服務的本質就是強迫 $\lambda > \mu$ 。
- **與 [零信任] 的關聯**：零信任的「假設已被攻陷」立場要求每個資源都有獨立的資源配額與速率限制，而非依賴邊界過濾。
- **與 [入侵偵測] 的關聯**：偵測阻斷服務需要以時間序列觀察流量與連線數的異常，而非以單一封包特徵比對，因此統計方法在此格外重要。
- **與 [演算法] 的關聯**：流量清洗的挑戰是在線上辨識攻擊流量，其問題形式近似於「已知正常分布下的異常樣本辨識」，是演算法與統計的交會。

## 範例

**範例：一次應用層與網路層混合的阻斷服務事件。**

1. **第一波（流量消耗）**：攻擊者以大量封包送向公開的 DNS 解析服務，利用反射放大特性，把目標網站置於數十倍於攻擊者實際流量的入站流量之下。受害者的上游連線頻寬被飽和，網站對 legit 使用者完全無回應。
2. **第二波（資源消耗）**：攻擊者發現單純的流量洪水效果有限（因採用者已向 ISP 申請流量清洗），轉而針對應用層：以合法的 HTTP 請求大量命中一個查詢成本極高的端點（例如未加索引的資料庫搜尋），每個請求消耗大量伺服器 CPU 與資料庫連線。
3. **第三波（連線耗盡）**：以慢速傳送佔滿伺服器的連線表，讓合法的短請求排隊等待，雖然流量不大卻完全阻塞服務。
4. **防守方的對應**：
   - **上游清洗**：在 ISP 端啟用自動流量清洗，將明顯的反射流量在進入骨幹前濾除。
   - **快取與預先計算**：把熱門查詢結果快取並設定合理的逾時，讓第二波的查詢成本大幅下降。
   - **速率限制**：以來源 IP 與 API 金鑰為維度設定速率上限，並對異常請求模式做挑戰式驗證。
   - **連線與逾時治理**：設定合理的握手逾時與最大連線數，讓慢速連線無法長期佔用。
   - **容量與降級**：靜態頁面與快取內容獨立於後端服務，資料庫過載時仍能提供基本服務。
   - **監控與預警**：以連線數、CPU、請求延遲的時間序列設定告警，讓團隊能在用戶注意到前先處置。
5. **事後檢討**：團隊發現三波攻擊分別針對三個不同層級，若只準備單一防線（只有清洗、或只有限流），都無法全身而退。

這個範例說明阻斷服務的防禦必須是**多層次且以容量思維為核心**：清洗處理流量型、限流處理請求型、降級處理資源型，三者缺一不可。

## 前因後果

- **前因**：骨幹鏈路容量與伺服器資源有限，而攻擊工具愈來愈便宜；網際網路的骨幹設計原本假設骨幹足夠寬、不會被單一來源飽和，這個假設在商業化攻擊工具面前失效。
- **後果**：阻斷服務成為跨國網路攻擊的主要形式之一，並推動流量清洗服務、ISP 層的協作機制、與雲端環境的自動彈性擴充；同時也讓「可用性」正式進入風險評估的量化表格。
- **互相驅動**：[端點防護] 與 [防火牆] 提供了第一層過濾；[事件回應] 定義了攻擊中的處置；[安全治理] 的風險評估則決定要為哪些服務預留彈性容量。

## 與相鄰分類的關聯

- 與 [入侵偵測] 的關係：偵測是阻斷服務唯一的早期預警來源。
- 與 [端點防護] 的關係：端點層的資源保護（行程配額）能緩解本機資源耗盡。
- 與 [防火牆] 的關係：過濾規則是流量型攻擊的第一道攔截，但單靠封鎖來源 IP 難以應對分散式與偽造來源。
- 在 [資訊安全] 與 [網路攻擊] 體系中，本條目是可用性威脅的代表，也提醒我們：**能抵禦資料竊取的系統，仍可能因可用性不足而毫無商業價值**。

## 容易混淆之處

- **阻斷服務不等於資料破壞**：服務可用但資料被竊是另一類事件，兩者的調查方向不同。
- **封鎖來源 IP 效果有限**：分散式與代理來源使單一封鎖的效用迅速衰減。
- **流量清洗不等於根治**：清洗處理的是症狀，應用層的資源消耗型攻擊需由容量與降級設計解決。
- **合法的尖峰與攻擊難分**：促銷或事件帶來的真實流量高峰，與攻擊在流量曲線上相似，需以行為而非單純流量判斷。
- **反射放大並非所有協定皆可用**：未經驗證的查詢回應的協定（如舊版 DNS）才是放大攻擊的溫床，修補本身就是防禦。
- **殺毒式思維不適用**：不存在「阻擋某個攻擊特徵」的永久解，因為攻擊型態會演進。
- **頻寬不是唯一瓶頸**：多數現代阻斷服務的瓶頸在應用層與資料庫，而非骨幹頻寬。

## 技術要點

- 對每個對外服務設定速率限制，並以多維度（金鑰、IP、端點）而非單一 IP 為基準。
- 部署自動流量清洗，並事先與 ISP 確認啟動流程與聯絡窗口。
- 應用層設計降級路徑：快取優先、靜態內容優先、非關鍵功能先捨棄。
- 設定握手與讀取逾時、最小連線速率與最大連線數，防範慢速攻擊。
- 對外僅暴露快取分發層，讓真實來源在入口即被吸收。
- 以連線數、請求率、延遲與錯誤率的時間序列設定多級告警。

## 常見的論爭

- **誰該為清洗成本付費**：清洗服務的費用由受害者承擔，業界對ISP 應否提供免費基礎保護仍無共識。
- **主動防禦的邊界**：ISP 在網路側丟棄特定類型流量雖有效，卻可能誤傷合法使用者，界線如何劃定具爭議。
- **攻擊歸因的困難**：分散式攻擊的溯源需要跨國協作，實務上多以推測與有限證據收案，歸因的證據標準仍在發展。
