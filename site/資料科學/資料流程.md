# 資料流程

> 隸屬：[資料科學]　·　狀態：初稿

> 對應維基百科：[中文維基百科：資料串流](https://zh.wikipedia.org/wiki/%E8%B3%87%E6%96%99%E4%B8%B2%E6%B5%81)　·　[English Wikipedia: Pipeline (computing)](https://en.wikipedia.org/wiki/Pipeline_%28computing%29)

資料流程（data pipeline）是把原始資料從來源搬運、轉換、組裝成分析可用表單的一整套機械與規則。它回答的不是「要算什麼」，而是「算的時候那些數字從哪來、經過什麼手續變成現在這樣」。

這套流程的存在理由是**可重現性**。假設某位分析師用 SQL 撈出一張轉換率表，若他只貼出最終數字，沒有人能判斷這個數字是否可信；但若整條流程被記錄成「從哪張表、經過哪些過濾、如何聚合、用哪一版程式碼、輸入資料截止到哪一天」，任何人都能重跑並得到同樣結果。

流程設計與 [軟體工程] 的建構觀念一致：把「建立環境、執行腳本、產生輸出」拆成可獨立檢查的步驟，每一步的輸出都是下一步的輸入。差別在於資料流程的步驟往往以資料表而非程式模組為單位，因此版本控制的單位更接近「查詢腳本 + 設定檔 + schema」。

## 技術與理論的關聯

- **管線即有向無環圖**：每個節點讀取上游表並寫出下游表，節點之間不應形成迴圈，否則無法確定執行順序與重跑範圍。
- **批次與串流的取捨**：批次管線以「全量重算」換取一致性，串流管線以「低延遲」換取一致的困難；兩者的冪等性要求不同。
- **冪等性是重跑的最低要求**：同一輸入重跑管線必須得到同一輸出，否則每次結果都不同，分析就無法累積。
- **資料契約（data contract）**：上下游對欄位型態、單位、允許值與更新頻率達成書面約定，否則「上游改了欄位」會變成下游的無聲故障。
- **推論與資料的邊界**：管線決定了哪些資料「看得到」，因此管線本身是一種 [統計推論] 的取樣設計；例如只保留完成結帳的使用者，就已經製造了 [樣本偏差]。
- **遞增計算與水位線**：以時間戳或主鍵水位線記錄「已處理到哪」，讓每日更新只處理新增資料，是批次管線能撐上億列的關鍵。

## 範例：每日推薦特徵表的建置

**目標**：每天 05:00 產出前一日的「使用者 × 商品」特徵表，供推薦模型訓練與線上查詢使用。

1. **資料取得**：從三個來源抽取——交易資料庫的訂單表、網頁事件日誌、還有商品主資料。三者的抽取都以「前一日 23:59:59 的資料截止時間」為界，抽取結果各自寫入原始層（raw layer），並記錄筆數與時間範圍。
2. **清理**：原始層的交易資料含測試帳號、已取消訂單與重複的 webhook 事件。清洗規則寫成可執行的規則表，規則本身納入版本控制；當日清洗後有效訂單 128,441 筆，佔原始的 96.1%。
3. **特徵工程**：把訂單與事件日誌以「使用者 + 商品」為鍵做關聯，衍生出 30 天內購買次數、該類商品的瀏覽未購買次數、加入購物車次數等特徵，每個特徵都附帶計算式說明。
4. **建模**：把特徵表與標籤（未來 7 天是否購買）合併，輸出訓練集；並同步輸出一份「線上查詢用」的欄位型態定義，確保離線與線上特徵一致。

管線的儀表板每天顯示四個數字：各層筆數、從 raw 到最終的流失比例、各步驟執行時間、以及是否存在遲到的資料（late-arriving data）。這四個數字構成了資料品質的最小監控集合。

## 前因後果

- **因為**：手動拉檔與 Excel 彙整無法回答「這個數字是怎麼來的」，而且在資料量成長後會直接崩潰。
- **所以**：流程被拆成可獨立執行的步驟，每步的輸出被視為資料資產，可以被版本化與回溯。
- **因而推動**：資料測試（檢查筆數、唯一鍵、值域）成為管線的一部分，而非額外工作。
- **反過來**：管線把「取樣決策」具體化，讓 [實驗設計] 中隨機化的組別可以被完整保存與重放。
- **再推動**：當流程穩定後，資料科學家才有餘裕研究模型，而不是每天修資料。

## 與相鄰分類的關聯

- 與 [探索性分析] 的關係：探索性分析提出問題，管線提供可回答問題的資料；管線若先於探索被固定，會把探索限制在既有欄位內。
- 與 [資料視覺化] 的關係：視覺化所需的中繼資料表通常由管線產出，兩者對「聚合層級」的要求必須一致。
- 與 [軟體工程] 的關係：管線本質上是資料版的軟體產品，因此同樣需要版本控制、自動化測試與部署紀律。
- 在上位概念 [資料科學] 中，本概念扮演什麼角色：它是資料科學的供給層與瓶頸所在，決定了分析與建模的上限。

## 容易混淆之處

- **管線不等於 ETL**：ETL 是轉換為中心的一種型態，現代管線常同時包含 ELT（先載入再轉換）與反向的資料產品流程。
- **管線不等於工作流排程器**：排程器只負責「何時執行」，管線還包含資料內容的轉換邏輯與資料相依。
- **資料品質報告不等於管線**：報告是監測，管線是生產，兩者不可互相取代。
- **原始層不等於不可變**：原始層應當不可變，但這需要寫入權限與儲存策略的配合。

## 技術要點

- 以「原始層 → 清理層 → 特徵層 → 產品層」分層，每層只做一件事，允許逐層重算。
- 每層輸出都應記錄：資料筆數、鍵唯一性、欄位非空率、涵蓋的時間區間。
- 設定檔與程式碼分離：環境、連線字串、路徑不寫死在程式碼中。
- 冪等鍵設計（例如以事件 ID 去重）比「先刪後插」更安全。
- 空值策略要明確：留空、填零、填中位數、還是視為缺漏樣本，四者對模型影響不同。
- 管線的執行時間應有目標上限，超時即告警，而不是默默跑六小時。

## 常見的論爭

- **過度工程之爭**：小型專案是否值得建立完整分層。支持者認為可重現性終將回報；反對者認為管線本身變成新的維護負擔。
- **SQL 與框架之爭**：以 SQL 為主或以 Spark 為主各有擁護者，爭點在於同一批工程是否需要同時維持兩套技能與兩種除錯方式。
- **資料網格 vs 資料倉儲之爭**：分散式資料湖與傳統倉儲的取捨，涉及組織已有的技能與治理成熟度，而非單純的技術優劣。
