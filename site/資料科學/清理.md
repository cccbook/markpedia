# 清理

> 隸屬：[資料科學] › [資料流程]　·　狀態：初稿

> 對應維基百科：[中文維基百科：数据清洗](https://zh.wikipedia.org/wiki/%E6%95%B0%E6%8D%AE%E6%B8%85%E6%B4%97)　·　[English Wikipedia: Data cleansing](https://en.wikipedia.org/wiki/Data_cleansing)

資料清理（data cleansing）是把取得的原始資料轉為**格式一致、型態正確、缺失可解釋**狀態的處理過程。它常被說成「把資料洗乾淨」，但這個比喻容易造成誤解：清理不是把資料弄成分析想要的形狀，而是把資料弄成**可被正確解讀**的形狀。

清理之所以是資料科學中佔比最高的工作之一，有一個結構性的理由。真實世界的資料記錄的是「事件」，而分析需要的是「欄位」；從事件到欄位的落差，就是清理的工作量所在。同一筆訂單可能被拆成三行明細、一張發票可能對應兩種貨幣、一個使用者可能有多種拼寫形式的姓名。

統計上，清理也直接影響 [統計推論] 的有效性。型態錯誤的數值（例如把「無」寫成 0）會把分布的尾巴拉長、讓 [描述統計] 失真，進而使後續檢定失去意義。因此清理必須以**可追溯、可重跑、可稽核**的方式進行，而不是在試算表裡手動修補。

清理有兩個方向：**結構清理**（統一格式與型態）與**語意清理**（判斷記錄是否代表它宣稱的事情，例如退款訂單不應計入營收）。前者多可自動化，後者往往需要領域知識，也因此最常被忽略。

## 技術要點

- **先定義「合格」**：把資料品質規則寫成明確的檢查清單（唯一鍵存在、值域合法、非空率門檻、時間戳合法範圍），沒有清單的清理會變成無止境的修補。
- **缺值分類處理**：區分「隨機缺失」「結構性缺失」「因未發生而為空」三種，空值策略必須分別決定，不能一律填中位數。
- **去重要有依據**：以事件唯一 ID 為準，而非以「欄位看起來一樣」判定，否則會誤刪合法重複（例如同日同品項的兩筆購買）。
- **型態正規化優先於刪除**：把「1,234」「１２３４」「1 234」統一為數值 1234，比刪除紀錄損失更小。
- **清理規則要版本化**：規則本身是程式碼，須納入版本控制，並記錄每條規則影響的筆數。
- **產出清理報告**：每次清理輸出筆數變化、規則命中統計與異常樣本，讓下游可以判斷資料是否可用。

## 範例：一份銷售資料的清理流程

**原始狀態**：單日訂單匯出檔 12,884 列，欄位為訂單編號、建立時間、商品編號、數量、單價、幣別、付款狀態。

1. **型態統一**：「數量」欄有 "2"、" 2 "、"2件"、"兩" 四種寫法；「單價」有 "$19.90" 與 "19.90"。以對應表轉換後，無法解析者共 37 列，列入待人工處理清單而非直接刪除。
2. **幣別正規化**：資料中混有 TWD 與 JPY，兩者以建立當日的匯率表換算為 TWD，匯率表版本隨資料一併存檔。
3. **缺值處理**：「付款狀態」空值 214 列，經比對後確認皆為尚未完成付款的訂單，故填入「未付款」而非刪除；「單價」空值 12 列屬於實際免費商品，填 0 會誤導統計，改以「單價缺失（贈品）」標記。
4. **去重**：以訂單編號 + 商品編號 + 建立時間（秒）為去重鍵，移除 96 列由重試機制產生的重複寫入，保留原始計數於報告中。
5. **邏輯檢查**：找出數量為負且付款狀態為已付款的 8 列，這是退貨被誤標為購買的系統性錯誤，必須回報來源系統修正，而非就地改成正值。
6. **結果**：可用列數 12,727（98.8%），規則命中統計、待處理清單與匯率表版本一併產出。

第 5 步是語意清理的典型：它發現的是**來源系統的意義問題**，這類問題不能靠清理解決，必須回頭修正系統，否則每一批資料都會重複出現同樣的錯誤。

## 與相鄰分類的關聯

- 與 [資料取得] 的關係：清理是取得之後的第一道工序，兩者的邊界在於是否改變資料內容。
- 與 [特徵工程] 的關聯：特徵工程建立在已清理的資料上，若清理不徹底，錯誤會被衍生特徵放大並難以追查。
- 與 [描述統計] 的關聯：清理直接決定描述統計的可信度；型態污染會讓平均數與標準差失真。
- 與 [偏差] 的關聯：清理時「刪掉看起來不對的列」是一種主觀取捨，若未記錄規則，會引入難以察覺的偏差。

## 容易混淆之處

- **清理不等於資料品質保證**：品質保證是長期監測與流程設計，清理是批次處理。
- **清理不等於去重**：去重只是清理的一種，且必須先定義「重複」的判準。
- **填補缺值不等於修補資料**：填補是統計假設，會把不確定性偽裝成確定。
- **清理不等於正規化到分析需求**：若清理只為讓某個模型好跑，會造成管線無法被其他用途重用。

## 常見的論爭

- **缺失值一律填補是否合理**：反對者認為填補會偽造資料；支持者認為在模型能吸收缺漏指標時，填補可保留樣本量。
- **清理應該自動還是人工**：自動規則可重現但可能誤判；人工判斷準確但不可重現，多數實務採「自動為主、人工抽樣覆核」。
- **是否應保留原始資料**：保留原始層佔用儲存，刪除則失去回溯能力，爭點在於法規要求與成本。

## 實務檢查清單

每次清理批次產出後，應逐項核對：

- 各規則命中多少列，占比是否在預期範圍內？
- 清理前後的筆數差異，是否有事先可解釋的理由？
- 缺值的處理方式是否與欄位文件一致？
- 型態轉換失敗的樣本是否全部進入待處理清單？
- 去重是否使用了明確的唯一鍵，而非欄位近似比對？
- 是否存在被整批刪除但未記錄原因的情況？
- 清理後的分布與前一批相比是否有異常跳動？
- 規則檔是否已提交版本控制並標註版本號？

## 進階考量

- **規則順序**：多條清理規則會互相影響，順序必須固定並記錄，否則同一批資料重跑可能得到不同結果。
- **轉換表維護**：型態對照表（如幣別、單位、狀態碼）本身是資料，必須有擁有者與更新流程。
- **跨表一致性**：使用者 ID、訂單 ID 等鍵在多張表中的編碼規則若不一致，關聯時會產生大量「查無此人」。
- **可回溯性**：清理後仍應能回答「這一列原本長什麼樣」，否則無法診斷下游的異常。
- **重算範圍**：修正一條早期規則時，應能只重算受影響的分區，而不是全表重跑。
