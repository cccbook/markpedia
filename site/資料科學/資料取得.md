# 資料取得

> 隸屬：[資料科學] › [資料流程]　·　狀態：初稿

> 對應維基百科：中文維基百科無對應條目　·　[English Wikipedia: Data collection](https://en.wikipedia.org/wiki/Data_collection)

資料取得（data collection）是把外部世界的紀錄搬進分析環境的過程。它回答的是三個問題：**來源在哪裡、抽取多少、以什麼頻率與時效抽取**。這三個答案一旦定下，資料的代表性與偏差就已經被決定了。

在傳統統計時代，資料取得主要是人工問卷與實驗測量，成本高但可控。網際網路把它徹底改變：事件日誌可以在使用者點擊的當下就產生一筆紀錄，數量以億計。於是「取得」不再是瓶頸，「篩選」與「治理」才成為瓶頸。

但可得性從未消除取樣問題。網站日誌只記錄**已經造訪**的人，問卷只回答**願意回答**的人，資料庫只包含**已經被記錄的交易**。每一種取得途徑都隱含一個母體定義，而母體定義就是偏差的來源。

因此資料取得在本質上是 [機率統計] 中抽樣設計的工程實作：先決定母體是誰，再用可辯護的方式抽出樣本，並留下抽樣過程的紀錄。

## 技術要點

- **先寫母體定義**：明確說明「我們想描述的對象是誰」，再決定資料來源；否則會取得大量與問題無關的資料。
- **來源分級**：交易資料（已發生、可靠）、系統日誌（詳細但偏技術）、第三方資料（覆蓋廣但定義未知）、問卷（直接但小樣本），四者應互補而非互相替代。
- **增量抽取與全量抽取**：全量每次重抽，簡單但昂貴；增量只抽新資料，靠水位線（時間戳或自增主鍵）維護，缺點是必須處理遲到與修改。
- **API 速率限制**：所有線上來源皆有配額，管線須內建退避重試與配額監控，否則一次流量高峰就會造成長期缺口。
- **欄位語意文件化**：每個欄位要記錄單位、允許值、更新頻率與空值意義；「0」與「無資料」在業務上常被混用而無從分辨。
- **原始層不可變**：抽出的原始資料只追加不改寫，所有清洗都發生在下游層，確保任何結論都能回到源頭重算。

## 範例：為推薦系統建立行為資料

**目標**：蒐集使用者對商品的瀏覽、收藏與購買行為，供推薦模型使用。

1. **母體定義**：先把母體寫清楚——「平台上的活躍使用者」，並明確排除內部測試帳號、機器人流量與已註銷帳號。
2. **來源選擇**：行為資料來自三個管道——前端埋點（瀏覽與收藏）、交易資料庫（購買）、與推送系統（曝光）。三者的使用者識別都統一到內部 user id，避免以裝置 id 造成的重複計算。
3. **抽取設計**：採每日增量抽取，以事件時間戳為水位線，並額外回補最近 72 小時以處理遲到事件；每日筆數約 1,900 萬。
4. **品質防線**：在抽取後立即檢查事件數波動（超過 ±20% 即告警）、user id 空值率（此時 0.03%）、時間戳逆序比例（0.11%）與欄位型態不符比例。
5. **同意狀態管理**：每個 user id 都對應到同意狀態（已同意／僅功能性／已撤回）；功能性事件與分析性事件分開落地，使撤回同意時可以只刪除分析用途的資料。
6. **文件化**：欄位字典寫入資料目錄，包含單位、允許值、更新頻率與空值意義，並由資料擁有者簽核。

這六步的關鍵在於**順序**：母體定義先於抽取，抽取先於品質檢查，同意狀態與資料落地綁定。若先抽後想「哪些要排除」，排除規則就會變成不可追溯的臨時腳本。

## 與相鄰分類的關聯

- 與 [清理] 的關係：取得階段的原始資料必然包含髒資料，清理是取得之後的第一道工序；兩者的邊界在於「是否改變資料內容」而非「是否碰資料」。
- 與 [樣本偏差] 的關係：每一種取得途徑都定義了被觀察到的群體，偏差由取樣設計決定，不是由分析技術決定。
- 與 [隱私] 的關係：埋點蒐集個人行為，涉及告知與同意，同意狀態必須在資料落地時就與資料同行。
- 與 [資料治理] 的關係：取得是資料進入組織的第一道閘門，資料目錄與權限設定都應在此建立。

## 容易混淆之處

- **取得不等於爬蟲**：爬蟲是取得的一種手段，且往往是最缺乏同意基礎的那一種。
- **取得量不等於代表性**：資料筆數再多，也無法補償母體定義錯誤。
- **即時性不等於完整性**：串流能降低延遲，但常以丟失重算能力為代價。
- **第三方資料不等於可信**：覆蓋廣不代表定義清楚，欄位語意常與自身系統不一致。

## 常見的論爭

- **事件日誌還是數倉快照**：前者細但成本高，後者簡單但回溯能力弱，爭點在於組織需要多細的行為顆粒度。
- **同意是否應逐項收集**：逐項同意尊重自主但提高流失率；概括同意易用但可能超出使用者預期。
- **平台內資料與第三方資料**：前者可控制但受限於自身產品，後者覆蓋廣但存在合規與信任風險。

## 實務檢查清單

在把新資料來源接入管線前，逐項確認：

- 這個來源對應的母體是誰，與既有來源是否重疊？
- 抽取是否有速率限制，重試策略為何？
- 延遲資料以什麼方式補回，補回期間的分析如何標示？
- 每個欄位的單位、允許值與空值意義是否已寫入資料目錄？
- 是否記錄了同意狀態，撤回同意時的處理流程為何？
- 抽取失敗時是重試、跳過還是告警，誰負責處理？
- 資料量比預期落差多少時觸發告警？
- 原始層是否可以由任何團隊成員唯讀保存？

## 進階考量

- **時間語意**：所有時間戳應統一為 UTC 儲存並保留原始時區，否則跨區域彙總時會出現無法解釋的偏移。
- **血緣追蹤**：每張衍生表都應能回溯到上游表與上游的版本，使得「數字為何如此」可以被回答。
- **存檔格式選擇**：原始層以列式格式存放可壓縮體積並加快聚合，但若需要隨機存取單筆紀錄，關聯式資料庫仍然合適。
- **成本結構**：抽取本身通常便宜，麻煩在於重跑時的計算量與下游等待時間，因此應控制重算範圍。
- **契約變更管理**：上游新增欄位多半無害，改名或改型別則是破壞性變更，須在協調窗口進行。
