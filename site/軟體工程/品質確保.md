# 品質確保

> 隸屬：[軟體工程]　·　狀態：初稿

> 對應維基百科：[中文維基百科：品質保證](https://zh.wikipedia.org/wiki/%E5%93%81%E8%B3%AA%E4%BF%9D%E8%AD%89)　·　[English Wikipedia: Software quality assurance](https://en.wikipedia.org/wiki/Software_quality_assurance)

品質確保研究**如何以客觀證據證明軟體符合其規格，且這些證據可以被重複取得**。它與品質保證不同：品質保證偏向「保證過程正確執行」（例如規定每個需求都要有對應測試），品質確保偏向「取得證據證明成品符合要求」（例如測試執行報告、缺陷率報告）。

軟體品質的難處在於**缺陷的種類極多且成本不均**：語法錯誤在編譯期就被攔截，邏輯錯誤可能在數月後才被發現，而需求誤解造成的缺陷即使測試全綠也不會消失。因此品質確保必須覆蓋從需求到運作的每一層，靠單一手段無法窮舉。

現代品質確保的核心觀念是**預防勝於偵測**：把檢查點前移，讓缺陷在成本最低的位置被發現。這正是 [持續整合] 的理論依據——把驗證成本從「每次發布的龐大批次」降為「每次提交的極小批次」。

## 技術與理論的關聯

- **品質是屬性，不是二元判定**：可靠性、效能、可維護性、可移植性彼此張力，一個提升可靠性的改動可能降低效能，因此品質確保必須是「針對屬性的度量」。
- **測試是統計性論證**：隨機測試只能發現已執行的缺陷，因此覆蓋率是「已被檢查的空間比例」，而非「已無缺陷的保證」。
- **缺陷密度是重要的團隊指標**：單位程式碼行數或功能的缺陷數，比總缺陷數更難以用數量灌水。
- **獨立驗證避免自我確認**：由不同於實作者的角色執行 [程式碼審查] 與測試，能捕捉實作者因系統性假設而看不見的錯誤。
- **回歸測試守護既有行為**：隨著系統演進，回歸套件的累積成本會成為改動速度的實質上限。
- **自動化是量產的前提**：手動測試的執行成本隨版本數線性成長，自動化把它降為固定成本，使高頻發布成為可能。

## 範例

以一個「每月釋出的記帳應用程式」為例，說明四類證據如何分工。

1. **單元測試**：對金額計算、稅額四捨五入與日期跨月處理寫表格驅動測試，覆蓋邊界值（0、負數、超過 2,147,483,647 的合計）。這些測試可在毫秒內執行，因此每次提交都跑。
2. **程式碼審查**：審查者特別檢查「資料庫交易是否與檔案寫入在同一交易中」這類跨元件一致性問題——這類錯誤單元測試看不出來。
3. **整合測試**：以真實資料庫（測試用容器）與模擬的外部稅務服務跑完整流程，驗證 API 契約與資料格式對得上。
4. **持續整合**：流水線依序執行「格式檢查 → 靜態分析 → 單元測試 → 整合測試 → 建置產物」，任一步失敗即阻止合併。
5. **發布後監控**：以實際使用資料比對預期，用量異常與錯誤率上升視為品質訊號，觸發 [回滾] 或熱修。

這五層證據的分工說明：**每一層只能證明它能證明的事**。單元測試無法證明元件之間的契約，靜態分析無法證明需求被正確理解，監控無法預防下一次提交引入的新錯誤。

## 前因後果

早期軟體以「測試者手動點擊」驗證，隨著系統規模擴大，此法完全不可行。1957 年 [艾倫·凱] 等人提出的「測試先行」觀念，配合 1960 至 1970 年代結構化測試與覆蓋率工具的發展，讓「可自動驗證」成為工程要求。

1990 年代，極限編程（XP）把測試自動化推到開發者本地，每次提交前必須全數通過；2000 年代持續整合把驗證中心化到伺服器上，使「綠色才可合併」成為團隊契約。與此同時，安全與合規領域的審計要求，又把品質確保從「工程實務」推向「可稽核的制度」，例如要求測試證據與需求、版本一一對應。

## 與相鄰分類的關聯

- 與 [軟體開發流程] 的關係：品質確保的檢查點位置由流程決定，末端集中測試與每次提交測試是兩種截然不同的風險配置。
- 與 [設計模式] 的關係：可測試的設計（依賴注入、介面化）讓單元測試能用替身取代真實協作者，否則測試將被外部系統綁架。
- 與 [需求工程] 的關係：驗收條件是測試案例的來源，需求若不可驗證，品質便無法度量。
- 與 [維護與演進] 的關係：回歸測試套件是維護成本的固定成員，也是重構的安全網。
- 在上位概念 [軟體工程] 中，本概念扮演「證據層」：它把「相信」換成「看見」，是流程得以收縮的前提。

## 容易混淆之處

- **品質保證與品質確保不同**：前者管過程，後者管證據。
- **測試與除錯不同**：測試顯示「有錯」，除錯找出「錯在哪並修掉」。
- **覆蓋率高不等於品質高**：覆蓋率只衡量執行的行數，不衡量斷言的強度與情境的代表性。
- **沒有缺陷不等於系統正確**：未被寫下的需求、罕見的邊界條件與環境相依的失效都不會出現在測試報告裡。
- **自動測試不等於好測試**：自動化的錯誤測試只是更快地產生錯誤信心。

## 技術要點

1. **測試金字塔要合理**：底層單元測試數量多且快，頂端端到端測試少而慢；比例失衡會讓套件既慢又不穩。
2. **每個缺陷都要有回歸測試**：缺陷是流程回饋的原料，沒有回歸測試的缺陷會再回來。
3. **CI 必須是門禁**：若合併不要求通過，流水線就只是資訊看板。
4. **度量缺陷逃逸率**：上線後才被發現的缺陷比例，直接反映驗證的有效性。
5. **讓測試可觀測**：報告需顯示執行時間、失敗原因與覆蓋率變化，否則無人能在第一時間看出退化。
6. **把非功能需求轉成測試條件**：效能與安全需求若沒有對應的自動化檢查，就等於沒有被驗證。

## 常見的論爭

1. **測試覆蓋率作為品質指標是否有用**：支持者認為它是可比較的最低指標；反對者認為它鼓勵為覆蓋而寫無意義的測試，並忽略缺陷密度與逃逸率。
2. **人工審查與自動化測試孰優**：經驗上兩者互補，但審查品質高度依賴人與時間壓力；爭點在於如何設計團隊制度讓審查真的發生。
3. **測試先行是否適用於所有領域**：探索性與資料驅動的開發往往難以先寫測試；支持者認為可先寫高階驗收測試，實務上仍存在先做後測的合理情境。
