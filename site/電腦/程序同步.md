# 程序同步

> 隸屬：[電腦] › [作業系統]　·　狀態：初稿

> 對應維基百科：[中文維基百科：同步 (計算機科學)](https://zh.wikipedia.org/wiki/%E5%90%8C%E6%AD%A5_%28%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%A7%91%E5%AD%A6%29)　·　[English Wikipedia: Synchronization (computer science)](https://en.wikipedia.org/wiki/Synchronization_%28computer_science%29)

程序同步是**讓多個並行執行單元在共享資料時保持一致、按規則協作的機制**。並行執行的指令以不可預測的順序交錯，若兩個行程同時加減同一變數、兩個執行緒同時更新同一鏈結串列，結果取決於時序——這叫競態條件。同步的任務就是消除「結果依賴時序」的部分：要嘛互斥（一次一人）、要嘛協調（你等我、我等你）。

這個條目是作業系統中理論味最濃的一章：號誌、監視器、條件變數與一整串經典難題（哲學家就餐、生產者—消費者、讀者—寫者），以及它們背後的死結理論。

## 技術與理論的關聯

- **競態的根源**：一行程式在機器層是多條指令，切換可發生在任意指令之間；「讀—改—寫」三步被切開就會丟更新。
- **臨界區與互斥**：需要獨佔的區段叫臨界區；互斥鎖保證同時至多一個執行單元在內，代價是等待。
- **號誌**：整數加 P（申請，歸零則睡）與 V（釋放，喚醒一人）兩個原子操作；二元號誌即互斥鎖，計數號誌可允許 N 個並行。
- **監視器與條件變數**：把共用資料與鎖封裝成一個物件，條件變數的 wait/signal 表達「條件未滿先睡」——Java 的 synchronized 與 Python 的 condition 都源自此。
- **原子指令與無鎖**：硬體的測試並設定（TAS）、比較並交換（CAS）讓鎖可以「自旋」而非睡眠；無鎖資料結構直接以 CAS 構成，等待者永遠不睡，但設計極易出錯（ABA 問題）。
- **死結四條件**：互斥、持有並等待、不可剝奪、循環等待同時成立才會死結；銀行家演算法事先判斷資源請求是否安全，破壞任一條件則預防（如全序加鎖破壞循環等待）。

## 範例

**問題**：兩個執行緒各執行 100000 次 `counter++`，初值 0，結果是多少？

1. **天真的預期**：200000。實際上每次執行都不同，常見 120000 至 199000 之間的任意值。
2. **原因**：`counter++` 編譯成三條指令：載入暫存器、加一、存回。兩執行緒交錯時，兩次加一可能都從同一初值讀起，各存回同一新值——一次更新蒸發。
3. **互斥鎖解法**：把三條指令包進 `lock(&m); counter++; unlock(&m);`；結果穩定為 200000，但鎖把並行退回序列，吞吐量下降。
4. **自旋鎖的取捨**：臨界區極短（三條指令）時，自旋比睡醒（上下文切換約數微秒）便宜；臨界區長則自旋燒 CPU，睡眠鎖正確。
5. **無鎖對照**：以 CAS 迴圈 `do { old = counter; } while (!compare_and_swap(&counter, old, old+1));` 無需鎖即正確；失敗者重試，競爭激烈時重試本身成為熱點。
6. **啟示**：同步的真正成本不在鎖本身，而在「共用狀態」——最好的同步是沒有共享（每執行緒私用計數器、最後合併）。

## 前因後果

- **前因**：多工程式（1960 年代）出現後，輸出交錯與資料損壞迫使學界形式化並行問題；Dijkstra 1965 年提出號誌與「協作順序」問題，Hansen 與 Hoare 提出監視器。
- **後果**：同步機制成為所有執行緒庫、資料庫鎖、分散式共識（Raft、Paxos 是同步思想的網路版）與無鎖程式設計的理論源頭；記憶體模型（Java、C++）的規範化讓跨核可見性也有法可依。

## 與相鄰分類的關聯

- 與 [行程] 的關聯：同步對象可以是行程或執行緒，理論相同。
- 與 [中斷] 的關聯：單核時代的關中斷是最原始的互斥；多核時代改用原子指令。
- 與 [資訊安全] 的關聯：競態本身是漏洞類別（TOCTOU：檢查後使用），同步缺失直接成為攻擊面。
- 在上位概念 [作業系統] 中，程序同步處理「共享」帶來的全部複雜度。

## 容易混淆之處

- **互斥與同步不同**：互斥防並入，同步（條件協調）管順序；生產者—消費者兩者都要。
- **死結與活結、飢餓不同**：死結是互相等待卡死，活結是一直禮讓繞圈，飢餓是有人永遠搶不到。
- **自旋鎖與互斥鎖不同**：前者原地等、後者睡覺讓位；單核上自旋幾乎總是錯的。
- **CAS 正確不等於無鎖演算法正確**：ABA 問題、記憶體排序錯誤都藏在使用者看不見的位元層。

## 技術要點

- P/V 操作必須原子，實作靠硬體 TAS 或關中斷加自旋的組合。
- 優先權反轉以優先權繼承協定處理（火星探路者 1997 年的著名故障）。
- 雙階段鎖定與死結偵測：資料庫以等待圖找環，找到就挑一個交易犧牲。
- 記憶體屏障（fence）控制指令重排的可見性，是無鎖程式設計的地基。
- 管道訊號（condvar）的虛假喚醒要求 wait 放在 while 迴圈內。
- 計數號誌的經典應用是限制並行度（連線池、執行緒池）。

## 常見的論爭

- **鎖的粒度**：粗鎖好寫好驗證、細鎖高效易死結，「先粗後細」與「設計即細」兩派工程文化並存。
- **無鎖 vs 鎖**：無鎖理論上免除死結且可擴展，但正確性極難證明；業界傾向「用驗證過的庫」而非手寫。
- **共用記憶體 vs 訊息傳遞**：Go 的口號「以通訊共享記憶體，別以記憶體共享通訊」代表後者，Erlang、Actor 模型同陣營；共用記憶體派以高效能反擊。

## 實務補充：鎖的代價與現代替代品

互斥鎖在多核心機器上並不便宜：未爭用時約數十奈秒，爭用時可能高達數微秒，且可能造成快取列在核心間來回轉移。高效能系統因降低鎖頻率、改用無鎖資料結構（lock-free、wait-free）與不可分割操作。

現代 CPU 提供如 compare-and-swap 的硬體原子指令，使無鎖佇列、堆疊與記憶體池得以實作；C++11 起的原子類別與 Rust 的所有權模型則讓「正確使用並行」從技巧變成型別系統可以強制的性質。

另一個方向是降低共享需求：不可變資料與函式式程式設計讓多執行緒之間只透過訊息溝通，把競爭從共享記憶體移回訊息佇列，讓除錯成本大幅下降。
