# 物件導向

> 隸屬：[程式設計]　·　狀態：初稿

> 對應維基百科：[中文維基百科：面向对象程序设计](https://zh.wikipedia.org/wiki/%E9%9D%A2%E5%90%91%E5%AF%B9%E8%B1%A1%E7%A8%8B%E5%BA%8F%E8%AE%BE%E8%AE%A1)　·　[English Wikipedia: Object-oriented programming](https://en.wikipedia.org/wiki/Object-oriented_programming)

物件導向是**把資料與操作資料的行為綁在一起、組成「物件」的程式設計典範**：每個物件同時持有狀態（屬性）與行為（方法），物件之間透過訊息傳遞互相作用。物件導向的三大支柱是封裝、繼承與多型，其工程目標是讓大型系統的複雜度被切割到可管理的邊界之內。

## 技術與理論的關聯

- **封裝把不變量變成可檢查的**：物件的私有狀態只能透過受控方法修改，於是「狀態必須合法」可以由類別本身保證，而不是靠全體程式碼的自律。
- **多型使呼叫端與實作端解耦**：呼叫端只依賴介面，替換實作不必修改呼叫端，這是依賴反轉與外掛架構的基礎。
- **抽象資料型別的實作**：物件導向把「資料型別」與「操作該型別的運算」綁在一起，是資訊隱蔽與模組化的具體化。
- **型別系統的多型機制**：物件導向的多型本身就是一種型別機制（子型多型），與 [型別系統語法] 中的名目型別、結構型別互相對應。
- **訊息傳遞對應行程與程序**：物件的「方法呼叫」在機器層是控制轉移，在 [作業系統] 層則是訊息佇列與行程間通訊，兩者共同構成物件導向的實作基礎。

## 三支柱與實務修正

- **封裝**：隱藏內部表示，只暴露穩定介面。實務上封裝常被「public 欄位」破壞，一旦欄位公開，內部表示就無法安全更改。
- **繼承**：以「is-a」關係建立型別層次。實務教訓是「組合優於繼承」：繼承耦合緊、跨類別層次的修改容易造成深層連鎖反應，組合則以傳參數的方式保持鬆耦合。
- **多態**：同一呼叫點依執行期實際型別分派到不同實作，分為子型多型（方法覆寫）與參數多型（泛型）。
- **組合與聚合**：以「has-a」組裝小物件達成重用，比深層繼承樹更易理解與測試。
- **SOLID 原則**：單一責任、開放封閉、里氏替換、介面隔離、依賴反轉，是物件導向設計的經驗總結。

## 範例：形狀的繼承體系與它的問題

```
abstract class Shape:
    def area(self) -> float:
        raise NotImplementedError

class Circle(Shape):
    def __init__(self, r):
        self.r = r
    def area(self) -> float:
        return math.pi * self.r ** 2

class Rectangle(Shape):
    def __init__(self, w, h):
        self.w = w
        self.h = h
    def area(self) -> float:
        return self.w * self.h

class Square(Rectangle):
    def __init__(self, s):
        super().__init__(s, s)
```

呼叫端只依賴 `Shape` 介面：

```
def total_area(shapes):
    return sum(s.area() for s in shapes)
```

這是物件導向最漂亮的樣子：新增 `Triangle` 不必修改 `total_area`。但它同時示範了兩個陷阱：

1. **`Square` 繼承 `Rectangle` 破壞不變量**：`Rectangle` 允許 `w != h`，`Square` 卻保證相等；`Rectangle.set_width` 之類的方法在 `Square` 上語意不成立（里氏替換原則被違反）。
2. **繼承耦合**：若 `Rectangle` 日後新增一個方法名稱與 `Square` 的某個欄位衝突，修改會沿繼承樹擴散。

改進方式是用組合而非繼承：讓 `Square` 直接持有一個 `Rectangle`，或抽出 `Shape` 介面讓兩者各自獨立實作。

## 範例：封裝如何把錯誤變成不可能

```
class Temperature:
    def __init__(self, celsius):
        self._celsius = float(celsius)

    @property
    def celsius(self):
        return self._celsius

    @property
    def fahrenheit(self):
        return self._celsius * 9 / 5 + 32
```

若改為公開欄位 `t.celsius = 1000`，任何人都能塞入不合理數值，所有換算邏輯都得自行防守；改成私有欄位加屬性後，非法狀態在建立時就被拒絕。**封裝的真正價值不是隱藏，而是讓錯誤的表示無法被構造。**

## 前因後果

- **前因**：1960 年代的批次處理語言讓「程式 + 大量共享資料」成為維護噩夢；Simula（[1967年]）引入類別以模擬實體，Smalltalk（1970 年代）把它推成完整典範，[1969年] 的 C 語言則同時提供了硬體效率。
- **後果**：1980–2000 年代，物件導向成為企業軟體的預設方法論，帶動了設計模式、依賴注入與現代 [軟體工程] 方法論；同時也產生了「深層繼承樹」「上帝類別」等反模式，並促成語言層面的補救（介面、泛型、mixin）。

## 與相鄰分類的關聯

- 與 [語言典範] 的關係：物件導向是四典範中最偏工程組織的一個。
- 與 [型別系統語法] 的關係：子型多型是型別系統設計的核心機制之一。
- 與 [命令式] 的關係：物件導向並未廢除命令式，而是限制可變狀態的暴露範圍。
- 與 [軟體工程] 的關係：模組邊界、介面穩定性與測試替身皆源於此。

## 容易混淆之處

- **物件導向不等於有 class 關鍵字**：JavaScript 的原型鏈與 Go 的介面隱含實作同樣是物件導向。
- **封裝不等於把欄位設成 private 就結束**：真正的封裝是「內部表示可自由更改而不影響外界」。
- **物件導向不等於一定更易測**：若物件持有全域資源或隱藏副作用，測試反而更難。
- **繼承不等於重用**：繼承關係表達「是一種」，用它來重用程式碼常造成脆弱基類問題。

## 技術要點

- 三支柱：封裝、繼承、多型；實務上以組合取代多數繼承。
- 依賴注入讓物件取得外部協作者，是可測試性的關鍵手段。
- 設計模式是可重用的物件协作結構，命名有助於溝通，但過度套用會增加複雜度。
- 垃圾回收讓物件的生命週期管理大幅簡化，是物件導向普及的技術前提之一。
- 不可變物件是兩種典範的交會點：可以有類別與封裝，卻不提供 setter。

## 常見的論爭

- **物件導向是否過度吹捧**：批評者認為它把簡單問題複雜化，且繼承樹難以重構；支持者強調封裝邊界對大型團隊分工的價值。
- **組合是否應完全取代繼承**：實務共識是「預設組合、慎用繼承」，但何謂「慎用」缺乏客觀標準。
- **mixin 與多重繼承**：折衷方案增加了語意複雜度，卻解決了語言層面的限制。
