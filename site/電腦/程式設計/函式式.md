# 函式式

> 隸屬：[程式設計]　·　狀態：初稿

> 對應維基百科：[中文維基百科：函数式编程](https://zh.wikipedia.org/wiki/%E5%87%BD%E6%95%B0%E5%BC%8F%E7%BC%96%E7%A8%8B)　·　[English Wikipedia: Functional programming](https://en.wikipedia.org/wiki/Functional_programming)

函式式是**以函式為基本單位、並要求函式保持「純粹」的程式設計典範**：純函數只依賴輸入、只產生輸出，不改變外部狀態、不產生副作用。由於沒有共享的可變狀態，函式的行為完全由其引數決定，因此可以被自由組合、重複呼叫、並行執行與推理驗證。

## 技術與理論的關聯

- **λ 演算是一切的基礎**：[1930年] Church 提出的 λ 演算證明「只用函式的定義與套用」就能表達所有可計算的量，這是函式式的理論原點。
- **Curry–Howard 對應**：命題對應型別、證明對應程式，因此「通過型別檢查」就是一種形式化證明；函式式語言與型別理論的結合是數學與工程最緊密的交會之一。
- **遞迴取代迴圈**：在數學上，遞迴地定義函式是自然的（數學歸納法同理），因此函式式語言幾乎都以遞迴而非迴圈為基本迭代機制。
- **不變性帶來可組合性**：若資料不可變，任何持有舊參考的人都不會看到「半途被改掉」的值，程式因此可安全並行。
- **代數結構的影響**：串列的 `map`、`filter`、`fold` 對應到函數的合成與套用，使集合操作有統一的抽象層。

## 函式式的核心特徵

- **純函數**：輸出只由輸入決定，無副作用、可重複呼叫、可用等價替換推理。
- **不可變資料**：資料一旦建立就不改變；「更新」實際上是產生一份新資料。
- **高階函數**：函式可作為值傳遞、作為引數接收、作為結果返回。
- **遞迴與尾呼叫**：以呼叫自身取代迴圈；尾呼叫最佳化讓深遞迴不致爆堆疊。
- **代數資料型別**：型別由建構子組合而成，如「一個空或一個值」的型別，可窮舉所有情況。
- **副作用隔離**：I/O 集中在邊界（主函式或效應管理器），核心邏輯保持純粹。

## 範例：串列處理的四種表達

**命令式（明確迴圈）**：

```
def lengths(names):
    out = []
    for n in names:
        out.append(len(n))
    return out
```

**以內建高階函式（仍是函式式風格）**：

```
lengths = lambda names: list(map(len, names))
```

**以 fold 表達（最貼近代數觀點）**：

```
def lengths(names):
    return foldr(lambda n, acc: len(n) : acc, [], names)
```

**以代數資料型別表達（Rust 的風格）**：

```
enum List {
    Cons(i64, List),
    Nil,
}

fn lengths(xs: &List) -> List {
    match xs {
        Cons(_, rest) => Cons(1 + head_len(xs), lengths(rest)),
        Nil => Nil,
    }
}
```

四種寫法最根本的差別是：前三種最終仍由語言的迴圈機制執行，但把「做什麼」從「怎麼做」中抽離；第四種則是真正把控制流交給型別結構本身——匹配 `Cons` 與 `Nil` 兩種情形，函式的定義即窮盡了所有輸入。

## 範例：純函數與不純函數的差別

```
// 純函數：相同的輸入永遠給出相同的輸出
def tax(amount, rate):
    return round(amount * rate, 2)

// 不純函數：依賴外部狀態，輸出可能不同
def tax_with_discount(amount, rate):
    global discount
    return round(amount * rate * discount, 2)
```

第二個版本不是「壞的」，但它帶來三個實際代價：

1. **測試困難**：必須先設定全域 `discount` 才能斷言結果。
2. **並行不安全**：兩個執行緒同時改動 `discount` 會造成競態。
3. **無法推理**：閱讀者無法只看函式本體就判斷它的行為。

把 `discount` 改成引數傳入，函式即恢復純粹——這就是函式式設計的第一個實用動作。

## 前因後果

- **前因**：λ 演算（1930 年）與 [1936年] 的 Church 編碼理論提供了理論基礎；[1958年] Lisp 把函式式思想帶入實際程式語言，但保留了可變狀態；1970 年代起 ML 家族加入型別系統，Haskell（[1990年]）則是首個純函數式語言的主流化。
- **後果**：函式式思想滲入現代語言的每一個主流——不可變結構、map/filter、lambda、模式比對、不可變集合；MapReduce 與不變日志的設計哲學直接來自此；同時它也催生了「函數式核心、命令式外殼」的務實折衷。

## 與相鄰分類的關聯

- 與 [語言典範] 的關係：函式式是理論最紮實、也最容易被部分吸收的典範。
- 與 [型別系統語法] 的關係：型別系統讓函式的組合可以被機器驗證，是函式式在工業界落地的前提。
- 與 [控制結構] 的關係：遞迴與高階函式取代了大部分迴圈，成為函式式的執行模型。
- 與 [命令式] 的關係：兩者是互補策略——「函數式核心、命令式外殼」是主流實務共識。

## 容易混淆之處

- **函式式不等於沒有變數**：它禁止的是「修改已綁定的狀態」，不是命名本身。
- **使用 lambda 不等於函式式**：C++ 的 lambda 只是匿名函式物件，若仍大量使用可變狀態，程式仍是命令式的。
- **不可變不是效能一定好**：大量小物件的建立會造成配置壓力，需要結構化共享等技術補償。
- **函式式不等於函數式風格的全家桶**：高階函數、不可變、副作用隔離三者常被混為一談，但可以各自獨立採用。

## 技術要點

- 尾呼叫最佳化是深遞迴能安全使用的關鍵。
- 代數資料型別的窮舉匹配讓「漏處理一種情況」變成編譯錯誤，屬於 [型別系統語法] 討論的範疇。
- 惰性求值把「何時計算」交給需求決定，能表達無限串列，但也使效能推理更困難。
- 記憶化是純函式的自然優化：相同輸入不重算。
- 副作用隔離的邊界設計（effect monad、effect handler）是純函數式語言處理 I/O 的核心機制。

## 常見的論爭

- **純粹性是否值得**：支持者強調可測試與可並行；批評者指出真實系統難以避免副作用，且過度抽象增加閱讀成本。
- **多核時代的重新評價**：不可變資料曾被視為效能負擔，現今硬體並行度提高後，其可無鎖共享的特性反成優勢。
- **是否需要專門語言**：Haskell 等純語言長期 niche，但 Rust、Swift、Kotlin、Scala 的功能特徵說明思想已被主流吸收。
