# 版本控制

> 隸屬：[程式設計] › [開發方法]　·　狀態：初稿

> 對應維基百科：[中文維基百科：版本控制](https://zh.wikipedia.org/wiki/%E7%89%88%E6%9C%AC%E6%8E%A7%E5%88%B6)　·　[English Wikipedia: Version control](https://en.wikipedia.org/wiki/Version_control)

版本控制是**記錄程式碼每一次變更、並允許隨時回到任何歷史版本的系統性做法**，白話說就是「幫程式碼建立可回溯的履歷表」。它的最小單位是**提交（commit）**：一次提交把一組相關的檔案變更包成一個有說明、有作者、有時間戳的節點。

版本控制的真正價值不在「存檔」，而在**讓多人並行修改同一份程式碼**。當變更歷史以提交圖（有向無環圖）的形式存在，「誰改了什麼」「兩條開發路線如何合併」「這段程式碼是什麼時候進來、為什麼進來」都變成可查詢的問題；這正是 [程式碼審查] 與 [測試驅動] 能夠運作的物理基礎。

## 技術與理論的關聯

- **版本控制把開發變成一條可回溯的歷史**：每次提交都是不可變的節點，錯誤可以精確地二分（bisect）到引入問題的那一次提交——「二分搜尋」這個演算法在提交圖上有了直接的應用。
- **分散式與集中式是權威歸屬的差異**：集中式版本控制（CVS、Subversion）由伺服器保存權威歷史；分散式版本控制（Git、Mercurial）讓每個用戶端都持有完整歷史，可離線提交、互相推送，權威因此不再由系統指定。
- **差分儲存降低儲存成本**：只記錄每個版本相對於前一個版本的差異（delta），使數千個版本的儲存量從平方級降到近似線性；RCS 與後來的 Git 都採此法。
- **提交圖是有向無環圖**：分支是圖上的分岔，合併是圖上的匯流點；理解「提交圖」而非「分支清單」，是現代版本控制技能的真正核心。
- **版本控制與開發流程互相塑造**：長期存在的分支是合併衝突的主要來源，因此短生命週期分支加主幹開發（trunk-based development）成為主流實務，Git Flow 等模型則在需要長期支援分支時另有位置。
- **標籤與提交是同一套機制的不同用法**：標籤只是指向特定提交的具名指標，用於發版與回滾。
- **版本控制是資料庫問題**：提交圖要能安全地同時被多人讀寫，且在斷電或網路中斷時不致損毀，因此底層多以不可變物件與原子操作實作。

## 範例：一個功能從開分支到合併的完整指令流程

```bash
# 1. 從最新主幹切出功能分支
git switch -c feature/bulk-discount

# 2. 開發過程中隨時查看狀態與差異
git status
git diff

# 3. 提交：一次提交一個意圖，訊息說明「為什麼」而非「改了什麼」
git add cart.py tests/test_cart.py
git commit -m "購物車滿千打折九五折，並補上邊界測試"

# 4. 推送並發起審查（審查本身就是版本控制工作流的一部分）
git push -u origin feature/bulk-discount

# 5. 若測試失敗，用二分找出引入問題的提交
git bisect start
git bisect bad HEAD
git bisect good v2.3.0
# 逐一測試，git bisect 會自動收斂到第一個壞掉的提交

# 6. 合併回主幹後，若發現問題可安全回滾
git switch main
git merge --no-ff feature/bulk-discount
git tag v2.4.0
```

這串指令的每一段都對應一個工程問題：分支解決並行開發，`diff` 與小而聚焦的提交服務於審查，`bisect` 服務於除錯，合併與標籤服務於發版。沒有版本控制，這些問題都只能靠記憶與口頭約定解決。

## 前因後果

- **前因**：1970 年代以前，程式碼以打孔卡片與紙本備份保存，修改的痕跡完全消失；多人同時修改同一個檔案時，最常見的結果是某人覆蓋掉別人的工作。
- **起步**：[1972年] 的源碼控制系统（SCCS）以「只存差異」的思路首次把變更歷史自動化；[1982年] 的 RCS（Revision Control System）成為 Unix 世界的主流工具。
- **擴散**：[1986年] 的 CVS 支援多人共享同一個儲存庫，長期成為開放原始碼社群的標準配備，也催生了「先更新再提交」的紀律。
- **轉折**：[2000年] 的 Subversion 修正了 CVS 許多設計缺陷，成為企業採用最多的集中式方案。
- **改變產業**：[2005年] 發布、並在數年內成為事實標準的 Git，以分散式模型、極快的分支成本與低摩擦的合併，重新定義了協作方式；[2008年] 上線的 GitHub 把「提交圖 + 審查 + 追蹤」包成網路服務，開源協作因此從少數人的興趣變成產業結構。
- **後果**：分支成本大幅下降，於是「每個功能一個分支」成為可能（推動 [敏捷] 的短週期迭代）；程式碼倉庫也成為新的法律與治理爭點（程式碼授權、貢獻者協議與供應鏈安全）。

## 與相鄰分類的關聯

- 與上位概念 [開發方法] 的關係：版本控制是四件配備的底層——沒有提交圖，審查、測試與迭代都無從談起。
- 與 [程式碼審查] 的關係：審查以提交或 Pull Request 為單位，審查的對象正是版本控制的差異。
- 與 [測試驅動] 的關係：每次綠燈重構都對應一次提交，測試讓提交可以安全地進行。
- 與 [軟體工程] 的關聯：版本控制是 [DevOps] 流水線（持續整合、持續部署）的技術前提；分散式模型也改變了團隊的權力結構。
- 與 [迭代] 的關係：迭代的每次交付成果都以標籤或版本號被標記，成為可回滾的時間點。

## 容易混淆之處

- **版本控制不等於備份**：版本控制記錄的是變更，備份保護的是資料；未提交的變更不在版本控制保護範圍內。
- **分支不等於副本**：分支是指針而非整份拷貝，建立分支成本極低；把分支當副本會造成大量重複與合併混亂。
- **提交不等於發版**：發版通常由特定提交加上標籤、設定檔與建置流程組成。
- **Merge 不等於Rebase**：合併保留兩條歷史，變基重寫歷史；對已共享的提交做變基會造成他人副本不一致。
- **分散式不等於沒有中心**：Git 可以有單一的權威遠端；「分散式」描述的是能力，不是治理方式。

## 技術要點

1. **提交要小而聚焦**：一次提交對應一個可獨立說明與回滾的意圖，這是審查與二分除錯的前提。
2. **提交訊息寫「為什麼」**：差異本身已說明「改了什麼」，訊息應說明動機與背景。
3. **先更新再合併**：合併前先取得上游最新版本，衝突面越小越好處理。
4. **用標籤標記發版點**：發版標籤是事故回滾的錨點，應視為正式產物管理。
5. **善用二分除錯**：當壞掉的提交範圍不明時，`git bisect` 能在數十次測試內定位問題提交。
6. **.gitignore 要從一開始就正確**：被誤提交的建置產物與憑證會永久留在歷史中，僅靠後續刪除並不能真正移除。
7. **保護重要分支**：對主要分支設定保護規則、要求審查與建置通過，是把工程紀律寫進工具的作法。

## 常見的論爭

- **集中式 vs 分散式**：集中式便於權限管理與備份，分散式在離線與並行開發上有優勢；Git 問世後，業界大致轉向分散式並以約定補足治理。
- **主幹開發 vs Git Flow**：前者主張短分支直接併入主幹，後者以長期整合分支支應多版本並行；爭點在團隊能否承受頻繁合併。
- **單一大型儲存庫 vs 多儲存庫**：大型儲存庫簡化相依管理與統一工具，卻放大建置時間與權限問題；工具鏈的成熟度是關鍵變數。
- **提交歷史的公開性**：把歷史視為公開文件，使「如何提交」本身成為專業技能，也讓審查與溝通紀律受到外部檢視。
