# 命令式

> 隸屬：[程式設計]　·　狀態：初稿

> 對應維基百科：[中文維基百科：指令式編程](https://zh.wikipedia.org/wiki/%E6%8C%87%E4%BB%A4%E5%BC%8F%E7%B7%A8%E7%A8%8B)　·　[English Wikipedia: Imperative programming](https://en.wikipedia.org/wiki/Imperative_programming)

命令式是**以「一個接一個改變系統狀態的指令」來描述程式的典範**：程式是一串陳述句，每一句都告訴機器「現在做這件事」，執行的順序就是語句的順序。變數是可變的儲存格，賦值是核心動作，程式行為因此可以用「執行軌跡」逐步追蹤。命令式與 [馮·諾伊曼] 架構的對映最直接，是幾乎所有主流語言的預設寫法。

## 技術與理論的關聯

- **圖靈機是命令式的理論模型**：紙帶上的格是變數，讀寫頭的動作是陳述句，狀態轉移函式就是程式本身；[圖靈] 的論證因此直接支持命令式程式的通用性。
- **馮·諾伊曼架構的軟體對應**：儲存器對應變數，累加器對應暫存器，控制流對應分支；硬體設計與語言語彙互相塑造，見 [馮·諾伊曼]。
- **副作用是命令式的特徵**：變數賦值、I/O、全域狀態改變都會影響後續指令的結果；這讓命令式程式難以推理，但也讓它能精確控制資源與時序。
- **迴圈與分支是其基本骨架**：它們在 [控制結構] 中佔有核心地位，且幾乎一一對應到機器碼的跳躍指令。
- **可變狀態是錯誤的主要來源**：狀態隨時間變化，使得「同一段程式在兩次執行中結果不同」成為可能，這正是後來各種典範要處理的問題。

## 命令式的構成要素

- **變數與賦值**：把值綁定到名字，或覆蓋名字原本的值。
- **順序性**：預設由上而下執行，除非用分支或迴圈改變順序。
- **副作用**：程式行為不只取決於輸入，還取決於被改變的外部狀態。
- **程式計數器**：隱含「現在執行到哪一行」的概念，錯誤訊息中的行號就是它的投影。
- **可變參數與引用**：允許子程式直接修改呼叫者的資料，效率高但耦合強。

## 範例：同一個排序的三種命令式寫法

需求：將一個整數陣列由小到大排序。

**以巢狀迴圈做交換排序（最古典的命令式）**：

```
def bubble_sort(a):
    n = len(a)
    for i in range(n - 1):
        for j in range(0, n - 1 - i):
            if a[j] > a[j + 1]:
                a[j], a[j + 1] = a[j + 1], a[j]
    return a
```

**以外掛迴圈旗標提前結束**：

```
def bubble_sort_flag(a):
    n = len(a)
    swapped = True
    while swapped:
        swapped = False
        for j in range(0, n - 1):
            if a[j] > a[j + 1]:
                a[j], a[j + 1] = a[j + 1], a[j]
                swapped = True
    return a
```

**以內建排序為例（仍是命令式介面，只是把迴圈藏進函式庫）**：

```
data = [5, 2, 9, 1]
data.sort()          # 就地排序，回傳 None
```

三段都是命令式：都修改同一份 `a`，都依賴「先檢查再交換」的順序邏輯。差別只在於控制旗標這個可變狀態是「內部迴圈」還是「外層迴圈」——這正是命令式程式複雜度的主要來源：**狀態散布在多個層級的迴圈旗標中**。

## 範例：命令式程式的典型錯誤與它的根源

```
total = 0
for item in items:
    if item.skip:
        continue
    total += item.price * item.quantity
```

這段程式有兩個常見陷阱：

1. **可變狀態的意外共享**：`total` 是全域變數，若另一段程式碼也用它，兩者會互相干擾。修正方式是傳入並回傳。
2. **早期 return 遺漏收尾**：若在迴圈中 `return`，任何需要清理的資源就可能洩漏。修正方式是讓資源生命週期由結構（with 敘述）管理。

這兩類問題都不是語法問題，而是「狀態與副作用」的直接後果——也正是 [函式式] 想消除的對象。

## 前因後果

- **前因**：早期電腦只有紙帶與累加器，程式天然是一串「做一件事」的指令；FORTRAN（[1956年]）的第一版編譯器直接生成機器碼，因此最初的 [高階語言] 就是命令式的。
- **後果**：命令式支撐了作業系統、C 語言與整個企業軟體工業；它的高效率與硬體接近性至今仍是嵌入式與效能關鍵系統的首選。同一原因也帶來技術債與並行難題，促成 [物件導向] 與 [函式式] 的崛起。

## 與相鄰分類的關聯

- 與 [語言典範] 的關係：命令式是歷史最久、影響最廣的典範，是其餘三個典範的對照基準。
- 與 [控制結構] 的關係：分支、迴圈、遞迴、例外處理都是命令式的組成要素。
- 與 [物件導向] 的關係：物件導向並未否定命令式，而是把可變狀態封裝進物件邊界。
- 與 [函式式] 的關係：函數式以純函數與不變性取代順序賦值，兩者是互補而非互斥。

## 容易混淆之處

- **命令式不等於沒有函式**：所有語言都有函式；命令式描述的是程式如何被組織，而非有沒有副程式。
- **命令式不等於低階**：Python 的高階語法寫出的程式仍是命令式。
- **順序執行不等於不可並行**：多執行緒的命令式程式只是把狀態改變變得更難追蹤。
- **「副作用是壞的」過於簡化**：副作用是與外部世界互動的必要機制；問題在於副作用是否被明確框定在邊界內。

## 技術要點

- 命令式的最小要素：變數、賦值、順序執行；再加上分支與迴圈即具完整計算能力。
- 副作用來源：全域狀態、I/O、參數傳遞（傳參考）、例外。
- 命令式程式可用狀態機模型分析：任一時刻的狀態是所有變數值的組合。
- 併行命令式程式的難點在於共享可變狀態的競爭，鎖只是緩解手段之一。
- 現代語言多為多典範：即使提供函式式特性，預設寫法仍是命令式。

## 常見的論爭

- **命令式是否難以維護**：批評者指出其複雜度隨分支路徑數指數成長；支持者反駁說命令式最貼近領域的實際步驟，且有成熟工具與大量既有程式碼。
- **goto 是否可用**：Dijkstra 1968 年的論文主張結構化程式設計；實務上 goto 常被允許，但僅用於例外跳轉等少數情境。
- **物件導向是否只是命令式的延伸**：主張者認為封裝改變了狀態的可見性，屬於典範層級的改變；反對者則認為核心仍是順序賦值。
