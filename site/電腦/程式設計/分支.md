# 分支

> 隸屬：[程式設計] › [控制結構]　·　狀態：初稿

> 對應維基百科：[中文維基百科：條件（編程）](https://zh.wikipedia.org/wiki/%E6%A2%9D%E4%BB%B6_%28%E7%B7%A8%E7%A8%8B%29)　·　[English Wikipedia: Branch (computer science)](https://en.wikipedia.org/wiki/Branch_%28computer_science%29)

分支是**讓程式依條件選擇不同執行路徑的語法機制**，白話說就是「如果……就……否則……」。它把程式從一條直線變成分岔的樹狀流程：條件為真走這條，為假走那條；條件越多，分支樹越寬，程式需要被理解和測試的組合也隨之膨脹。

分支是人類寫程式時最先學會、也最常寫錯的結構。錯誤通常不在語法，而在**分支的完整性**：漏掉一種情況、兩個分支處理同一件事卻給出不一致的結果、條件永遠為真而使後面的程式碼變成死碼（dead code）。這些錯誤多數不會被編譯器抓到，因此分支是測試與審查的主要對象（見 [程式碼審查]）。

## 技術與理論的關聯

- **分支是「選擇」的最小單位**：Böhm–Jacopini 定理（[1966年]）證明，任何可計算函式都可僅由順序、選擇與重複三種結構寫成；分支正是其中的選擇。
- **分支與程式碼審查同源**：分支的可讀性取決於「條件是否涵蓋所有情況、每個情況是否有清楚出口」，這正是結構化程式設計運動（[1968年] [狄克斯特拉] 的〈Go To 語句有害論〉）要解決的問題。
- **布爾代數是分支的語意基礎**：條件運算子遵守德摩根律等恆等式；短路求值（`&&` 遇 false 即停、`||` 遇 true 即停）正是為了配合這種代數性質而定義的。
- **分支與型別系統互相塑造**：列舉型別加窮舉比對（Rust 的 `match`、TypeScript 的窮盡檢查）能把「新增一種情況卻忘記處理」從執行期 bug 變成編譯期錯誤。
- **分支密度影響測試成本**：若一個函式有 $ n $ 個獨立分支，窮舉路徑可達 $ 2^n $ 條；實務上以分岔覆蓋率與基準測試取代窮舉。
- **分支是宣告式語言的隱形元素**：SQL 的 `WHERE`、正則表達式的量詞、樣式表的選擇器，本質都是把分支交給引擎代勞。

## 範例：同一個需求的三種分支寫法

需求：依會員等級給不同折扣。

**if／else 鏈（最常見，也最易失控）**：

```python
def discount(level, amount):
    if level == "gold":
        return amount * 0.8
    elif level == "silver":
        return amount * 0.9
    elif level == "bronze":
        return amount * 0.95
    else:
        return amount
```

問題在於：新增一個等級要同時改函式與呼叫端對「有哪些等級」的假設，且忘寫 `else` 時會默默回傳原價。

**查表式（把分支變成資料）**：

```python
DISCOUNT = {"gold": 0.8, "silver": 0.9, "bronze": 0.95}

def discount(level, amount):
    rate = DISCOUNT.get(level, 1.0)
    return amount * rate
```

分支被「資料」取代，新增等級只需加一筆資料，執行期成本也更低。

**以型別窮舉分支（Rust）**：

```rust
enum Level { Gold, Silver, Bronze }

fn discount(level: &Level, amount: f64) -> f64 {
    match level {
        Level::Gold => amount * 0.8,
        Level::Silver => amount * 0.9,
        Level::Bronze => amount * 0.95,
    }
}

fn main() {
    let lv = Level::Gold;
    println!("{}", discount(&lv, 1000.0));   // 800
}
```

編譯器會檢查所有列舉值是否都被處理：若漏掉 `Level::Bronze`，編譯直接失敗，錯誤被提前到編譯期。

三種寫法的差別是**「分支由誰維護」**：由程式碼維護、由資料維護，或由型別系統替你檢查。第三種最安全，代價是必須先把「有哪些情況」定義成型別。

## 前因後果

- **前因**：組合語言只有條件跳躍指令，分支是以「比較旗標加跳躍」手動拼出來的，程式一大就出現跳躍交錯的 spaghetti code。
- **轉折**：1960 年代末期的結構化程式設計運動把分支提升為一級語法構件，要求「每個分支都有清楚的入口與出口」；高階語言普遍以 `if`／`switch` 承載分支。
- **後果**：C 在 [1972年] 引入 `switch` 敘述，讓多路分支可讀化；1990 年代以後，語言逐漸補上「窮舉檢查」能力（Rust 的 `match`、Scala 的 sealed trait、TypeScript 的窮盡檢查），把分支維護的一部分責任轉移給編譯器。
- **長期影響**：分支的完整性如今是靜態型別語言設計的核心議題之一；同時，分支密集的程式碼被研究反覆指出是缺陷與可讀性問題的主要來源。

## 與相鄰分類的關聯

- 與上位概念 [控制結構] 的關係：分支是控制結構三支柱之一，與 [迴圈]、[遞迴] 共同構成結構化程式的最小集合。
- 與 [型別系統語法] 的關係：窮舉檢查把列舉型別與分支綁定，是「型別即規格」的典型實作。
- 與 [語言典範] 的關係：函式式典範以高階函式取代顯式分支（條件式皆以函式組合），宣告式則把分支下放給引擎。
- 與 [演算法] 的關係：二分搜尋、排序中的比較與交換，都是分支的密集應用；分支成本直接影響演算法複雜度。
- 與 [程式碼審查] 的關係：審查者最常提出的問題之一就是「這個分支是否處理了所有情況」。

## 容易混淆之處

- **分支不等於條件判斷的唯一寫法**：短路求值、`?.` 運算子、樣式比對（pattern matching）都是分支的不同表現。
- **`switch` 不等於 `if` 的完全替代**：C 語言的 `switch` 只適合整數或枚舉型別，且容易忘寫 `break` 造成意外貫穿（fall-through）。
- **分支深度過深不等於錯**：但三層以上的巢狀通常代表該抽出函式或改用策略表；早返回（early return）可減少縮排。
- **用例外取代分支是反模式**：以例外處理「可預期的常態情況」會讓控制流不可預測且效能更差。

## 技術要點

1. **先寫正常路徑**：把最常見的情況寫在最前面，其餘以早返回處理，可大幅降低巢狀深度。
2. **衛語句（guard clause）** 適合驗證輸入：不符合條件就立刻返回，剩下的程式碼不必再縮排。
3. **避免重複條件**：同一條件若出現在多處分支，改用查表或把型別整理成列舉。
4. **短路求值要小心副作用**：`f() && g()` 若 `f()` 有副作用，短路會讓 `g()` 不執行；把副作用移出條件運算子。
5. **邊界值要測試**：`<=` 與 `<`、`>=` 與 `>` 的差異是分支最常見的缺陷來源。
6. **窮舉檢查優於人工提醒**：能用列舉型別與 `match` 表達的分支，就不要用字串比對。

## 常見的論爭

- **分支是否應被消滅**：函式式社群主張以高階函式與代數資料型別取代分支，將條件變成資料流；實務派則指出分支無所不在，與其迴避不如寫好。
- **巢狀深度的上限**：沒有普遍規則，但經驗值是同一函式內分支層數超過三層即應重構。
- **可讀性與安全性的取捨**：查表式最簡潔但失去靜態檢查；窮舉 `match` 最安全但要求型別先行。
