# 例外處理

> 隸屬：[程式設計] › [控制結構]　·　狀態：初稿

> 對應維基百科：[中文維基百科：異常處理](https://zh.wikipedia.org/wiki/%E5%BC%82%E5%B8%B8%E5%A4%84%E7%90%86)　·　[English Wikipedia: Exception handling](https://en.wikipedia.org/wiki/Exception_handling)

例外處理是**語言用來表達「正常流程無法繼續」並把錯誤路徑與主流程分開的機制**，白話說就是「出錯了就跳到專門處理錯誤的地方去，不必在每一步都問『成功了嗎』」。

它的設計目標是**把罕見但必須處理的錯誤從正常路徑中抽離**。沒有例外處理時，傳統作風是每個函式回傳錯誤碼、每個呼叫端都檢查一次，於是主流程被成千上萬行的錯誤檢查淹沒；有了例外處理，正常路徑只剩「做正確的事」，錯誤路徑集中在一處。代價是控制流不再完全顯性——錯誤可能從深處「跳出」數十層呼叫，因此語言都提供 finally 與資源清理機制來補償。

## 技術與理論的關聯

- **例外是非局部跳躍**：拋出點與捕捉點可以相隔數百層呼叫，這使得靜態分析更難，也要求語言提供 finally／上下文管理來保證清理。
- **例外處理把「錯誤碼紀律」升級為語言機制**：C 風格的 `if (err != NULL) return -1;` 檢查，若有一處被遺漏，錯誤會被誤當成正常結果繼續往下走；例外則讓「未處理」在執行期立刻浮現。
- **可預期與不可預期的錯誤應分開**：把「檔案不存在」這類預期情況用例外表達，是最常見的設計錯誤；Rust 以 `Result` 型別把可預期錯誤變成型別的一部分，Java 則用受檢例外（checked exception）強迫呼叫端宣告處理。
- **例外與迴圈、分支互補**：分支處理「預期的不同情況」，例外處理「非預期的失敗」；兩者混用（例如用 try/except 檢查字典鍵是否存在）會讓程式結構劣化。
- **例外安全與資源管理**：C++ 的 RAII（資源取得即初始化）讓物件解構時自動釋放資源，即使拋出例外也不會洩漏；Python 的 `with` 敘述是同一理念的語言化。
- **拋出成本集中在拋出瞬間**：try 區塊本身幾乎零成本，真正的花費在「建立例外物件 + 堆疊解開」，因此熱路徑中以例外當流程控制會明顯變慢。
- **例外是程式碼審查的重點**：捕獲範圍過廣（`except:` 吞掉一切）、捕獲後不處理、錯誤訊息無脈絡，都是審查時最常見的建議（見 [程式碼審查]）。

## 範例：三種語言裡的同一個錯誤處理

需求：讀取設定檔，檔案可能不存在。

**Python（try/except/finally 與上下文管理）**：

```python
def load_config(path):
    try:
        with open(path, encoding="utf-8") as f:
            return f.read()
    except FileNotFoundError:
        return ""              # 可預期的情況：以空字串代替
    except OSError as e:
        raise RuntimeError(f"無法讀取 {path}") from e   # 不可預期的錯誤：包裝後往上拋
    finally:
        print(f"結束處理 {path}")
```

`with` 確保檔案一定被關閉（即使讀取途中出錯），`finally` 保證收尾程式一定執行。

**Java（受檢例外）**：

```java
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

String loadConfig(Path path) throws IOException {
    if (!Files.exists(path)) {
        return "";
    }
    return Files.readString(path);
}
```

方法簽章上的 `throws IOException` 讓「這個方法可能失敗」成為介面契約的一部分；呼叫端被迫決定處理或繼續往上拋。

**Rust（用型別承載可預期錯誤）**：

```rust
use std::fs;

fn load_config(path: &str) -> Result<String, std::io::Error> {
    match fs::read_to_string(path) {
        Ok(content) => Ok(content),
        Err(e) if e.kind() == std::io::ErrorKind::NotFound => Ok(String::new()),
        Err(e) => Err(e),
    }
}
```

Rust 的 `Result` 是普通型別，編譯器會強制呼叫端處理「成功」與「失敗」兩條路徑；無法用型別表達的異常（程式缺陷）才使用 `panic`。

## 前因後果

- **前因**：早期語言多以狀態旗標或全域變數回報錯誤，錯誤資訊容易遺失或被後續操作覆寫，錯誤處理佔滿主流程。
- **轉折**：PL/I 在 [1968年] 前後引入「條件（ON condition）」機制，把錯誤路徑與正常路徑在語法上分開，是例外處理的先驅；C 語言則選擇相反路線，以 `errno` 與回傳碼維持慣例。
- **後果**：Java 在 [1995年] 把例外機制定為語言的核心，並引入受檢例外；Python 以精簡的語法（沒有受檢例外）贏得普及；2000 年代的 .NET 與 Java 社群則讓例外成為企業應用的主流。
- **長期影響**：Rust 在 [2015年] 走向另一端，用 `Result` 與 `?` 運算子讓錯誤路徑在型別層可見、可組合，被許多人視為例外處理的重新設計；同時 C++ 社群提出 `std::expected` 類似的型別化方案，顯示這場爭議並未結束。

## 與相鄰分類的關聯

- 與上位概念 [控制結構] 的關係：例外處理是第四種控制結構，補上了「非局部轉移」這一缺口。
- 與 [分支] 的關係：兩者都是「選路」，但分支處理預期情況、例外處理非預期錯誤；把預期情況做成例外是最常見的誤用。
- 與 [迴圈] 的關係：迴圈中的 `break` 與例外都可中斷流程，但例外能跨出迴圈之外，兩者混用使控制流難以推理。
- 與 [軟體工程] 的關聯：錯誤處理策略是架構層決定，會牽動整個專案的介面設計與團隊慣例，屬於 [品質確保] 的一部分。
- 與 [型別系統語法] 的關係：`Result`、`Option` 一類的型別化錯誤處理，把「錯誤」從執行期的意外提升為型別層的規格。

## 容易混淆之處

- **例外不等於錯誤碼的相反面**：兩者是同一問題的不同解法，選擇取決於團隊紀律與語言支援。
- **捕捉例外不等於處理問題**：捕獲後若不記錄、不修正、不往上拋，等於把錯誤藏起來。
- **finally 不等於一定會執行到底**：行程被強制終止時 finally 不保證執行。
- **`catch(Exception)` 不等於安全**：過度寬鬆的捕捉會把真正的程式缺陷當成正常情況吞掉。
- **例外不該用於常態分支**：以例外代替 `if` 檢查，會讓正常路徑變慢、程式碼意圖變模糊。

## 技術要點

1. **分類錯誤**：先問「這個錯誤可預期嗎？」「呼叫端有辦法處理嗎？」再決定用回傳值、用例外還是用型別。
2. **捕獲具體型別**：只捕捉你能處理的例外類別，廣泛的 `catch` 應留到最外層記錄與轉換。
3. **保留脈絡**：拋出時附上「在哪裡、對哪個資源失敗」；包裝例外時用 `raise ... from ...`（Python）或 `cause`（Java）保留原始原因。
4. **清理靠結構而非靠記憶**：用上下文管理器或 RAII 確保資源釋放，不依賴人記得寫 finally。
5. **不要用例外做迴圈控制**：以例外跳出大量迭代的迴圈，會讓熱路徑付出昂貴代價。
6. **對外穩定、對內豐富**：把細碎低階錯誤在模組邊界包裝成少數幾種高階錯誤，能讓呼叫端的選擇大幅減少。

## 常見的論爭

- **例外 vs 回傳錯誤碼**：Java 與 Python 陣營認為例外能減少噪音；Rust 陣營主張錯誤路徑應顯式可見、可由型別系統強迫處理。兩派各有代表語言與社群。
- **受檢例外是好設計嗎**：贊成者認為介面契約應揭露失敗可能；反對者指出它造成大量 catch 噪音與跨層傳遞負擔，許多 Java 專案實務上普遍繞過它。
- **例外是否讓控制流不可預測**：反對者認為非局部跳躍讓靜態分析與效能預估困難；支持者則指出有 finally 與結構化清理機制後，實務風險可控。
