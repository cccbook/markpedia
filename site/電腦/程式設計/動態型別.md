# 動態型別

> 隸屬：[程式設計]　·　狀態：初稿

> 對應維基百科：[中文維基百科：類型系統](https://zh.wikipedia.org/wiki/%E9%A1%9E%E5%9E%8B%E7%B3%BB%E7%B5%B1)　·　[English Wikipedia: Type system](https://en.wikipedia.org/wiki/Type_system)

動態型別是**在程式執行期間才檢查型別相容性的型別系統**：型別附在值（物件）身上而非變數宣告上，語言允許同一個名字在不同時間綁定到不同型別的值，只要當下的操作合法即可。程式碼因此不必宣告型別，撰寫快速、互動性強，代價是型別錯誤從編譯期被推遲到執行期——可能在使用者按下按鈕的那一刻才爆。

## 技術與理論的關聯

- **值攜帶型別**：物件在執行期知道自己屬於哪個類別，方法查找依執行期型別進行，這就是「late binding」的基礎。
- **對偶性**：靜態型別在編譯期綁定方法對應到「值的宣告型別」，動態型別在執行期綁定到「值的實際型別」；兩者是把同一個多型機制放在生命週期的兩端。
- **漸進型別的中間地帶**：TypeScript 與 Python 的型別提示正是企圖在不改變執行期語意的前提下，把部分檢查前移，證明「檢查時機」是可以漸進調節的。
- **執行期標籤（tag）的代價**：值帶著型別標籤，意味著每次操作都可能需要標籤檢查與分派；這是動態派送成本的主要來源，也是即時編譯技術的著力點。
- **與腳本語言的共生**：腳本語言需要「先跑再說」的開發節奏，型別檢查若強制前置就會拖慢迭代，因此兩者在設計意圖上相互強化。

## 動態型別的主要特徵

- **無需宣告型別**：變數在賦值時綁定當下的型別。
- **多型或子類型（polymorphism）**：同一變數在不同時間可指向不同型別的值（但在特定語言中限定同一「形狀」）。
- **執行期錯誤**：型別不相容的操作在執行到該行時拋出例外，而非編譯時被拒絕。
- **內建反射**：程式可以在執行期查詢型別、屬性、方法，這是執行框架與動態語言的關鍵能力。
- **猴子修補與開放物件**：執行期替物件加上屬性或方法，讓系統能在不重新編譯的情況下擴充。

## 範例：同一段程式在兩種型別系統下的命運

需求：把兩個數值相加。

**動態型別（Python）**：

```
def add(a, b):
    return a + b

print(add(10, 5))       # 15
print(add("a", "b"))    # "ab"：字串也能相加，語意合理
print(add(10, "b"))     # TypeError：執行到這行才爆炸
```

**靜態型別（Rust）**：

```
fn add(a: i64, b: i64) -> i64 {
    a + b
}

fn main() {
    println!("{}", add(10, 5));   // 15
    // println!("{}", add(10, "b"));  // 編譯錯誤：型別不符
}
```

差異不在於「能不能加字串」——在 Rust 中要寫 `String` 的版本必須換一個函式或用泛型；在 Python 中 `add` 一個函式同時服務數字與字串。這種彈性是動態型別的實際價值：**同一段程式碼能適應多種輸入型別，無須重複或泛型化**。

## 範例：錯誤發現時機的實際代價

```
def process(payload):
    total = payload["amount"] * 2     # ← 假設 payload 有 "amount" 鍵
    return total

# 呼叫端傳入沒有 "amount" 鍵的字典
process({"total": 100})
```

- 在 [靜態型別] 語言中，若 `payload` 的型別是明確的結構（例如 `dict[str, int]`），這類「鍵不存在」多半在編譯期或以明確型別（如 `dict` 搭配取值 API 回傳選項）被暴露。
- 在動態型別中，這行會在執行到 `payload["amount"]` 時拋出 `KeyError`；若該程式碼路徑在測試中沒有被執行到，錯誤會一路留到正式環境才出現。

這就是動態型別最典型的工程風險：**錯誤的發現時機與測試覆蓋率綁在一起**。降低風險的常見手段包括：型別提示搭配靜態檢查器、以模式比對取代直接索引、必要時對輸入做執行期驗證。

## 前因後果

- **前因**：[1958年] 的 Lisp 以動態型別起步，讓「程式即資料」的實驗傳統得以延續；1980–1990 年代的網頁腳本語言與快速原型文化，讓動態型別在應用開發中取得主導地位。
- **後果**：動態型別推動了 [人工智慧] 與 [資料科學] 的快速迭代——研究程式多半是短命的、探索性的，重寫成本低比執行效能更重要；同時它也讓執行期型別檢查與反射式框架（如依賴注入容器、ORM、動態代理）成為可行的工程基礎。

## 與相鄰分類的關聯

- 與 [型別系統語法] 的關係：動態型別是檢查時機上的另一半，與靜態型別、推論、漸進型別構成完整地圖。
- 與 [腳本語言] 的關係：兩者設計意圖一致——快速取得結果、容忍探索。
- 與 [物件導向] 的關係：執行期多型是動態派送語言（如 JavaScript 原型鏈、Python 的 duck typing）的基礎。
- 與 [軟體工程] 的關係：動態型別把驗證責任推向執行期與測試，因此測試策略必須相應調整。

## 容易混淆之處

- **動態型別不等於弱型別**：Python 是動態但強的——它不會把字串悄悄轉成數字。
- **動態型別不等於慢**：即時編譯能消除大部分動態派送成本；效能差異主要來自實作品質與資料結構，而非動靜本身。
- **無型別宣告不等於沒有型別**：每個值在執行期都有型別，只是檢查時機不同。
- **duck typing 不等於不驗證**：Python 雖無靜態檢查，仍可用型別提示與執行期檢查補足。

## 技術要點

- 執行期標籤檢查是動態派送的主要成本來源。
- 隱藏屬性與方法（name mangling）是物件導向語言維持封裝時常用的手段。
- 猴子修補讓執行期擴充成為可能，也讓「程式碼在什麼時候被載入」變得難以追蹤。
- 漸進型別與型別提示是動態與靜態之間的工程折衷，也是目前最重要的發展方向。
- 反射與執行期型別資訊讓框架能自動完成註冊、序列化與相依注入。

## 常見的論爭

- **執行期錯誤是否不可接受**：批評者認為把錯誤推遲到正式環境是重大風險；支持者則指出實際專案的錯誤多數是領域邏輯錯誤，型別檢查本來也擋不住。
- **動態型別是否妨礙大型專案**：以型別提示與測試補強後，動態語言在大型 codebase 的可用性已被廣泛驗證。
- **漸進型別能否終結爭論**：若能讓「檢查時機」變成可調參數，兩造都會受益；實務上這正是 TypeScript 與 Python 生態的方向。
