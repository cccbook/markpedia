# 測試驅動

> 隸屬：[程式設計] › [開發方法]　·　狀態：初稿

> 對應維基百科：[中文維基百科：測試驅動開發](https://zh.wikipedia.org/wiki/%E6%B5%8B%E8%AF%95%E9%A9%B1%E5%8A%A8%E5%BC%80%E5%8F%91)　·　[English Wikipedia: Test-driven development](https://en.wikipedia.org/wiki/Test-driven_development)

測試驅動開發（Test-Driven Development，TDD）是**先寫會失敗的測試、再寫剛好讓它通過的程式碼、最後重構的開發紀律**。白話說就是「先寫好考題與標準答案的判準，再寫作答過程」，程式碼必須通過事先寫下的檢驗才能存在。

它的核心不是「多寫測試」，而是**用測試來驅動設計**：因為測試必須先於實作存在，程式士被迫先想清楚介面該長什麼樣、要回傳什麼行為，而不是先寫出一堆程式再補測試。整個循環被稱為「紅—綠—重構」（Red–Green–Refactor），每一輪循環通常以分鐘為單位。

## 技術與理論的關聯

- **TDD 是極限編程的實踐之一**：1990 年代末，Kent Beck 推動的極限編程（XP）把測試先行、持續整合、結對程式設計與重構列為核心紀律；[敏捷] 宣言在 [2001年] 為這些做法提供了共同名稱（見 [敏捷]）。
- **TDD 與重構是互補的兩半**：綠燈狀態若不重構，程式會隨每輪迭代逐步劣化；「紅—綠—重構」中，重構步驟不可省略，否則 TDD 只是「測試先行」。
- **測試是可執行的規格**：傳統需求文件會與程式碼脫節，測試則在每次建置時被重新驗證，因此是最不會腐化的規格形式（與 [品質確保] 的觀點相合）。
- **TDD 迫使介面先行的設計**：寫不出測試往往代表需求未想清楚；測試同時扮演了「可呼叫的規格範例」（executable specification）。
- **失敗的測試是安全的靠背護欄**：重構時若破壞行為，測試立刻失敗，使「在不破壞既有行為的前提下改寫程式」成為可行的工作方式。
- **測試金字塔決定 TDD 的成本**：單元測試多而快、端到端測試少而慢；若 TDD 寫的全是端到端測試，每輪循環會慢到無法執行，紀律自然瓦解。
- **測試即設計文件，但會腐化**：當測試只是為了通過而寫，測試會綁死實作細節而阻礙重構；「測試行為而非實作」是此時的核心原則。

## 範例：一個折扣功能的完整「紅—綠—重構」

需求：購物車滿 1000 元時打 95 折。

**第一步（紅）：先寫會失敗的測試**

```python
from cart import Cart

def test_total_applies_discount_over_threshold():
    cart = Cart()
    cart.add("書", price=600)
    cart.add("筆", price=500)
    assert cart.total() == 1050      # 1100 打 95 折
```

此時 `Cart` 尚不存在，測試以匯入錯誤失敗——這就是「紅」：確認測試確實會察覺缺少的功能。

**第二步（綠）：寫剛好能通過的程式碼**

```python
class Cart:
    def __init__(self):
        self.items = []

    def add(self, name, price):
        self.items.append({"name": name, "price": price})

    def total(self):
        raw = sum(i["price"] for i in self.items)
        return round(raw * 0.95) if raw >= 1000 else raw
```

不寫多餘的介面、不提前最佳化，只求測試轉綠。

**第三步（重構）：在保護下整理結構**

```python
class Cart:
    def __init__(self, items=None):
        self.items = list(items or [])

    def add(self, name, price):
        self.items.append({"name": name, "price": price})

    def raw_total(self):
        return sum(i["price"] for i in self.items)

    def total(self):
        raw = self.raw_total()
        return round(raw * DISCOUNT_RATE) if raw >= DISCOUNT_THRESHOLD else raw
```

重構後所有測試仍為綠燈，行為未變但結構更清楚——這時才適合提交（見 [版本控制]），並發起審查（見 [程式碼審查]）。

**第四步：補上邊界案例**

```python
def test_total_without_discount_below_threshold():
    cart = Cart()
    cart.add("筆", price=500)
    assert cart.total() == 500
```

邊界測試是 TDD 特別擅長的部分：因為測試先寫，撰寫測試的人會自然去問「那如果剛好 1000 元呢？」

## 前因後果

- **前因**：1970 至 1990 年代的主流做法是「先寫程式、後寫測試」（或根本不寫）。缺陷往往在整合測試甚至上線後才浮現，修復成本隨時間指數上升。
- **轉折**：1990 年代的 XP 將測試先行制度化；[1998年] 的 JUnit 讓這套紀律在 Java 生態中有了低摩擦的執行工具，同一時期的 xUnit 家族把單元測試推向主流。
- **推廣**：[2002年] 出版的《Test-Driven Development: By Example》把循環與「三條規則」整理成可教學的系統，之後敏捷與 DevOps 團隊普遍以持續整合承載這套紀律。
- **後果**：TDD 改變了程式碼的形狀——模組邊界更清楚、函式更小、依賴更少，因為這些特質是「容易測試」的同義詞。它也把缺陷發現時機從「交付前」移到「寫下當下」。
- **長期影響**：當前大型語言與框架幾乎都以測試作為一等公民；自動化測試的累積也成為 AI 輔助程式設計的重要訓練與評測資料來源。

## 與相鄰分類的關聯

- 與上位概念 [開發方法] 的關係：TDD 是四件標準配備中的「規格產生器」，其產物同時是 [版本控制] 的提交內容與 [程式碼審查] 的審查對象。
- 與 [軟體工程] 的關聯：TDD 屬於工程方法層，與流程管理層的 [敏捷] 互補——敏捷決定節奏，TDD 決定程式碼品質的產生方式。
- 與 [品質確保] 的關聯：TDD 是品質保證中最靠近工程師的一環，強調「預防」而非「偵測」。
- 與 [迴圈]、[分支] 的關係：測試案例的設計本質上就是枚舉控制結構的各種路徑；分支覆蓋率的分岔覆蓋（branch coverage）概念直接來自 [分支] 的組合數。
- 與 [演算法] 的關係：演算法的正確性驗證常以性質測試（property-based testing）與邊界測試最有效，TDD 提供其落地流程。

## 容易混淆之處

- **TDD 不等於提高測試覆蓋率**：覆蓋率高只代表程式碼被執行過，不代表行為被驗證；錯誤的測試可以有 100% 覆蓋率。
- **TDD 不等於先寫測試就緒**：若測試只是遷就既有實作，TDD 的設計收益完全消失。
- **TDD 不等於所有程式都適合**：探索性原型、資料探勘與一次性腳本，強行套用反而拖慢節奏。
- **「先寫測試」不等於「測試先行團隊」**：若測試撰寫者與實作者是同一個人且無法獨立思考，測試往往只是實作的鏡像。

## 技術要點

1. **三條規則**：沒有失敗的測試就不寫實作；不寫超過讓測試通過所需的實作；不寫超過驗證當前需求所需的測試。
2. **每輪循環要短**：一輪應在數分鐘內完成，否則回饋延遲，紀律會崩壞。
3. **重構在綠燈下進行**：任何時候都保持測試全綠，是重構安全的唯一前提。
4. **測試命名即規格**：測試名稱應描述行為（「滿額時套用九五折」），而不是描述實作（「呼叫 apply_discount」）。
5. **避免測試相依**：測試之間不應有執行順序依賴，否則失敗難以診斷。
6. **隔離外部世界**：對資料庫、網路與時間依賴以替身（test double）取代，才能讓測試快且可重現。
7. **舊程式也要測**：先以「特徵測試」記錄既有行為，再在其保護下重構，是進入 TDD 的務實起點。

## 常見的論爭

- **TDD 是否總是划算**：支持者視其為設計工具而非測試工具；反對者以探索性工作與需求變動頻繁的專案為例，認為先寫測試會寫出錯誤方向的規格。
- **覆蓋率作為品質指標**：支持覆蓋率者視其為最低防線；批評者指出它鼓勵無意義的測試，且高覆蓋率與低缺陷密度並無必然關聯。
- **AI 輔助程式設計時代的 TDD**：自動生成程式使「寫測試」的成本大幅下降，爭論焦點轉為「由 AI 生成的測試是否真的能驗證意圖」，這也是當前審查與驗證的核心難題。
