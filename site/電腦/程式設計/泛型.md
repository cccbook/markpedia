# 泛型

> 隸屬：[程式設計] › [型別系統語法]　·　狀態：初稿

> 對應維基百科：[中文維基百科：泛型編程](https://zh.wikipedia.org/wiki/%E6%B3%9B%E5%9E%8B%E7%BC%96%E7%A8%8B)　·　[English Wikipedia: Generic](https://en.wikipedia.org/wiki/Generic)

泛型是**把「型別」本身當成參數來抽象的程式設計手法**：同一段「容器」或「演算法」的程式碼，只寫一次，就能安全地用於整數、字串或任何其他型別。沒有泛型時，程序設計師要嘛為每種元素型別各寫一份程式碼，要嘛把元素型別降級成萬用的 `Object`（物件）而失去靜態檢查。

泛型的白話解釋是：**「一套模板，任意填料」**。抽屜清單、堆疊、排序比較器都屬於這類：抽屜的形狀不變，裡面裝什麼可以換。泛型把這個直覺變成型別系統中的第一級抽象，並讓編譯器負責保證「裝進去的和取出來的型別一致」。

## 技術與理論的關聯

- **泛型把多型提升到型別層**：物件導向的多型（同一介面、不同實作）處理的是「同一操作、不同物件」；泛型處理的是「同一演算法、不同元素型別」，兩者是不同層次的多型。
- **泛型需要推論配合**：若沒有 [推論]，呼叫泛型容器時必須顯式指定型別參數（例如 `List<String>`），冗長且容易與推論的型別衝突；現代語言多採兩者並存。
- **兩條實作路線**：編譯期單態化（C++ 模板、Rust 的泛型與 trait）為每個型別各產生一份機器碼，執行期零成本但編譯較慢、二進位較大；執行期抹除（Java 早期與 Scala 某些用法）共用一份碼並以動態派送處理代價，則失去部分靜態資訊。
- **泛型與高階型別的關係**：以 Curry–Howard 對應觀之，泛型函式等價於接受型別參數的高階函式，Hindley–Milner 的多型推論正是其理論基礎。
- **泛型是演算法重用的前提**：沒有泛型，排序、搜尋、容器這類與元素型別無關的演算法，就無法在保持型別安全的前提下被重複使用（見 [演算法]）。
- **型別參數是契約也是約束**：泛型宣告了「這段程式對 T 的要求」（例如 `T : Comparable`），這條約束會沿著呼叫鏈傳播，形成隱藏的耦合。

## 範例：同一個排序在不同泛型設計下的樣貌

需求：把一個數字清單遞增排序後輸出。

**Java（型別抹除）**：

```java
import java.util.Collections;
import java.util.List;

List<Integer> nums = List.of(3, 1, 2);
Collections.sort(nums);
System.out.println(nums);   // [1, 2, 3]
```

編譯後 `List` 只剩原始型別 `List`，元素型別資訊在執行期被抹除；字串清單與數字清單共用同一份 `sort` 程式碼。

**Rust（單態化）**：

```rust
fn largest<T: PartialOrd>(items: &[T]) -> &T {
    let mut best = &items[0];
    for item in items {
        if item > best {
            best = item;
        }
    }
    best
}

let nums = vec![3, 1, 2];
let mut n = nums.clone();
n.sort();
println!("{:?} {}", n, largest(&nums));   // [1, 2, 3] 3
```

`T: PartialOrd` 就是泛型的「契約」：呼叫端要能比較，就必須滿足這個界線；編譯器會為 `i32` 與 `f64` 各產生一份版本。

**C++（模板）**：

```cpp
#include <algorithm>
#include <iostream>
#include <vector>

int main() {
    std::vector<int> nums{3, 1, 2};
    std::sort(nums.begin(), nums.end());
    for (int x : nums) std::cout << x << " ";   // 1 2 3
}
```

模板在編譯期以文字替換展開，錯誤訊息往往深埋在展開後的模板實例裡——這是 C++ 模板最常見的教學負擔。

**TypeScript（泛型加推論）**：

```typescript
function first<T>(items: T[]): T | undefined {
  return items[0];
}
const n = first([3, 1, 2]);        // n: number | undefined
const s = first(["a", "b"]);        // s: string | undefined
```

推論讓呼叫端不必寫 `first<number>(...)`，這正是泛型實務上可用的關鍵。

## 前因後果

- **前因**：早期語言缺乏泛型，同一容器要靠「複製貼上後改型別」或「轉成萬用物件」兩種笨拙方式應對不同資料型別；程式庫因此快速膨脹，型別錯誤也無處可查。
- **轉折**：CLU 語言在 1970 年代中期的實作中發展出今日泛型的核心機制；Ada 在 [1983年] 把它帶入標準語言；C++ 於 [1986年] 以模板形式推廣。
- **後果**：Java 在 [1995年] 將泛型納入語言（採用型別抹除），使 Java 標準函式庫得以泛化（`Collections`、`Comparable`），並催生 Guava 等補丁函式庫；C# 與 Scala 的泛型則提供不同的取捨。
- **長期影響**：泛型讓「泛型容器＋泛型演算法」的組合成為主流，使 C++ 標準模板庫（STL）在 1990 年代成為決定性影響力，也讓 Rust 的 trait 系統、TypeScript 的泛型成為後來者的參照。
- **教學代價**：模板的錯誤訊息過於冗長曾長期是 C++ 學習者最大障礙，Rust 的 trait 邊界（trait bound）即是針對此問題重新設計的介面。

## 與相鄰分類的關聯

- 與 [推論] 的關係：推論讓泛型呼叫端不必指定型別參數，是泛型在現代語言中普及的技術前提。
- 與上位概念 [型別系統語法] 的關係：泛型是靜態型別系統中最能重用程式碼的機制。
- 與 [控制結構] 的關係：泛型容器常以迭代器（iterator）形式提供遍歷，迭代器的 `next()` 回傳型別使迴圈得以泛用；`for` 迴圈在許多語言中即是泛型介面的糖衣。
- 與 [演算法] 的關係：演算法一旦泛型化，就能從教學範例升級為可重用的標準庫元件。
- 與 [數學] 的關係：泛型對應多型 lambda 演算，Hindley–Milner 系統的型別推論即為其實作。

## 容易混淆之處

- **泛型不等於巨集（macro）**：C++ 模板雖以文字替換展開，語意上是型別層的抽象，與巨集的本質不同。
- **泛型不等於「只是把 Object 換個名字」**：若編譯器無法在呼叫點檢查型別，那只是把型別檢查延後或取消，安全性反而下降。
- **泛型不等於泛型方法**：部分語言支援在單一方法上宣告型別參數，其可視範圍小於類別層級的泛型，兩者用途不同。
- **泛型不等於模板元程式**：模板可以刻意被用來做運算期運算，產生高度抽象但難以維護的程式碼；這是濫用而非泛型設計的常態。

## 技術要點

1. **契約要明確**：型別參數的界線（bound、trait、constraint）應精確表達需求，「什麼都能塞」的泛型等於沒有契約。
2. **單態化與抹除的取捨**：前者執行期零成本、後者二進位小但失去型別資訊；Rust 與 C++ 走前者，Java 的部分情境走後者，Scala 則提供兩者。
3. **泛型與推論要一起設計**：好的泛型語言必須讓呼叫端自然地不必指定參數。
4. **集合工廠與型別實例的差異**：泛型容器（如 `List<T>`）與型別實例（`IntList`）在 Java 等語言中是兩套東西，混淆會導致序列化與反射時的型別遺失。
5. **錯誤訊息是使用體驗的核心**：型別參數越深，錯誤訊息越需精心設計（Rust 的「協助訊息」即為此而生）。
6. **泛型不可跨運算期邊界**：經過序列化、反射或 FFI 後，泛型型別資訊通常只剩外層容器，元素型別必須另外攜帶。

## 常見的論爭

- **泛型是否值得其複雜度**：反對者以 C++ 模板的學習與除錯成本為據；支持者指出 STL 級別的重用收益無法以其他方式達成。
- **抹除是否安全**：Java 社群視抹除為務實取捨，Rust 社群則主張靜態檢查不應有洞，因而發展出零成本的 trait 系統。
- **泛型是否讓語言太複雜**：提議者強調泛型是多數實務型別需求（容器、演算法、回傳型別）最少重複的解法，複雜度主要來自組合方式而非泛型本身。
