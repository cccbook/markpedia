# 遞迴

> 隸屬：[程式設計] › [控制結構]　·　狀態：初稿

> 對應維基百科：[中文維基百科：遞歸](https://zh.wikipedia.org/wiki/%E9%80%92%E5%BD%92)　·　[English Wikipedia: Recursion (computer science)](https://en.wikipedia.org/wiki/Recursion_%28computer_science%29)

遞迴是**函式（或程序）呼叫自己來解決規模更小的子問題的技巧**，白話說就是「把大問題交給同一個方法處理小一號的問題，直到小到可以直接回答」。遞迴的兩要素是**基底條件**（何時停止）與**遞迴步驟**（如何把問題縮小）；兩者缺一，程式就會無限遞迴下去。

遞迴的價值在於**用最接近問題定義的寫法表達演算法**：數學上以遞迴定義的東西（階乘、費波那契數、樹的遍歷、漢諾塔），用遞迴寫幾乎是逐字翻譯，證明也容易得多。代價則是執行期成本——每次呼叫都在堆疊上多佔一層，深遞迴可能直接讓程式崩潰。

## 技術與理論的關聯

- **遞迴與數學定義同形**：遞迴式（recursive definition）由基底與遞迴式兩部分構成，程式中的遞迴函式與之逐項對應，因此「程式正確」可以直接用歸納法論證。
- **遞迴的計算能力來自自身**：可計算性不要求無限記憶體，但要求能把中間結果存下來——遞迴以呼叫堆疊「借用」語言的記憶體，這正是它能表達無限計算的原因。
- **Rosser 計數性反例（[1936年]）**：存在可計算但不可終止的遞迴函式，這說明「能描述」不等於「會停止」，基底條件因此不是風格而是必要條件。
- **尾遞迴與堆疊消去**：若遞迴呼叫是函式的最後一個動作，編譯器可把呼叫堆疊換成迴圈，遞迴即變成迭代；Scheme 等語言在語言層面強制保證尾呼叫最佳化。
- **遞迴與迴圈在理論上等價**：任何遞迴皆可改寫成以明確堆疊驅動的迴圈（見 [迴圈]）；反之，模擬語言機器的迴圈要靠遞迴。差別在於哪一種寫法更清楚。
- **分治法是遞迴的工程化**：二分搜尋、合併排序、快速排序都以「分成兩半再分別處理」為核心，是遞迴在演算法中的標準形態（見 [演算法]）。
- **記憶化是遞迴的加速器**：把已算過的子問題結果快取起來，可將某些遞迴的時間複雜度從指數級降到多項式級，代價是額外空間與實作複雜度。

## 範例：漢諾塔與費波那契的遞迴寫法

**漢諾塔（遞迴的經典示範）**：

需求：把 $ n $ 個圓盤由 A 柱全部移到 C 柱，每次只移一個，且大盤不得壓在小盤上。

```python
def hanoi(n, source, target, spare):
    if n == 1:                       # 基底條件
        print(f"把圓盤從 {source} 移到 {target}")
        return
    hanoi(n - 1, source, spare, target)    # 先把上面 n-1 個移到備用柱
    print(f"把圓盤從 {source} 移到 {target}")
    hanoi(n - 1, spare, target, source)    # 再把備用柱上的 n-1 個移到目標柱

hanoi(3, "A", "C", "B")
```

輸出共 7 行，對應最少的移動次數 $ 2^n - 1 $ ： $ n = 3 $ 時 $ 2^3 - 1 = 7 $ 。遞迴的三行結構就是「先移上面、先移下面、再移上面」，與數學課本上的標準解法完全一致。

**費波那契（遞迴 vs 迴圈 vs 記憶化）**：

```python
def fib_recursive(n):
    if n < 2:
        return n
    return fib_recursive(n - 1) + fib_recursive(n - 2)     # 指數級：n=30 要算約 160 萬次

def fib_loop(n):
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a                                                  # 線性：n=30 只需 30 次

def fib_memo(n, memo={}):
    if n < 2:
        return n
    if n not in memo:
        memo[n] = fib_memo(n - 1, memo) + fib_memo(n - 2, memo)
    return memo[n]                                            # 每個子問題只算一次
```

同一個定義，三種實作的呼叫次數差距是數量級的：遞迴版本因為重複計算相同的子問題， $ T(n) = 2T(n-1) + O(1) $ 導出 $ T(n) = O(2^n) $ ；迴圈版本是 $ O(n) $ ；記憶化版本則是 $ O(n) $ 但保留了遞迴的可讀性。

## 前因後果

- **前因**：早期組合語言沒有呼叫堆疊，遞迴必須手動用堆疊區塊與跳轉指令模擬，撰寫痛苦且易錯，因此實務上以迴圈為主。
- **轉折**：1950 年代起，Lisp 把遞迴當成一等公民；FORTRAN 等語言雖保留遞迴，卻因實作效率考量不受鼓勵。學術界則長期以遞迴作為演算法表述的標準語言。
- **後果**：1970 年代的結構化程式設計運動雖以迴圈為主，卻也正式承認「遞迴與迭代等價」，使兩種風格在教學上並列；物件導向語言的虛擬方法呼叫本質上就是動態派送版的遞迴。
- **長期影響**：隨著函式式語言復興，尾遞迴最佳化重新受到重視；如今多數現代語言（Rust、Scala、OCaml、F#）都提供尾遞迴最佳化或編譯期警告，使遞迴從「效能不佳」變成「看情況使用」。

## 與相鄰分類的關聯

- 與上位概念 [控制結構] 的關係：遞迴是控制結構中「以呼叫堆疊換取記憶體」的特殊形態。
- 與 [迴圈] 的關係：兩者可互相轉換；遞迴適合表達樹狀與遞迴定義的問題，迴圈適合避免堆疊溢位與提升效能。
- 與 [分支] 的關係：基底條件就是一個分支，遞迴函式的可讀性取決於基底條件寫得是否清楚。
- 與 [演算法] 的關係：分治法、樹與圖的遍歷、動態規劃的遞迴版本都建基於遞迴之上（見 [演算法]）。
- 與 [數學] 的關係：遞迴式、歸納法、數學歸納法原理是同一件事的三種表達。

## 容易混淆之處

- **遞迴不等於無條件遞迴**：遞迴必須有基底條件與嚴格的「縮小」，否則就是無限遞迴。
- **互遞迴不是迴圈**：兩個函式互相呼叫（ mutual recursion ）是合法的遞迴形式，但除語言層設定外，遞迴深度同樣受限。
- **深遞迴不等於高階**：用遞迴包裝簡單的迴圈只是增加呼叫成本，沒有抽象收益。
- **尾遞迴最佳化不是普遍保證**：只有明確支援最佳化的語言與編譯器才會受益，其餘語言的尾遞迴仍佔用堆疊。

## 技術要點

1. **先寫基底條件**：它決定函式何時停止，也是函式正確性的第一道證明。
2. **確認參數嚴格逼近基底**：每次呼叫都應朝基底前進一步，否則遞迴不收斂。
3. **記憶化處理重複子問題**：當遞迴樹中出現大量重複節點時，快取是最直接的加速手段。
4. **留意堆疊深度**：Python 預設遞迴深度約一千層，深層資料（如目錄樹）應改用明確堆疊的迴圈版本。
5. **尾遞迴值得優先寫**：若函式最後一個動作就是遞迴呼叫，改寫成尾遞迴可讓支援最佳化的語言把它變成迴圈。
6. **遞迴的可讀性有其代價**：即使可轉為迴圈，遞迴版本往往更貼近問題定義，可用註解說明其意圖。

## 常見的論爭

- **遞迴應不應該被教**：支持者認為它是思考遞迴式問題的思維工具；反對者以工業語言多無尾呼叫最佳化、且除錯困難為由，主張實務應以迴圈為預設。
- **深遞迴是否可用**：在作業系統核心與垃圾收集器中，深遞迴曾被大量使用，也因此造成過嚴重的堆疊溢位事故；今天的共識是核心路徑應避免深遞迴。
- **除錯遞迴是否比迴圈困難**：迴圈的執行軌跡是線性的，遞迴則是一棵樹，需要更強的視覺化工具與紀律。
