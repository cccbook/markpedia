# 迴圈

> 隸屬：[程式設計] › [控制結構]　·　狀態：初稿

> 對應維基百科：[中文維基百科：迴圈](https://zh.wikipedia.org/wiki/%E8%BF%B4%E5%9C%88)　·　[English Wikipedia: Iteration](https://en.wikipedia.org/wiki/Iteration)

迴圈是**讓同一段程式重複執行、直到條件不再成立的語法機制**，白話說就是「再做一次，直到做完」。它是程式從「一次性」走向「處理任意量資料」的關鍵：沒有迴圈，程式只能處理固定數量的項目。

迴圈的三個要素是**初始化、繼續條件、推進**（把狀態往終點移動）。三要素缺一不可：漏掉推進就是死迴圈，漏掉初始化或條件則可能在第一輪就出錯。迴圈也是程式裡最常出現「差一錯誤」（off-by-one）的地方——迴圈邊界用 `>` 還是 `>=`、索引從 0 還是 1 開始，往往就是缺陷的所在。

## 技術與理論的關聯

- **迴圈是「重複」結構的最小單位**：Böhm–Jacopini 定理指出，任何可計算函式都能只由順序、選擇與重複三種結構寫出；迴圈即其中的重複。
- **迴圈不變量是正確性的核心武器**：證明迴圈正確的標準做法，是找出一個在每次迭代前後都成立的性質（不變量）。這個技巧同時也是除錯利器——把不變量寫成斷言，錯誤就會在第一個被破壞的迭代點現形。
- **迴圈與分支互為表裡**：`while` 迴圈在機器碼層次就是「條件跳躍 + 無條件跳回」的組合，因此 [分支] 的邊界錯誤必然同時是迴圈邊界錯誤。
- **迴圈與遞迴可互相轉換**：任何遞迴都能改寫成以明確堆疊驅動的迴圈（見 [遞迴]），尾遞迴則是兩者完全等價的情況。
- **迴圈是演算法複雜度的度量單位**： $ O(n) $ 、 $ O(n \log n) $ 這類複雜度描述的正是「輸入量變大時，迴圈執行幾次」；巢狀迴圈的深度直接決定了演算法的複雜度階（見 [演算法]）。
- **迭代器把迴圈的通用性抽象掉**：`for` 迴圈在多數現代語言中其實是「取一個元素」的介面呼叫，讓遍歷容器不必知道其內部結構。
- **迴圈是資源洩漏的高危區**：忘記關閉檔案、連線與鎖，常是在迴圈中累積資源不足而失敗。

## 範例：同一個「求總和」的三種迴圈寫法

需求：把清單中所有數字加總。

**while 迴圈（最接近機器模型）**：

```python
nums = [3, 1, 4, 1, 5]
i = 0
total = 0
while i < len(nums):
    total = total + nums[i]
    i = i + 1
print(total)          # 14
```

三要素一目了然：初始化 `i = 0`、條件 `i < len(nums)`、推進 `i = i + 1`。缺任何一項，迴圈都不會正常結束。

**for 迴圈（把三要素綁在語法裡）**：

```python
nums = [3, 1, 4, 1, 5]
total = 0
for n in nums:
    total = total + n
print(total)          # 14
```

`for` 迴圈把「迭代」封裝成語言機制，讓程式士不必手動管理索引，因此大幅減少了差一錯誤——但索引型迴圈仍存在，`for i in range(len(nums))` 一旦寫成 `range(len(nums) + 1)` 就會越界。

**以函式表達「對清單做什麼」**：

```python
nums = [3, 1, 4, 1, 5]
print(sum(nums))      # 14
```

標準函式庫把常見迴圈收進更高階的抽象。從 while 到 sum 的距離，正是程式抽象層一路墊高的縮影。

## 前因後果

- **前因**：早期機器只有累加器與紙帶，重複必須靠跳躍指令手動安排，迴圈是以「位址計數器 + 跳回」拼湊出來的，因此充滿手寫錯誤。
- **轉折**：FORTRAN 在 1950 年代引入 `DO` 迴圈，把計數器與邊界綁定為語法；1960 年代的結構化程式設計運動（[1968年] [狄克斯特拉] 的〈Go To 語句有害論〉）則確立了「迴圈須有單一出口」的紀律。
- **後果**：迴圈成為高階語言的基本積木，伴隨而來的是抽象層的分化——計數迴圈、條件迴圈、集合迴圈各自演化出不同語法；許多現代語言的 `for` 語法糖同時支援多種迭代協議。
- **持續影響**：隨著多核心與運算加速器普及，迴圈也成為平行程式設計的基本單位——資料切分（parallel loop）讓同一段迴圈同時在多個執行緒執行，資料競爭因而成為新的缺陷類別。

## 與相鄰分類的關聯

- 與上位概念 [控制結構] 的關係：迴圈是控制結構三支柱之一，與 [分支] 共同構成順序程式的骨架。
- 與 [遞迴] 的關係：兩者是同一件事的兩種寫法；遞迴在表達樹狀結構時更自然，迴圈在避免堆疊溢位與提升效能時更安全。
- 與 [演算法] 的關係：排序、搜尋、圖表遍歷的核心都是迴圈；迴圈次數即演算法複雜度。
- 與 [語言典範] 的關係：函式式的 `map`、`filter` 是「不寫出來的迴圈」，宣告式則由查詢引擎代勞遍歷。
- 與 [程式碼審查] 的關聯：審查時最常被追問的就是迴圈邊界與提前結束條件。

## 容易混淆之處

- **`for` 與 `while` 的差異在首輪**：`do-while` 保證至少執行一次，`while` 可能一次都不執行，兩者互換時常藏著邏輯錯誤。
- **迭代器不是索引**：在修改清單長度的迴圈中，索引式迴圈可能越界，迭代器式迴圈則可能漏掉元素或拋出例外。
- **迴圈不是所有重複的最好形式**：能用標準函式庫的高階抽象取代時，抽象往往比手寫迴圈更可靠。
- **尾遞迴不等於迴圈**：尾遞迴在沒有尾呼叫最佳化的語言中仍會耗盡堆疊。

## 技術要點

1. **先寫不變量**：動手前先說出「每輪結束時什麼必須為真」，這一句話往往直接決定迴圈的寫法。
2. **邊界統一**：整個程式碼庫用同一種索引慣例（0 起算或 1 起算），並在必要時寫成 `for i in range(n)` 這類不易出錯的形式。
3. **避免手動推進**：`i = i + 1` 容易漏寫或寫錯位置，用語言提供的推進語句（`i++`、`i += 1`、迴圈變數）更安全。
4. **巢狀迴圈要計成本**：兩層 $ n $ 的迴圈是 $ O(n^2) $ ，三層就是 $ O(n^3) $ ；大資料量下必須重新設計演算法。
5. **迴圈展開是效能手段**：編譯器常把小型迴圈展開以減少跳轉開銷，但程式碼可讀性會下降，因此多交給編譯器處理。
6. **離開迴圈的路徑要明確**：用 `break`、`return` 或 `continue` 離開時，確認它們不會讓某個狀態更新被跳過。

## 常見的論爭

- **迴圈還是不是好程式**：現代實務大量使用高階組合子取代迴圈；但可讀性上，簡單的 for 迴圈通常比三層函式嵌套更容易讀懂。
- **goto 迴圈是否可用**：形式上是違反結構化紀律，實務上在部分機器碼層與特殊控制需求中仍有其位置，Linux 核心即為例。
- **微優化 vs 可維護**：手動迴圈展開與手動迴圈合併有時能提升效能，但多數情況下應先信任編譯器。
