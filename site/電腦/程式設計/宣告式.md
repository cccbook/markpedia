# 宣告式

> 隸屬：[程式設計]　·　狀態：初稿

> 對應維基百科：[中文維基百科：宣告式編程](https://zh.wikipedia.org/wiki/%E5%AE%A3%E5%91%8A%E5%BC%8F%E7%B7%A8%E7%A8%8B)　·　[English Wikipedia: Declarative programming](https://en.wikipedia.org/wiki/Declarative_programming)

宣告式是**描述「結果或關係是什麼」，而不描述「一步步怎麼得到」的程式設計典範**：程式碼陳述的是問題的性質或目標的狀態，具體的執行策略交給引擎——資料庫的查詢最佳化器、版面排版引擎、規則推斷引擎或編譯器。程式碼因此從「程序」變成「對問題的描述」。

## 技術與理論的關聯

- **宣告式的理論根基是邏輯與代數**：Horn 邏輯與關聯式資料庫給出宣告式查詢的完整基礎；正規表示式則是描述字串語言的宣告式 formalism。
- **求值順序與否證（naïve evaluation）**：宣告式語言的實作難題是「宣告的順序不必然是執行的順序」，Prolog 的回溯求解與資料庫的查詢最佳化都是此一難題的解答。
- **最佳化器是宣告式的另一半**：宣告式把「怎麼算」的決策權交給引擎，因此引擎必須擁有足夠的資訊與足夠的搜索能力，才能把程式碼翻譯成有效率的執行計畫。
- **與函式式的關係**：宣告式常以函式的組合來表達（串接運算子），因此 [函式式] 的不可變性與高階函式是宣告式的自然實作風格。
- **邏輯式語言的極致**：Prolog 讓「宣告事實與規則、由引擎推論」成為可能，是宣告式最徹底的形態。

## 宣告式的常見形態

- **查詢語言**：SQL 陳述「要哪些資料與條件」，由最佳化器決定掃描、索引與join順序。
- **設定與組態**：宣告「這個服務的設定長什麼樣」，由工具渲染成實際檔案。
- **版面與樣式**：HTML 與 CSS 陳述結構與外觀，由瀏覽器排版。
- **建置與基礎架構**：宣告基礎設施的期望狀態，由工具偵測差異並收斂（converge）。
- **規則引擎**：陳述規則與事實，由推論引擎找出結論。
- **數學式描述**：以等式或代數式描述問題，由符號引擎求解。

## 範例：同一個查詢的三種表達

需求：找出訂單金額大於 1000 的客戶姓名。

**命令式（程序式取資料）**：

```
def find_big_spenders(conn, threshold=1000):
    cursor = conn.cursor()
    cursor.execute("SELECT customer_name, amount FROM orders")
    result = []
    for row in cursor.fetchall():
        if row.amount > threshold:
            result.append(row.customer_name)
    return result
```

**宣告式（SQL）**：

```
SELECT customer_name
FROM orders
WHERE amount > 1000;
```

**更進階的宣告式（LINQ，運算式本身就是宣告）**：

```
from o in orders
where o.amount > 1000
select o.customerName
```

宣告式版本短得多，而且——這是關鍵——它把「如何掃描」交給最佳化器：資料庫可以選用索引掃描、平行掃描或物化檢視，**不必修改程式碼**。命令式版本則把掃描策略硬寫在程式裡，資料量一變就要改程式。

## 範例：宣告式設定的收斂過程

宣告式基礎設施的運作方式是「宣告期望狀態 → 引擎比對實際狀態 → 套用差異 → 重複直到收斂」：

```
期望狀態（宣告）        實際狀態（觀察）
   web 伺服器 × 3   ──▶   web 伺服器 × 1
   資料庫 × 1        ──▶   資料庫 × 1（版本過舊）
   防火牆規則 × 5    ──▶   防火牆規則 × 4
        │                     │
        ▼                     ▼
   引擎計算差異：新增 2 台伺服器、升級資料庫、新增 1 條規則
        │
        ▼
   套用差異 → 重新觀察 → 已收斂
```

這個模型的價值在於「宣告意圖」與「執行方式」分離：同樣一份宣告在 AWS、Azure 與本地叢集上會被各自的引擎以不同方式實現，但描述的是同一個期望狀態。命令式腳本則必須為每個平台各寫一份。

## 前因後果

- **前因**：1960 年代的關聯式資料庫與 SQL（1970 年代）、Prolog（[1972年]）把「描述」與「執行」分離的想法正式帶入軟體工程；早期介面程式碼與批次處理的維護成本，是這條路線的直接推力。
- **後果**：宣告式滲透到現代軟體的每一層——雲端基礎架構宣告、容器編排宣告、前端樣式宣告、持續整合流水線宣告、資料查詢宣告。它們共同提供一項關鍵能力：**意圖與實作分離，使最佳化器可以在不修改程式碼的情況下改進執行方式**。

## 與相鄰分類的關聯

- 與 [語言典範] 的關係：宣告式是抽象層次最高的典範，控制力最小而最佳化空間最大。
- 與 [函式式] 的關係：多數宣告式語言以函式組合實作宣告，兩者常並用。
- 與 [物件導向] 的關係：以物件建模資料、以宣告描述狀態，是現代設定系統的常見組合。
- 與 [軟體工程] 的關係：宣告式基礎設施改變了維運流程，把「寫程序」轉成「描述期望」。

## 容易混淆之處

- **宣告式不等於沒有演算法**：SQL 查詢背後仍有查詢計畫、索引選擇與成本估算，演算法只是被藏在引擎裡。
- **宣告式不等於不需效率考量**：引擎仍受資料量限制，只是最佳化由引擎負責；寫出無法最佳化的宣告（如在索引欄位上套函式）仍會很慢。
- **宣告式不等於易學**：把控制權交出去，等於把推理成本轉移到「我能否預期引擎會怎麼做」。
- **宣告式與命令式常在同一程式中共存**：現代系統通常是「宣告式描述意圖 + 命令式實作邊界」。

## 技術要點

- 宣告式語言的實作要點：宣告的內部表示（AST）、最佳化規則、執行引擎三者分離。
- 查詢最佳化的核心是成本模型：以統計資訊估算不同執行計畫的代價，選最省者。
- 宣告式基礎設施依賴「期望狀態 vs 實際狀態」的差異比對與冪等操作，才能安全重複執行。
- 規則引擎的宣告式表現在於把「規則」與「推論程序」分離，同樣的規則集可配不同推論策略。
- 宣告式的可測試性通常更好：輸出一組期望結果即可斷言，不需模擬執行過程。

## 常見的論爭

- **過度宣告式的風險**：抽象層越高，除錯越難；「它就是不會動」而不會告訴你哪裡錯，是宣告式系統最常見的抱怨。
- **最佳化器是否真的比人強**：小資料量或特殊負載下，人工調整的執行計畫常勝過通用最佳化器。
- **宣告式是否只是延後問題**：一派認為複雜度只是被推給引擎，並未消失；另一派認為這正是把重複勞作一次性投資的正確做法。
