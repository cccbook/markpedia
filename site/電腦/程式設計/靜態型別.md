# 靜態型別

> 隸屬：[程式設計]　·　狀態：初稿

> 對應維基百科：[中文維基百科：類型系統](https://zh.wikipedia.org/wiki/%E9%A1%9E%E5%9E%8B%E7%B3%BB%E7%B5%B1)　·　[English Wikipedia: Type system](https://en.wikipedia.org/wiki/Type_system)

靜態型別是**在程式執行之前（通常是編譯期）就完成型別檢查的型別系統**：每個值在來源碼中就帶有被宣告或被推論出的型別，編譯器會拒絕型別不相容的組合。它換來的是「錯誤提前被發現」與「大型重構有編譯器把關」，代價則是型別註記帶來的書寫成本與檢查規則帶來的限制。

## 技術與理論的關聯

- **型別即規格**：型別註記是程式設計中最接近「機器可驗證的合約」的東西——「這個函式只接受整數」寫成簽名後，編譯器會在每一個呼叫點免費驗證一次。
- **Curry–Howard 對應的實用化**：型別對應命題、程式對應證明，因此強型別語言的型別檢查可視為有限的自動證明，這是 [數學] 與工程最緊密的交會之一。
- **Hindley–Milner 演算法**：讓編譯器能從使用情境反推型別，是型別推論的技術基礎，也讓「不寫註記也有型別」成為可能。
- **子型多型**：以型別層次表達「是一種」的關係，是 [物件導向] 多型的實作原理；Liskov 替換原則則要求子型可安全替代父型。
- **可判定性與保守性**：完整型別檢查在一般情形下不可判定，因此實用系統選擇可判定但保守的規則——寧可拒絕部分正確的程式，也不放行錯誤的程式。

## 靜態型別的主要流派

- **名目型別（nominal）**：兩個型別相容與否由宣告決定，Java、C# 屬之。
- **結構型別（structural）**：兩個型別相容與否由其結構（欄位與方法）決定，TypeScript、Haskell 屬之。
- **依值型別（dependent）**：型別可依賴值，型別檢查等於定理證明，Coq、Agda、Idris 屬之。
- **漸進型別（gradual）**：允許部分程式碼無型別，並在邊界做執行期檢查，TypeScript 與 Python 的型別提示屬之。
- **漸進式泛型**：泛型寫法逐漸被允許（TypeScript 的 any），是開發速度與安全性的妥協點。

## 範例：型別系統攔截的典型錯誤

```
def average(xs: list[int]) -> float:
    return sum(xs) / len(xs)

result = average([1, 2, 3])
print(result)
```

若呼叫端誤傳字串，編譯期即被拒絕：

```
result = average(["1", "2", "3"])   # 錯誤：list[str] 不能傳給 list[int]
```

若忘記處理空清單，型別系統（尤其支援窮舉匹配或非空型別的語言）也能在編譯期指出：

```
match xs:
    case []: raise ValueError("空清單沒有平均值")
    case [single]: return float(single)
    case many: return sum(many) / len(many)
```

**要注意的界線**：型別能擋下「形狀錯誤」（shape error），卻擋不住「語意錯誤」——把年齡設成負數、把百分比當成小數，型別系統都不會有意見。這是為什麼 [品質確保] 與領域建模仍然不可取代。

## 範例：靜態檢查帶來的重構能力

假設要修改 `send_email(to: str, body: str)` 的簽名，改成接受一個 `EmailAddress` 值型別：

```
type EmailAddress = str   # 概念上：帶型別別名的地址

def send_email(to: EmailAddress, body: str) -> None:
    ...

send_email("alice@example.com", "hi")     # 型別別名仍接受 str，編譯通過
send_email("alice", "hi")                 # 若使用新包裝型別，編譯期即被標記
```

在具名型別語言中，把參數型別從 `str` 改成 `EmailAddress` 這一項修改，編譯器會列出全專案中所有受影響的呼叫點；在 [動態型別] 中，同樣的修改只能靠搜尋與測試發現。這就是靜態型別最實際的價值：**讓「我改了什麼、會影響誰」變成可列舉的清單**。

## 前因後果

- **前因**：1950 年代的 FORTRAN 有原始型別但檢查極弱；1960 年代的 ALGOL 與 ML 家族開始把型別當成語言的核心機制；推力來自大型專案裡「把字串當數字用」這類錯誤的比例過高。
- **後果**：靜態型別讓大規模重構、泛型容器與編譯期最佳化（因為型別已知，別名分析與單態化得以進行）成為可能；它也催生了漸進型別這類折衷，以消化既有程式碼的改造成本。

## 與相鄰分類的關聯

- 與 [型別系統語法] 的關係：靜態型別是型別系統在檢查時機上的那一半，與推論、泛型、漸進型別緊密相連。
- 與 [物件導向] 的關係：子型多型與介面型別是靜態型別語言支撐物件導向的主要機制。
- 與 [控制結構] 的關係：窮舉匹配與非空型別把「漏處理一種情況」變成編譯錯誤。
- 與 [軟體工程] 的關係：型別系統是「維護成本」的第一道自動防線。

## 容易混淆之處

- **靜態不等於強**：C 是靜態但弱型別（指標可任意轉型），Python 是動態但強型別；兩者是正交的軸。
- **型別註記不等於測試**：型別只驗證形狀，不驗證業務規則。
- **編譯期檢查不等於零成本**：大型泛型程式碼的建置時間可能顯著增加。
- **型別註記會過期**：註解與真實型別不同步時，IDE 與編譯器可能誤導；可由檢查器強制同步。

## 技術要點

- 檢查時機、推論能力、強弱程度是三個獨立維度，組合成實務上的多樣型別系統。
- 泛型實作有編譯期單態化與執行期抹除兩條路線，影響效能與二進位大小。
- 型別推論可涵蓋 Hindley–Milner 的完整演算法，也有只做局部推論的保守實作。
- 漸進型別的關鍵設計是「任何標註都不改變執行期語意」，讓型別可以逐步引入。
- 邊界型別（refinement type）是把值域限制寫進型別的嘗試，例如「年齡大於零」。

## 常見的論爭

- **靜態型別是否必然優於動態**：長久的陣營之爭；近年共識趨向「依專案規模、變更頻率與團隊組成選擇」。
- **型別註記是文件還是噪音**：一派視簽名為最可靠的自動更新文件；另一派認為推論已足，註記徒增維護面積。
- **依值型別是否值得**：能證明任意性質，但學習與工程成本高，工業語言仍停在「抓常見錯誤」的甜蜜點。
