# 推論

> 隸屬：[程式設計] › [型別系統語法]　·　狀態：初稿

> 對應維基百科：[中文維基百科：類型推論](https://zh.wikipedia.org/wiki/%E7%B1%BB%E5%9E%8B%E6%8E%A8%E8%AE%BA)　·　[English Wikipedia: Type inference](https://en.wikipedia.org/wiki/Type_inference)

推論是**讓工具從程式碼本身反推型別的機制**——程式士不必手寫每個值的型別，只要寫得夠清楚，編譯器或型別檢查器就能自行補完。舉例而言，在 Haskell 裡 `x = 2` 這一行會被推論為 `x :: Num a => a`；在 Rust 裡 `let mut total = 0;` 會被推論為 `i32`，直到某處把它與 `f64` 相加，檢查器才會要求你補上型別標註。

「推論」的白話解釋是：**型別標註原本要程式士手寫的資訊，改由工具根據上下文代勞**。它把型別系統從「必須逐處標註」放寬為「必須一致但不必寫出」，因而讓靜態型別從研究語言的特權變成日常可用的工程選項。

## 技術與理論的關聯

- **推論的可行性來自 Curry–Howard 對應**：型別即命題、程式即證明，因此證明的型別可以由證明本身導出，而不必先寫下命題。這是 [數學] 與程式設計在型別理論上的交會點。
- **Hindley–Milner 演算法（[1982年]）** 給出了最經典的推論規則：先做型別變數代換，再以統一化（unification）收斂，得到最小型別。ML 家族、OCaml、Haskell 皆以此為基礎。
- **推論與泛型是一體兩面**：泛型是「把型別當參數」，[泛型] 提供跨型別的抽象；推論則是「讓型別自己現形」。兩者互相依賴——泛型函式若無推論，呼叫端必須顯式指定型別參數，冗長難讀。
- **主體多型（polymorphic let）** 是推論的高階形態：同一個 `let` 綁定可以在多處以不同型別使用，這需要比簡單代換更強的推論能力。
- **單態化限制**：型別類別（type class）系統中，若一個泛型值同時被要求兩種不同型別的實例，Hindley–Milner 系統會拒絕，需要明確的型別註記或多態的 let 綁定。
- **漸進型別的折衷**：TypeScript 與 Python 的型別提示允許「要檢查就檢查，不檢查也能跑」，推論在這類系統中扮演「未標註部分」的角色。
- **推論是編譯期成本**：每次編譯都要執行型別檢查與統一化，複雜專案可見明顯的編譯時間增加——這是開發體驗與靜態檢查強度的直接交易。

## 範例：同一段程式在四種語言裡的型別來源

需求：把一個數字清單轉成字串清單。

**Haskell（完整推論，連回傳型別都自動決定）**：

```haskell
showAll :: [Int] -> [String]
showAll xs = map show xs
```

其中 `show` 來自 `Show` 型別類別，元素的確切型別由呼叫端的 `xs` 決定；`showAll` 的簽名若不寫，Haskell 也能推論出 `Show a => [a] -> [String]`。

**OCaml（推論加少量註記）**：

```ocaml
let show_all xs = List.map string_of_int xs
```

推論器由 `string_of_int` 得知 `xs : int list`；若改成 `List.map string_of_float xs`，推論器會立刻回報型別不符——錯誤在編譯期被攔下。

**Rust（局部推論，型別隨著需求具體化）**：

```rust
fn main() {
    let nums = vec![1, 2, 3];
    let mut total = 0;          // 推論為 i32
    for n in &nums {
        total += *n;             // 此處要求 total 為整數
    }
    let labels: Vec<String> = nums.iter().map(|n| n.to_string()).collect();
    println!("{} {:?}", total, labels);
}
```

`total` 一開始只是 `0`（尚未定型），在 `+=` 出現時才被收斂為整數型別。若改成 `let mut total = 0.0;`，`+=` 整數就會報型別錯誤。

**Python（動態執行期才發現）**：

```python
def show_all(xs):
    return [str(x) for x in xs]

show_all([1, 2, 3])       # 正常
show_all([1, "two", 3])   # 執行到這裡才得到 ['1', 'two', '3']，沒有任何錯誤
```

四段示範了同一筆交易的兩端：**推論把「型別錯誤」從執行期搬到編譯期，代價是編譯器必須真的做推論工作**。

## 前因後果

- **前因**：早期語言多為「無型別」或「全部標註」。Fortran 與 Lisp 只有粗略的型別區分；ALGOL 68 的型別系統過於複雜，實作困難，阻礙了它的普及。
- **轉折**：1970 年代的 ML 語言把 Hindley–Milner 推論實作成可用的語言特性，讓「不寫型別也能有靜態檢查」從理論變成工程事實。
- **後果**：1990 年代的 OCaml 讓推論進入學術與工業語言；2000 年代的 TypeScript 把「可選的靜態型別 + 推論」帶到網路前端的整個生態，使 JavaScript 專案得以在不重寫的情況下獲得編譯期檢查。
- **持續後果**：Rust 與 Swift 把推論與「零成本抽象」結合，推論讓高階語法不必犧牲執行效率；同時推論對編譯器實作的要求，也促成 LLVM 與 rustc 這類高效編譯基礎設施的成熟。
- **[2015年]** Rust 1.0 正式發行，其推論與借用檢查的組合成為「靜態安全」主張的代表性實作。

## 與相鄰分類的關聯

- 與 [泛型] 的關係：泛型是型別層的抽象，推論是型別層的省略；兩者合用才能同時獲得抽象與簡潔。
- 與上位概念 [型別系統語法] 的關係：推論是靜態型別體系的必要配套，否則標註成本會壓垮採用意願。
- 與 [控制結構] 的關係：推論要求分支兩側的型別一致（Rust 的 `match` 可要求窮舉並綁定型別），因此型別資訊會回頭影響控制結構的寫法。
- 與 [演算法] 的關係：泛型演算法（如排序、搜尋）必須配合推論才能讓呼叫端不必指定型別參數。
- 與 [軟體工程] 的關係：推論把「型別正確」這類文件性質的約束變成可自動檢查的規格，降低團隊對口頭紀律的依賴。

## 容易混淆之處

- **推論不等於沒有型別**：推論出來的型別一樣受型別系統規則約束，只是由工具填上。
- **推論不等於型別註記可省略一切**：在公共介面上，註記仍是文件與相容性契約；多數語言要求匯出簽名明確標註。
- **推論不解決「型別錯誤的意圖」**：它能擋下字串與整數相加，卻擋不下把年齡設成負數。
- **推論與動態型別無關**：兩者都在「少寫型別」，但動態型別根本沒有推論器，型別在執行期才決定。

## 技術要點

1. **統一化是推論的心臟**：把兩個型別求公因數的過程，決定了推論器能收斂多快、以及會不會報出難懂的型別錯誤。
2. **註記是給推論器的提示**：需要時加一行註記，往往能讓整個函式的型別變得可讀，而不是消滅推論。
3. **區域多型與主體多型是不同層次**：前者是「同一段程式在不同地方可有不同型別」，後者是「同一個值同時有多種型別」，混用時容易產生困惑。
4. **推論的方向決定了可用性**：由約束往回推（ bidirectional checking）比單向推論更容易產生好的錯誤訊息，也更容易實作。
5. **編譯時間是推論的稅**：大型單體專案常需關閉部分檢查或增量編譯緩解。
6. **型別錯誤訊息的可讀性**是推論系統好壞的實務判準，比推論能力本身更影響工程體驗。

## 常見的論爭

- **推論是否讓程式更難讀**：支持者認為型別是隱含意圖，應由工具輔助閱讀；反對者指出大型專案中，未標註的推論結果常需反覆查詢型別才看得懂。
- **隱式型別 vs 顯式型別**：Rust 社群常主張「讓型別易於推論」比「要求處處標註」更有效，與之相對的一派則認為顯式標註是最佳文件。
- **推論的上限在哪**：可推論的型別子集在理論上是有界且保守的（Hindley–Milner 系統不可判定），因此推論器多半選擇「寧可多問一句」。
