# 程式碼審查

> 隸屬：[程式設計] › [開發方法]　·　狀態：初稿

> 對應維基百科：[中文維基百科：程式碼審查](https://zh.wikipedia.org/wiki/%E4%BB%A3%E7%A0%81%E5%AE%A1%E6%9F%A5)　·　[English Wikipedia: Code review](https://en.wikipedia.org/wiki/Code_review)

程式碼審查是**由人（或工具）在程式碼合併前，逐行閱讀並提出修改意見的品質與知識活動**，白話說就是「在別人接手你的成果之前，先讓另一雙眼睛看過一遍」。

審查有兩個目的，兩者同等重要：**抓出缺陷**與**傳播知識**。業界經驗與研究一致顯示，審查攔下的多數不是會造成事故的嚴重 bug，而是可讀性、命名與設計問題；同時，審查是新人熟悉程式脈絡最有效的方式。審查因此既是品質關卡，也是團隊的知識傳播機制。

## 技術與理論的關聯

- **審查是「人的檢查點」**：自動化工具（型別檢查、靜態分析、測試）能檢查的是形式性質；審查能檢查的是意圖——「這段程式為什麼這樣寫」「這個特例是否必要」。
- **審查是組織設計的產物**：審查能有效，前提是團隊規模足以讓「另一雙眼睛」存在；兩三人的團隊往往沒有真正的審查，只能靠互相看程式碼的習慣。
- **審查與版本控制是一體的**：審查的單位是提交或 Pull Request，也就是 [版本控制] 的差異物件；沒有提交圖就沒有審查。
- **審查與測試互補**：測試驗證「程式做了什麼」，審查驗證「程式該做什麼、是否做了多餘的事」，兩者缺一不可（見 [測試驅動]）。
- **審查延遲是主要成本**：研究與實務都指出，審查回饋的等待時間比審查本身的嚴格程度更影響士氣與產出；審查拖過一天，程式碼品質下降的幅度往往超過放寬標準。
- **社會因素與技術因素同等重要**：審查的互動本質決定了它的效果——匿名審查與具名審查、權威差異與平權討論，會得到不同的結果。
- **審查的知識傳播效果可量化**：跨團隊的審查把「某人知道但沒人知道的事」轉為組織資產，這是開源專案能累積數百名貢獻者的關鍵機制。

## 範例：一次 Pull Request 審查的完整往返

情境：團隊成員提交「購物車滿額折扣」功能（程式碼見 [測試驅動] 的紅綠重構段落）。

**第一步：作者準備**（決定審查能否順利）：

```
- 提交只含兩個檔案：cart.py 與 tests/test_cart.py
- 提交訊息說明動機：促銷活動需要滿額折扣，門檻設在 1000 元
- 描述欄列出自己已檢查的事項：測試通過、格式已跑過
```

**第二步：審查者閱讀**（先看意圖再看細節）：

```
1. 整體：折扣門檻 1000 與 9.5 折是硬編碼，是否應為設定？
2. 邊界：raw 恰好等於 1000 時套用折扣，符合需求描述嗎？
3. 型別與命名：round() 未指定小數位，是否應明確？
4. 測試：缺少「剛好 1000 元」的案例
5. 可讀性：total() 內同時做加總與判斷，可否拆成 raw_total()？
```

**第三步：作者回應**（逐條處理，不混為一談）：

```
- 門檻與折扣率已抽出為模組常數，後續可改為設定讀取
- 已補上邊界測試 test_total_at_exact_threshold
- round() 改為 round(raw * rate, 2)
- 已重構為 raw_total() + total()
```

**第四步：合併前檢查**（審查與自動化協同）：

```
- 持續整合重新執行全部測試：全綠
- 審查者檢視作者的反應後回覆「可以合併」
- 合併到主幹，標記發版版本
```

這個往返呈現審查的關鍵性質：**審查的價值不在攔下，而在把「我以為的意思」與「別人讀到的意思」對齊**。作者在過程中被迫把隱含假設寫成文字，那些假設往往正是缺陷所在。

## 前因後果

- **前因**：1970 年代的程式審查是「坐在同一間房間、拿著印出來的程式碼一起讀」的集體活動，源自硬體時代對「壞掉的線路要靠人眼看出來」的檢查觀念。
- **轉折**：[1976年] IBM 的 Michael Fagan 推動程式碼審查制度化，強調「審查不是找錯，而是找出所有可能改進之處」，此觀點至今仍被引用。
- **網路化**：1990 年代末的開源社群把審查搬到網路上，讓「非同步、多人、大量」的審查成為可能；審查延遲與審查負擔成為新的管理課題。
- **產業化**：[2013年] 之後，微軟、Google 等大型團隊發表的審查數據與指引，使審查從「團隊習俗」升級為有數據支持的管理實務，也讓「審查能不能當成招募篩選器」這類問題進入公開討論。
- **後果**：審查成為現代軟體工程中最普遍的品質機制，與持續整合、自動化測試共同構成「小步合併」的基礎；審查品質也成為 AI 輔助程式設計時代的新課題——當程式碼由模型大量生成，人類審查的負擔與重要性同時上升。

## 與相鄰分類的關聯

- 與上位概念 [開發方法] 的關係：審查是四件配備中的「攔截點」，其餘三者（版本控制、測試驅動、敏捷）都為它準備材料。
- 與 [版本控制] 的關係：審查的載體是提交；審查者看到的應是「意圖 + 差異」，而非整個檔案。
- 與 [測試驅動] 的關係：測試是審查的重要參照物——審查者應確認測試真的描述了需求，而非只描述實作。
- 與 [軟體工程] 的關聯：審查是 [品質確保] 中最依賴人的一環，也是 [敏捷] 中「完成定義」的組成部分（審查通過常被列入完成的條件）。
- 與 [分支]、[迴圈] 的關係：審查最常聚焦的正是控制結構的邊界——分支是否處理所有情況、迴圈邊界是否正確。

## 容易混淆之處

- **審查不等於審核風格**：格式與命名應交給自動化工具（格式化器、靜態檢查），人的審查時間應留給語意與設計。
- **審查不等於刁難**：審查的對象是程式碼不是人；把審查當成地位競賽或上對下的關卡，是團隊失效的常見原因。
- **批准不等於正確**：審查者只是「沒有發現問題」，不能保證沒有問題；風險仍需由測試與監控分擔。
- **審查數量不等於品質**：快速連續送出大量請求以累積「審查數」，是常見的反模式。
- **作者不能自我審查**：同一人寫又審，幾乎無法發現自己的盲點。

## 技術要點

1. **審查要小**：變更越小越容易審，數百行的請求應要求拆分；過大的變更多半會被草率通過。
2. **先看意圖再看實作**：描述、提交訊息與關聯議題能讓審查者用正確的心智模型閱讀。
3. **明確標註問題等級**：區分「必須修正」與「建議」，避免每個註解都被當成阻擋。
4. **回應要逐條**：作者對每一則意見給出「已修改」或「不修改的理由」，審查記錄因此成為日後可查的決策依據。
5. **回覆要快**：能在一個工作天內完成審查最好；逾時未回覆的請求應主動轉派或關閉。
6. **自動化先行**：格式、命名規則、静態分析與測試必須在送審前全綠，否則人的注意力會被噪音耗盡。
7. **審查者需有上下文**：沒有領域知識的審查只能看到表面；因此審查者的指派應考慮模組熟悉度。
8. **定期回顧審查品質**：檢視被攔下的缺陷類型、平均回應時間與被忽略意見的比例，是改善團隊的入口。

## 常見的論爭

- **審查成本是否值得**：反對者以審查延遲拖慢交付、且大型變更常被形式化審查為由，質疑其效益；支持者以攔下缺陷與知識傳播的數據反駁。
- **嚴格 vs 寬鬆**：嚴格審查提高品質但拉長週期、可能壓抑新手；寬鬆審查加快交付但累積技術債。沒有普適答案，只有與團隊風險承受度匹配的平衡點。
- **是否需要具名**：匿名審查可降低權威偏誤，但也削弱責任感與討論深度；不同組織有不同經驗。
- **AI 時代的審查**：當程式碼大量由模型生成，人工逐行審查的成本上升；是否改以「驗證生成結果的測試」取代「逐行閱讀」，成為新的實務辯論。
