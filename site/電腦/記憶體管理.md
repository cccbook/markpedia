# 記憶體管理

> 隸屬：[電腦] › [作業系統]　·　狀態：初稿

> 對應維基百科：[中文維基百科：記憶體管理](https://zh.wikipedia.org/wiki/%E8%A8%98%E6%86%B6%E9%AB%94%E7%AE%A1%E7%90%86)　·　[English Wikipedia: Memory management](https://en.wikipedia.org/wiki/Memory_management)

記憶體管理是**作業系統決定「誰能用哪一段實體記憶體、用多久」的機制**。它的三個任務：分配（把記憶體切給行程）、保護（不讓行程互相踐踏）、以及透明化（讓每個行程以為自己擁有一整台機器的位址空間）。沒有它，多行程共享記憶體就等於災難。

現代記憶體管理以「分頁」為基石：把虛擬位址空間與實體記憶體都切成 4 KiB 的頁，MMU 硬體以多級頁表完成轉換。在此之上，作業系統疊加置換（swap）、按需載入、寫時複製與緩衝快取，把有限實體記憶體放大成一個看起來無限大的空間。

## 技術與理論的關聯

- **虛擬位址空間**：每個行程有獨立的虛擬位址空間（64 位元系統實用約 256 TiB），程式從不碰實體位址。
- **多級頁表與 TLB**：x86-64 用四級頁表；TLB 快取最近的轉換結果，TLB 不命中的成本是十至百個週期，因此出現大頁（2 MiB、1 GiB）技術。
- **按需分頁**：`malloc` 只登記虛擬空間，真正讀寫時觸發缺頁例外才配置實體頁——記憶體被「許諾」而非「實付」。
- **置換與工作集**：實體頁不足時，置換演算法（LRU 近似、時鐘演算法）挑一頁寫回磁碟；工作集理論說明「保持熱頁常駐」是效能關鍵。
- **寫時複製**：fork 不拷貝整個位址空間，父子共享頁面、標記唯讀，任一方寫入才複製——行程建立因此近乎免費。
- **外碎片與內碎片**：連續配置產生外碎片（小空洞）、固定塊產生內碎片（配置大於需求）；分頁消除了外碎片，夥伴系統（buddy allocator）管理實體頁。

## 範例

**問題**：程式 `int *p = malloc(100MB); p[0] = 1;` 實際發生什麼？

1. **malloc 層**：C 函式庫向核心請求擴充堆（`mmap` 或 `brk`），核心只登記虛擬區間，不動實體記憶體。
2. **第一次寫入**：`p[0]=1` 觸碰第一頁，MMU 查頁表發現無映射，CPU 產生缺頁例外。
3. **核心接手**：缺頁處理函式從實體頁池取一頁、填零（安全考量）、填入頁表項、標記可寫。
4. **恢復執行**：例外返回後同一條指令重執行，這次成功；其餘 25600 頁（100MB ÷ 4 KiB）仍只是虛擬許諾，未碰則不佔實體記憶體。
5. **記憶體吃緊時**：若系統全體頁不足，核心的時鐘演算法挑選冷頁——若它是匿名頁（如這些堆頁）就寫入 swap；若是檔案頁（如程式碼）可直接丟棄、日後從檔案重讀。
6. **對照**：`fork()` 之後父子行程的這 100 MB 虛擬空間共享同一組實體頁（唯讀），任一方寫入才觸發複製——一個 4 GiB 程式的 fork 實際只花幾 MB，這是寫時複製的威力。

## 前因後果

- **前因**：早期機器把行程緊貼排列，連續配置造成的碎片與「無法載入大程式」是硬傷；分頁（Atlas，1962）把位址空間與實體記憶體解耦，虛擬記憶體從此誕生。
- **後果**：虛擬記憶體成為行程隔離、記憶體保護與記憶體映射檔（mmap）的基礎；GC 語言的堆、資料庫的緩衝池與 mmap I/O 全部踩在分頁之上。

## 與相鄰分類的關聯

- 與 [階層式儲存] 的關聯：swap 是階層的最底延伸，缺頁例外是階層之間的搬運工。
- 與 [行程] 的關聯：位址空間是行程身分的核心部分。
- 與 [資訊安全] 的關聯：不可執行頁（NX）、位址空間隨機化（ASLR）都是記憶體管理提供的安全機制。
- 在上位概念 [作業系統] 中，記憶體管理與排程並列兩大核心職能。

## 容易混淆之處

- **虛擬記憶體與 swap 不同**：虛擬化是位址轉換與保護機制，swap 只是它的一個用法。
- **malloc 配置不等於實體記憶體佔用**：寫入前是純虛擬許諾，`free` 之後也未必立刻歸還核心。
- **GC 語言的記憶體管理與 OS 的不同**：垃圾回收器在使用者層管理堆，OS 記憶體管理在其下層運作，兩層各自有碎片問題。
- **缺頁不等於錯誤**：絕大多數缺頁是正常流程；只有非法位址（segfault）才是真的故障。

## 技術要點

- 頁表項的位元：存在位、讀寫位、使用者/核心位、存取位與髒位——置換演算法依賴存取與髒位。
- TLB 失效要用指令（如 `invlpg`）顯式驅逐，改頁表後必做。
- 大頁減少 TLB 壓力，資料庫與 JVM 常啟用 transparent huge pages。
- mmap 讓檔案直接映射進位址空間，讀寫檔案變成讀寫記憶體，缺頁即 I/O。
- OOM killer 是 Linux 記憶體耗盡的最後手段，按壞名聲分數挑選犧牲者。
- 效能指標的真相：快取命中率、TLB 命中率與缺頁率比「記憶體使用率」更能預測延遲。

## 常見的論爭

- **swap 的價值**：足夠 RAM 時要不要禁 swap？支持者強調它吸收冷頁、救回偶發尖峰，反對者指出桌面場景的卡頓來自換頁抖動。
- **4 KiB 頁是否過小**：記憶體容量百年成長而頁大小幾乎不動，大頁派與碎片成本派各有理據。
- **GC 的代價**：手動管理（C）、自動管理（Java）與區域管理（Rust）的生產力與延遲之爭，是程式語言界長期戰場。

## 實務補充：配置器與碎片

動態記憶體配置（malloc 系列）在實作上有兩大策略：分區配置（每次配置一個連續區塊，回收時易產生外部碎片）與分頁配置（把空間切成固定大小的小塊，回收時易產生內部碎片）。現代分配器多採後者並配合大小分離（small/large/oversize）與空閒清單最佳化。

碎片是長期運行的伺服器常見的記憶體洩漏來源：即使程式邏輯沒有遺失指標，配置器內部的碎片也可能讓行程的常駐記憶體持續上升。

記憶體管理還包括垃圾回收（追蹤式與引用計數的取捨）、記憶體對齊與大頁（huge pages）等主題；後者能減少 TLB 缺失，對資料庫與機器學習等大工作集特別有效。

### 記憶體分配的實務原則

實務上常見的原則是讓生命週期明確對齊：能用靜態或栈配置的，就不要用堆配置；能讓物件在單一函式內結束生命的，就不要讓它跨呼叫存活。這能大幅減少配置器壓力與洩漏風險。

對長駐服務而言，週期性檢查常駐記憶體、追蹤配置次數與碎片率是必要的維運手段；把記憶體當作與 CPU 同等重要的資源來預算，是現代服務的基本要求。

### 與硬體的協作

記憶體管理離不開硬體支援：頁表由 MMU 轉譯，TLB 快取轉譯結果，實體頁框框架由核心分配，並可搭配硬體換頁提示（如 Linux 的 MADV_HUGEPAGE 或頁面遷移提示）協助核心做出更好的決策。缺少硬體支援時，軟體只能以較粗糙的粒度管理記憶體，開銷也更高。
