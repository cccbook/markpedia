# 整數與浮點

> 隸屬：[電腦] › [資料表示]　·　狀態：初稿

> 對應維基百科：[中文維基百科：浮點數運算](https://zh.wikipedia.org/wiki/%E6%B5%AE%E7%82%B9%E6%95%B0%E8%BF%90%E7%AE%97)　·　[English Wikipedia: Floating-point arithmetic](https://en.wikipedia.org/wiki/Floating-point_arithmetic)

整數與浮點是**電腦表示數值的兩大方案**。整數用二補數精確表示有限範圍內的整數，適合計數、索引與金額；浮點用「科學記號的二進位版」表示極大與極小的實數，適合科學計算與圖形，但只能近似。兩者的選擇不是偏好問題而是正確性問題：把錢用浮點算會丟分、把座標用整數算會溢位。

整數的表示簡單而致命的細節是溢位；浮點的表示複雜而致命的細節是誤差。這個條目把兩套方案的規則、陷阱與工程對策一次講清楚。

## 技術與理論的關聯

- **二補數整數**：n 位元範圍 $-2^{n-1}$ 至 $2^{n-1}-1$ ；加減法用同一電路，溢位以「繞回」或陷阱處理。
- **IEEE 754 浮點**：數值 = $(-1)^s \times 1.m \times 2^{e-bias}$ ；單精度 32 位元、雙精度 64 位元，另有特殊值 ±0、±∞ 與 NaN。
- **精確性與近似的分界**：浮點只能精確表示分母為 2 的冪的分數；0.5 精確、0.1 不精確。
- **捨入模式**：IEEE 754 預設「捨入到最接近、偶數優先」（banker's rounding），這讓大量運算的誤差統計上更均勻。
- **誤差會累積**：Kahan 求和演算法用一個補償變數追蹤捨入誤差，把長串浮點加法的誤差壓低數個數量級。
- **特殊值是特性不是錯誤**：NaN 表示未定義（如 0÷0）、∞ 表示溢位，比較運算對它們有特殊規則（NaN 與任何值比較皆為假）。

## 範例

**問題**：計算 0.1+0.2 是否等於 0.3，並示範正確的金額運算。

1. **位元拆解**：雙精度 0.1 的實際值是 0.1000000000000000055511151231257827…；0.2 是 0.2000000000000000111022302462515654…。
2. **相加**：兩者相加得 0.3000000000000000444089209850062616…，比 0.3（0.2999999999999999888977697537484345…）略大。
3. **比較結果**：`0.1+0.2 == 0.3` 在多數語言回傳 False——這不是 bug，是二進位表示的必然。
4. **工程對策一**：比較用容差 `abs(a-b) < 1e-9`。
5. **工程對策二**：金額以「最小單位整數」計算——把 1.23 元存成 123 分，所有運算都是整數，最後展示時才加小數點；這是銀行與支付系統的標準做法。
6. **對照整數溢位**：32 位元整數上限 2147483647，加 1 得 -2147483648（繞回）；2038 年 1 月 19 日，Unix 時間戳將撞上這個上限，是溢位的現實注腳。

## 前因後果

- **前因**：早期機器各用各的浮點格式，同一程式跨機器結果不同，1980 年代 Intel 8087 的設計者推動 IEEE 754 標準（1985 年定案），統一了捨入與特殊值。
- **後果**：標準化使數值程式可攜；此後的爭議轉向精度與效能的取捨——GPU 以 FP16、FP8 換取 AI 訓練吞吐量，金融系統堅持整數分。

## 與相鄰分類的關聯

- 與 [二進位] 的關聯：兩種方案都是二進位位元串的解讀約定。
- 與 [資料科學] 的關聯：統計計算的數值穩定性（條件數、正規化）直接取決於浮點誤差管理。
- 與 [演算法] 的關聯：累加求和的順序影響結果，Kahan 求和是演算法對誤差的正面回應。
- 在上位概念 [資料表示] 中，本條目處理「數」這個最基礎的資料類型。

## 容易混淆之處

- **浮點不等於實數**：浮點是有限精度近似，運算不滿足結合律：`(1e16 + 1) - 1e16` 得 0 而非 1。
- **單精度與雙精度不同**：有效位數分別約 7 與 15 位十進位數字。
- **NaN 不等於 NaN**：`x == x` 對 NaN 為假，檢測要用 `x != x`。
- **溢位與下溢不同**：溢位超過上限，下溢是太小而被捨為 0（漸進下溢以非正規數緩衝）。
- **整數除法向下捨去對負數的方向**：C 與 Python 對 -7÷2 的結果不同（-3 對 -4），跨語言要小心。

## 技術要點

- 二補數的快速取負：取反加一。
- 浮點比較的標準做法是 ULP（最後位元單位）容差而非絕對容差。
- Kahan 求和每步補償誤差，誤差從 $O(n\varepsilon)$ 降到 $O(\varepsilon)$ 。
- 混合精度（如 FP16 存、FP32 算）是現代 AI 晶片的主流策略。
- 整數溢位在 C 是未定義行為，編譯器可能刪除看似冗餘的溢位檢查，是安全漏洞來源。
- 128 位元整數與任意精度整數庫（如 Python 的原生大整數）消除了溢位，但代價是速度。

## 常見的論爭

- **浮點該不該用於金額**：主流共識是絕不用；但交易系統的即時估值仍大量使用浮點，界線在「結算」與「展示」。
- **精度與能耗**：FP8、FP4 在 AI 晶片的普及是否損害科學可信度，模擬界與機器學習界意見相左。
- **語言對溢位的態度**：Rust 預設偵錯模式陷阱、發布模式繞回；Swift 選擇永遠陷阱——「安全」與「速度」的取捨仍無定論。

## 實務補充：溢位與精度陷阱

整數溢位在 C 語言中是未定義行為，編譯器可假設它不會發生並據此最佳化，這就是某些安全漏洞的根源；安全的做法是在運算前後顯式檢查邊界。

浮點數則有兩個方向的誤差：表示誤差（無法精確表示 0.1）與運算誤差（多次運算的誤差累積）。在要求累加精確的場合，Kahan 補償求和等數值技巧可把誤差壓到極低。

兩者還有語意差別：IEEE 754 定義了 NaN、±Infinity 等特殊值，並讓除以零產生例外而非直接崩潰；然而在硬體中啟用完整的 IEEE 754 語意會增加電路成本，因此嵌入式與遊戲主機常使用較快的近似設定，導致同一段浮點程式在 不同平台上得到不同結果。
