# 資料表示

> 隸屬：[電腦]　·　狀態：初稿

> 對應維基百科：[中文維基百科：資料類型](https://zh.wikipedia.org/wiki/%E8%B3%87%E6%96%99%E9%A1%9E%E5%9E%8B)　·　[English Wikipedia: Data type](https://en.wikipedia.org/wiki/Data_type)

資料表示研究**資訊如何被編碼成位元、以及位元如何被解讀回資訊**。電腦內部只有高低兩種電位，一切內容——整數、小數、文字、聲音、影像、程式碼——都必須約定成一串 0 與 1。資料表示就是這些約定的總集：它既是硬體運算的對象，也是軟體之間交換資料的合約。

這個子分類的重要性在於「誤解位元的代價」：把有號整數讀成無號、把 UTF-8 位元組流當成 Big5 解碼、把浮點數當實數比較相等，都會產生真實的錯誤。因此程式語言的型別系統、檔案格式的標頭、網路協定的編碼欄位，本質上都是在防止同一串位元被錯誤解讀。

## 技術與理論的關聯

- **二進位是唯一語言**：任何資料先轉成位元；正整數用二進位，負數用二補數，實數用浮點格式，文字用字元編碼。
- **二補數的妙處**：負數 $-x$ 表示為 $2^n - x$ ，使減法可以直接用加法器完成，硬體不必另做減法電路。
- **浮點數是近似值**：IEEE 754 以「符號、指數、尾數」三段表示實數，多數十進位小數（如 0.1）在二進位下無法精確表示，累加誤差因此產生。
- **字元編碼的歷史包袱**：ASCII 用 7 位元，中文世界的 Big5 與 GBK 各自擴充，最後由 Unicode 統一；UTF-8 兼容 ASCII 成為網路事實標準。
- **壓縮的兩條路**：無失真壓縮（ZIP、PNG）保留全部資訊，利用統計冗餘；失真壓縮（JPEG、MP3）捨棄人類感知不敏感的資訊，換取更大倍率。
- **型別系統是軟體層的資料表示**：編譯器用型別決定位元的解讀方式與運算的合法性，是硬體編碼約定的高階投影。

## 範例

**問題**：把十進位數 13、負數 -13、以及字串「A」與「安」全部表示出來。

1. **正整數**：13 = 8+4+1 = `1101`（二進位），一個位元組表示為 `00001101`。
2. **負整數（8 位元二補數）**：-13 = 256 − 13 = 243 = `11110011`；驗證：`11110011` 的最高位是 1，代表負數，取反加一得 `00001101` = 13，正確。
3. **字元「A」**：ASCII 65 = `01000001`；UTF-8 中仍是單一位元組 `01000001`，這就是 UTF-8 兼容 ASCII 的好處。
4. **中文字「安」**：Unicode 碼位 U+5B89，UTF-8 編碼為三個位元組 `E5 AE 89`；若以 Big5 解讀則變成亂碼——同一串位元，編碼不同，意義全非。
5. **浮點近似**：0.1 在 IEEE 754 單精度下實際是 0.100000001490116119384765625；把 0.1 加十次再與 1.0 比較，結果常常不相等，這是浮點誤差的經典示範。
6. **壓縮的直覺**：一段「AAAAAAABBB」若直接每字元 8 位元要 80 位元；用霍夫曼編碼讓 A 佔 1 位元、B 佔 2 位元，只需 9 位元——冗餘度越高，壓縮率越好。

## 前因後果

- **前因**：電報與打孔卡的編碼傳統（摩斯電碼、BCD）提供了「以符號表示資訊」的先例，二進位則由布林代數給出運算基礎。
- **後果**：資料表示決定了整個軟體生態的相容性——同一份檔案跨作業系統可開、同一套程式跨機器可跑，都靠編碼與位元組序的標準化；壓縮技術更直接催生了 MP3、串流影音與整個數位媒體產業。

## 與相鄰分類的關聯

- 與 [電腦架構] 的關聯：算術單元支援的運算（加、移位、比較）完全依賴二補數與浮點格式的定義。
- 與 [作業系統] 的關聯：檔案系統儲存的是未解讀的位元組流，解讀責任在應用程式，因此副檔名與檔頭成為必要的約定。
- 與 [資訊安全] 的關聯：雜湊與加密的輸入輸出都是位元串，編碼錯誤常成為安全漏洞的來源。
- 在上位概念 [電腦] 中，本子分類是**合約層**：硬體與軟體之間、軟體與軟體之間的一切交換都靠它。

## 容易混淆之處

- **位元、位元組與字元不同**：位元是 0 或 1，位元組是 8 位元，字元是邏輯單位（一個字元可能占 1 至 4 位元組）。
- **二進位與二補數不同**：前者是記法，後者是負數的表示方案。
- **浮點數不等於實數**：浮點是有限精度的近似，運算不滿足結合律。
- **UTF-8 與 Unicode 不同**：Unicode 是字元集（碼位表），UTF-8 是其中一種編碼方式。
- **失真壓縮不等於劣質**：MP3 捨棄的是人耳聽不到的頻段，感知上幾乎無損。

## 技術要點

- 位元組序（大端、小端）影響跨平台資料交換，網路位元組序規定為大端。
- n 位元無號整數範圍是 0 至 $2^n - 1$ ；8 位元即 0 至 255。
- 二補數只有一個零，且加法溢位可用環繞或陷阱兩種策略處理。
- IEEE 754 規定單精度 32 位元（1+8+23）、雙精度 64 位元（1+11+52）。
- UTF-8 的自我同步特性：任何位元組都可判斷自己是字元開頭還是延續，損壞不會擴散。
- 無失真壓縮有理論極限：資訊熵給出平均每符號位元數的下界，霍夫曼編碼在符號獨立前提下接近此界。

## 常見的論爭

- **Big-endian 與 little-endian 之爭**：源自《格列佛遊記》的雞蛋之爭，實務上 x86 採小端、網路協定採大端，兩者並存至今。
- **失真壓縮是否損害藝術完整性**：音樂人反對 MP3 的音質損失，串流平台則以高碼率折衷。
- **字元編碼的遷移成本**：從 Big5、GBK 遷移到 UTF-8 需要改資料庫與程式，遺留系統是否值得升級至今仍是企業難題。

## 實務補充：資料表示的取捨

資料表示的選擇本質上是資訊理論與工程實務的折衷：位元越多表示越精確，但佔用更多記憶體頻寬。定點數省電、精度可預期，適合訊號處理；浮點數運算單位更通用，但需要更複雜的硬體與軟體支援。

同一份資料的不同表示會導向不同的演算法效率：把資料轉成可排序的整數鍵，能讓資料庫用二分搜尋而非全表掃描；把矩陣轉成稀疏格式，能讓運算量從 O(n²) 降到與非零元素數成正比。

表示方式也決定了互通成本：檔案格式、序列化格式與網路協定若採不同編碼，系統之間就必須寫轉換程式，這也是通用標準（如 UTF-8、Unicode）存在的理由。
