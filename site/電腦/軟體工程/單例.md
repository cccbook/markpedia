# 單例

> 隸屬：[設計模式]　·　狀態：初稿

> 對應維基百科：[English Wikipedia: Singleton pattern](https://en.wikipedia.org/wiki/Singleton%20pattern)

單例模式（singleton，白話說就是「某個東西全系統只准有一個，誰要都用同一個」）是 [設計模式] 中最著名也最具爭議的創建型模式。它把類別的建構權收歸己有：外部不能自行 `new`，只能透過統一的取用方法拿到那唯一一份實例。

單例要解決的問題很真實：組態管理員、資料庫連線池、記錄器這類物件，建立成本高或語意上必須唯一，若到處各自建立，不只浪費資源，還可能因為各自持有狀態而互相矛盾。單例把「唯一性」寫進程式碼，讓編譯器幫忙執行這條規則。

## 典型實作

```python
class Config:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance.data = {}
        return cls._instance

a = Config()
b = Config()
assert a is b  # 兩次取得是同一份
```

三個要點：建構子受控（`__new__` 攔截）、全域取用點（單一進入方法）、延遲建立（第一次取用才生成）。多執行緒環境還必須處理競爭——兩個執行緒同時通過 `if` 檢查會造出兩份實例，所以需要鎖或其他保證。

## 範例

某電商系統的折扣規則組態原本由各模組自行讀檔：

- 問題：五個模組各自載入 `rules.json`，改檔後有的模組用新規則、有的用舊規則，大促期間出現「同一筆訂單兩種折扣」的事故。
- 改法：抽出 `Config` 單例，統一載入與熱更新，各模組一律 `Config()` 取用。
- 結果：組態來源唯一，事故歸零；代價是所有模組都依賴 `Config` 這個具體類別。

## 為何被稱為「最被濫用的模式」

1. **藏起依賴**：單例是隱性全域變數，讀程式碼時看不出函式依賴它，測試時也難以替換。
2. **妨礙測試**：單例狀態在測試之間殘留，必須手動重置，容易造成「單獨跑會過、一起跑就掛」的 [單元測試] 失敗。
3. **攜帶語意錯誤**：「只要一個」常常只是「現在只要一個」，未來要第二個（例如多租戶）時，所有呼叫點都要改。

正因如此，依賴注入容器成為主流替代：由容器統一管理「只有一份」的事實，類別本身保持可注入、可替換。單例並未消失，而是**從手寫模式退到框架機制**裡。

## 前因後果

單例隨 GoF（Gang of Four，四人幫）在 [1994年] 出版的模式目錄廣為人知，是書中 23 個模式之一。它源自物件導向之前就存在的全域變數需求，用 [物件導向] 的封裝把全域狀態包裝起來。

1990 年代末單例被大量使用，隨後十年間測試文化興起，社群逐漸把它列為「知道但不輕用」的模式。2010 年代依賴注入與框架級生命週期管理普及，多數語言生態提供了宣告式的「單例作用域」，手寫單例的場景大減。它的演變史正是 [設計模式] 觀念本身演變的縮影：**從手動套模式，到讓框架承擔模式**。

## 與相鄰分類的關聯

- 隸屬 [設計模式] 的創建型分支，與 [工廠] 同屬「控制物件建立」的問題域；工廠管「怎麼造」，單例管「造幾份」。
- 與 [物件導向] 的關係：單例依靠封裝與私有建構子，是語言特性的直接應用。
- 與 [品質確保] 的關係：單例的全域狀態是 [單元測試] 隔離性的最大障礙之一。
- 與 [維護與演進] 的關係：隱性依賴會累積成 [技術債]，重構時常需把單例改回注入參數。

## 容易混淆之處

- **單例不等於靜態類別**：靜態類別無法多型、無法延遲初始化實例狀態；單例仍是一般物件。
- **「只有一個」要問範圍**：每個程序一個？每個執行緒一個？每個租戶一個？沒講範圍的單例需求都是半成品。
- **延遲建立不是單例的本質**：是否延遲是取捨，不是定義。
- **方便不等於合理**：因為「呼叫方便」而用單例，是用全域狀態交換短期效率。

## 技術要點

1. 多執行緒下必須保證建立安全（鎖、雙重檢查或語言級特性）。
2. 提供**測試重置點**（如 `reset()`）或改用注入，否則測試互相污染。
3. 序列化與反射可能破壞唯一性，語言相關時要額外防護。
4. 單例持有**可變狀態**越少越好，唯讀組態是最佳使用場景。
5. 新專案優先考慮依賴注入容器提供的單例作用域，而非手寫。

## 常見的論爭

1. **單例是不是反模式**：一派認為其本質就是美化過的全域變數；另一派認為在組態、日誌這類天然唯一場景它最直接。主流立場是「可用但別擴散」。
2. **與依賴注入孰優**：注入需要容器與設計紀律，單例零成本；小工具與大型系統的答案往往不同。
3. **語言機制該不該內建**：Kotlin `object`、Python 模組本身即是單例，說明某些場景由語言直接承擔更乾淨。
