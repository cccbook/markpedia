# 回滾

> 隸屬：[維護與演進]　·　狀態：初稿

> 對應維基百科：[中文維基百科：回滚](https://zh.wikipedia.org/wiki/%E5%9B%9E%E6%BB%9A)　·　[English Wikipedia: Rollback (data management)](https://en.wikipedia.org/wiki/Rollback%20%28data%20management%29)

回滾（rollback，白話說就是「出事了就退回上一個正常狀態」）是 [維護與演進] 的安全機制：當新版本上線後出現問題，把系統狀態退回上一個已知正常的版本。它橫跨多個層面——**資料庫交易**可以回滾未確認的變更、**部署**可以回退到前一版構件、**資料與結構**（migration）可以回退到前一版 schema。

回滾的工程意義來自一個認知轉變：**上線後的問題不必靠「線上修」解決**。以前工程師在深夜的生產環境熱修，壓力大、容易錯上加錯；有了可靠的回滾，「先退回、白天再修」成為標準作業——把止血與治療分開，是可用性工程最重要的紀律之一。

回滾能力的設計必須發生在上線**之前**：能不能退、退了資料會怎樣、誰來決定退——這些問題的答案若等到事故當晚才找，通常已經太晚。因此回滾不是維運的事後技巧，而是與 [版本發布] 同步設計的發布屬性。

## 各層的回滾

1. **交易回滾**：資料庫的原子性保證——一組操作部分失敗時整組撤銷，資料回到交易前的狀態。
2. **部署回滾**：切回前一版構件。藍綠部署（兩套環境切換流量）與金絲雀發布把「退回」變成「把流量切回」，秒級完成。
3. **資料結構回滾**：migration 提供向上與向下腳本；向下腳本必須與向上腳本同樣受測試。
4. **功能開關回滾**：新功能以開關保護，出事直接關掉，不必重新部署。
5. **組態回滾**：設定檔與基礎設施宣告納入版本控制，可整體回退。
6. **快取與佇列**：回滾不只退程式——訊息佇列中的新格式訊息、快取中的新欄位資料，都是回退後舊版程式要面對的世界。

## 範例

某支付服務的回滾實務：

1. **事前**：每次發布附「回滾手冊」——觸發條件（錯誤率 > 1% 持續 5 分鐘）、負責人、回退指令、資料相容性備註。
2. **演練**：上線前在預備環境實際演練一次回滾，確認 `2.4 → 2.3` 的 migration 向下腳本能安全執行。
3. **事發**：`2.4.0` 上線 12 分鐘後，金絲雀分組的錯誤率升至 3.1%，主因是新欄位在舊批次工作失敗。
4. **止血**：觸發回滾——流量切回 `2.3.2`、新欄位寫入改為相容模式、監控確認錯誤率 3 分鐘內回落至 0.2%。全程 8 分鐘，無資料損失。
5. **治療**：隔日修復批次工作相容性，補上「新欄位對舊工作可見性」的 [整合測試]，再重新發布 `2.4.1`。

關鍵設計是**資料向前相容**：`2.4` 的 schema 改動讓舊版程式仍能讀寫，因此退回 `2.3` 不會壞掉資料。

事後檢討的兩個假設對照，最能說明事前準備的價值：若金絲雀流量是 25% 而非 5%，受影響的付款請求會多四倍；若回滾手冊沒有事先寫下「新欄位以相容模式寫入」這一步，團隊得在事故當晚現場判斷資料相容性，止血時間很可能從 8 分鐘變成一小時。

## 前因後果

回滾的觀念根基是資料庫交易的原子性，1970 年代起就是資料庫系統的核心保證。應用層面的回滾則長期闕如：早期軟體安裝後難以乾淨移除，「升級失敗」是常見事故。

2000 年代 [敏捷] 與 [持續整合] 使發布頻率提高，「一年發一次、失敗熬夜修」的模式失效，快速回滾成為必要能力。2010 年代 [DevOps] 把它制度化：不可回滾的發布不被允許；藍綠部署、金絲雀與功能開關成為標準配置；「回滾演練」進入發布檢查清單。回滾也因此從「災難應變」升級為**常態風險控制**——發布頻率越高，回滾反而越少被用到，因為每次發布的爆炸半徑都夠小。

## 與相鄰分類的關聯

- 隸屬 [維護與演進]，是 [版本發布] 計畫中成文的一部分：沒有回滾計畫的發布是不完整的發布。
- 與 [持續整合] 的關係：CI 產出的版本化構件是回滾的地圖；管線越標準，回退越機械化。
- 與 [版本控制] 的關係：回滾到某構件，等於回到對應 commit 的可重現狀態。
- 與 [品質確保] 的關係：[單元測試] 與 [整合測試] 降低「需要回滾」的機率，回滾則是測試漏網時的最後防線。
- 與 [持續整合] 的關係：構件化與版本標記讓「退回上一版」從考古題變成一條指令。

## 容易混淆之處

- **回滾不等於撤銷一切**：日誌、稽核紀錄與使用者產生的資料必須保留；回滾的是系統版本與行為，不是歷史。
- **回滾程式不等於回滾資料**：資料結構向下遷移常比向上遷移危險，最穩健的設計是讓資料向前相容、程式可退。
- **回滾不等於失敗**：它是計畫中的一步；把回滾視為丟臉，會誘使團隊「硬撐著修」，代價更大。
- **交易回滾不等於部署回滾**：前者由資料庫保證，後者需要部署系統與相容性設計配合。
- **演練過不等於上線可用**：預備環境的資料量、流量與組態都與生產不同，回滾手冊要標明這些假設。

## 技術要點

1. 每次發布**成文回滾手冊**：觸發條件、指令、負責人、資料相容性備註。
2. 資料結構改動遵守**向前相容**：先加後減、新舊版程式都能讀寫的雙寫期。
3. migration **向下腳本與向上腳本同等對待**：都要測試、都要演練。
4. 用**藍綠或金絲雀**讓回滾只是流量切換，秒級完成且可先小範圍驗證。
5. 高風險功能以**功能開關**保護，關閉即是零風險回滾。
6. 定期**演練**回滾；沒演練過的回滾計畫只是樂觀的想像。
7. 監控指標與回滾觸發條件**使用同一組定義**，避免「看的是不同儀表板」的判斷分歧。
8. 回滾後立即保留問題時刻的日誌與快照，供隔日分析，不因止血而破壞現場。

## 常見的論爭

1. **回滾還是向前修**：小事立刻回滾；但若新版本已產生舊版無法處理的資料，「向前修」成了唯一選項。判準在於資料相容性，這也印證事前設計的重要性。
2. **回滾該多自動**：指標觸發自動回滾最快，但誤判會造成振盪（來回切換）；多數團隊對自動回滾設保守門檻，並要求人工確認關鍵系統。
3. **要不要保留「回到兩版以前」的能力**：理論上越遠越安全，實務上資料相容鏈越長越脆弱；常見折衷是保證「上一版可回滾、更舊版本只保證可重現」。
4. **回滾經驗要不要公開**：把每次回滾寫成事故報告供全員閱讀，會短期揭露問題、長期降低同類事故；反對者擔心報告淪為問責素材，關鍵在組織是否建立「對事不對人」的文化。
