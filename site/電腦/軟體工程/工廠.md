# 工廠

> 隸屬：[設計模式]　·　狀態：初稿

> 對應維基百科：[English Wikipedia: Factory method pattern](https://en.wikipedia.org/wiki/Factory%20method%20pattern)

工廠模式（factory，白話說就是「把 `new` 收進一個專門的生成點，要用時跟工廠要，不要自己造」）是 [設計模式] 中的創建型模式家族，包含簡單工廠、工廠方法（factory method）與抽象工廠（abstract factory）三個層次。共同目標只有一個：**讓呼叫方依賴「想要什麼」，不依賴「怎麼造出來」**。

直接 `new` 的問題在於把兩件事綁死了：使用物件的人必須知道具體類別名稱、建構參數與相依子物件。一旦建立流程改變（例如要連資料庫、要註冊到登記簿、要按組態選型別），所有 `new` 的地方都要改。工廠把這些知識集中到一處，用一個介面對外供貨。

## 典型實作

```python
from abc import ABC, abstractmethod

class Parser(ABC):
    @abstractmethod
    def parse(self, text: str) -> dict: ...

class JsonParser(Parser):
    def parse(self, text): return {"kind": "json", "value": __import__("json").loads(text)}

class CsvParser(Parser):
    def parse(self, text):
        rows = [line.split(",") for line in text.strip().splitlines()]
        return {"kind": "csv", "value": rows}

def parser_factory(fmt: str) -> Parser:   # 工廠方法
    return {"json": JsonParser, "csv": CsvParser}[fmt]()

p = parser_factory("csv")
print(p.parse("a,b\n1,2"))  # {'kind': 'csv', 'value': [['a', 'b'], ['1', '2']]}
```

## 三個層次

1. **簡單工廠**：一個函式按參數回傳不同實例（如上例）。嚴格說不是 GoF 模式，卻是實務中最常見的形態。
2. **工廠方法**：把「造什麼」下放給子類別決定——父類別定義建立流程骨架，子類別只填 `create()` 一格。
3. **抽象工廠**：一次生成**一族**相關物件（如「Mac 風 UI 元件組」整組按鈕、選單、視窗），保證族內相容。

層次越高，彈性越大、樣板越多。選擇的準則是：只有一個變動軸用工廠方法，多個相關變動軸才上抽象工廠。

## 範例

某報表系統要支援三種輸出（PDF、Excel、HTML），並依使用者權限與訂閱等級決定可用格式：

- 第一版：每個報表功能裡 `if fmt == "pdf": ... elif ...`，共 14 處分支；新增「Markdown 匯出」時漏改 2 處，同一報表兩種入口行為不一致。
- 重構：定義 `Exporter` 介面與三個實作，`exporter_factory(fmt, tier)` 集中處理權限檢查與格式選擇；14 處呼叫改為向工廠要實例。
- 結果：新增格式只改工廠一處；「免費版不能出 PDF」的規則從散落各處收斂為工廠內一行檢查。

這個例子的重點不只是集中 `new`，而是**建立時的跨切面規則**（權限、登記、組態）終於有了單一落點。

## 前因後果

建立型模式的思想在 1980 年代的框架設計中成熟——框架無法預知應用程式要造什麼類別，只能提供「由應用決定」的建立掛勾。GoF 在 [1994年] 將工廠方法與抽象工廠收錄為 23 個模式中的兩個創建型代表。

1990 年代末至 2000 年代，依賴注入容器把工廠的角色一般化：物件圖的組裝集中交給容器，應用程式碼幾乎不再出現 `new`。與此同時，測試需求（把真實物件換成替身）成為工廠/注入普及的最大推手——[單元測試] 若能控制建立點，就能注入假的相依物件。今日多數語言生態的框架都內建了這種機制，手寫工廠集中在「建立流程本身有業務規則」的場景。

## 容易混淆之處

- **工廠方法不等於簡單工廠**：前者用繼承把「造什麼」下放子類別，後者只是一個選擇函式；混稱常見但設計含義不同。
- **抽象工廠不等於工廠的工廠**：它的重點是「一族相容物件」，不是巢狀呼叫。
- **工廠不是免`new`魔咒**：建立流程簡單且穩定時直接 `new` 更清楚，硬包一層只是加碼。
- **回傳介面是重點**：回傳具體類別的工廠只搬移了 `new`，沒有解耦。

## 技術要點

1. 工廠回傳**抽象型別**，把具體類別封鎖在工廠模組內。
2. 建立過程中的**跨切面規則**（權限、登記、驗證）集中寫在工廠，避免散落。
3. 選擇邏輯用對照表而非長串 if-else，新增型別只加一行。
4. 需要一族相容物件時才用抽象工廠，單一變動軸用工廠方法即可。
5. 測試時允許**替換工廠或注入替身**，否則工廠反而變成測試障礙。

## 常見的論爭

1. **手寫工廠還是依賴注入容器**：容器統一管理物件圖但增加框架依賴；小專案手寫工廠更直白。爭點是物件複雜度是否已到需要容器的程度。
2. **簡單工廠算不算模式**：學院派說不是 GoF 模式；工程派說它是最高頻的實際形態，名字不重要。
3. **靜態工廠方法好不好**：Java 等語言中靜態工廠（如 `List.of()`）好用但不可替換、不利測試；標準庫與應用程式碼的答案不同。
