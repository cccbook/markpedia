# 單元測試

> 隸屬：[品質確保]　·　狀態：初稿

> 對應維基百科：[中文維基百科：单元测试](https://zh.wikipedia.org/wiki/%E5%8D%95%E5%85%83%E6%B5%8B%E8%AF%95)　·　[English Wikipedia: Unit testing](https://en.wikipedia.org/wiki/Unit%20testing)

單元測試（unit test，白話說就是「把程式切到最小可測塊，一塊一塊單獨驗證」）是 [品質確保] 中粒度最細的自動化測試：針對單一函式、方法或類別，餵入已知輸入、斷言輸出與副作用。單元是「最小可獨立執行的測試單位」，關鍵在**隔離**——被測單元外部的檔案、網路、資料庫與時鐘都要替換掉，讓測試只驗證這一塊的邏輯。

單元測試的價值不在「抓 bug」的當下，而在**未來**：它是一份可執行、永遠不會過期的行為規格。任何人之後改動程式，跑一遍測試就知道有沒有踩壞既有行為。沒有單元測試的程式碼庫，每一次修改都是盲改。

## 典型結構

```python
def discount(price: int, vip: bool) -> int:
    return int(price * 0.8) if vip else price

def test_vip_gets_20_percent_off():
    assert discount(100, vip=True) == 80

def test_non_vip_full_price():
    assert discount(100, vip=False) == 100

def test_discount_is_integer():
    assert discount(99, vip=True) == 79  # int() 截斷而非四捨五入
```

每個測試遵循 **Arrange–Act–Assert** 三段：準備（建好輸入與替身）、執行（呼叫被測單元一次）、驗證（斷言結果）。一個測試只驗證一件事，失敗時訊息才能直接指向問題。

## 範例

某金流團隊對「手續費計算」模組建立單元測試：

1. **清點行為**：三種卡片、兩種幣別、金額上下限、取整規則，共 14 條獨立行為。
2. **對映測試**：14 個測試函式，各驗證一條行為；外部匯率服務以替身（stub）固定匯率，時鐘以注入的假時鐘固定。
3. **覆蓋率**：行覆蓋率 100%，分支覆蓋率 96%（未覆蓋的是「不可能發生」的防禦分支，明確標註理由）。
4. **成效**：半年後改動取整規則（四捨五入取代截斷），3 個測試立即變紅，精準指出 3 處受影響行為；在沒有測試的舊專案裡，同類改動曾引發上線後才發現的計費差錯。
5. **教訓**：覆蓋率是下限指標不是目標——為了拉數字寫的「呼叫一下就過」測試抓不到任何回歸。

## 前因後果

單元測試的實踐早於工具：1960 至 1970 年代工程師就在 REPL 與測試驅動程式裡手動驗證小單元。1997 年，Kent Beck 與 Erich Gamma 把 SUnit 的理念移植為 Java 的 JUnit，連同 [敏捷] 運動掀起「程式設計師測試」的普及——測試從 QA 部門的專職，變成開發者的日常。

2000 年代初 [測試驅動]（TDD）把順序反轉：先寫失敗的測試，再寫剛好通過的實作。TDD 的支持者強調它強迫設計出可測（也就鬆耦合）的介面；反對者指出前後端驗證與探索性程式碼不適合硬套。2010 年代之後，單元測試與 [持續整合] 結合成標準配置：每次提交自動執行全部測試，紅燈即禁止合併。測試金字塔則把定位講清楚——單元測試數量最多、速度最快，往上才是 [整合測試] 與端對端測試。

## 與相鄰分類的關聯

- 隸屬 [品質確保]，是 [測試驅動] 與 [持續整合] 的基礎建材。
- 與 [驗證] 的關係：規格的驗收條件應能在單元層對映出測試案例。
- 與 [設計模式] 的關係：可測性驅動設計——[工廠] 與依賴注入讓替身可以插入，[單例] 與全域狀態則是測試的頭號障礙。
- 與 [維護與演進] 的關係：測試是 [重構] 的安全網，也是 [回滾] 判斷「壞掉」的依據。

## 容易混淆之處

- **單元測試不等於什麼都能測**：跨資料庫、跨服務的行為屬於 [整合測試]；硬用替身模擬整個外部世界只會測到自己的假設。
- **測試不是實作鏡像**：斷言「內部陣列排序兩次」這類實作細節，重構時全部誤報；要測的是可觀察行為。
- **覆蓋率不等於品質**：100% 覆蓋但零斷言的測試毫無價值；覆蓋率用來找漏網之魚，不用來當 KPI。
- **替身不等於造假**：stub 回固定值、mock 驗證互動；濫用 mock 會讓測試與實作黏死。

## 技術要點

1. 一個測試一件事，命名直接說出行為（`vip_gets_20_percent_off`）。
2. 用**建構器或 fixture** 收斂重複準備碼，但保持每個測試自明。
3. 外部相依一律注入（時間、亂數、網路），讓測試**可重現、可平行**。
4. 失敗訊息要能定位：斷言寫出期望值與實際值，避免「AssertionError」裸奔。
5. 與 [持續整合] 綁定：全量單元測試應在數分鐘內跑完。
6. 修 bug 先寫重現該 bug 的測試，再修程式——測試順便成為回歸防線。

## 常見的論爭

1. **TDD 是否處處適用**：支持者視之為設計方法；反對者指出 UI、探索性原型與第三方整合用 TDD 成本過高。主流立場是按風險與穩定度選用。
2. **mock 該用多少**：倫敦學派重隔離、大量 mock；底特律學派重狀態驗證、少 mock。爭點實質是「單元」該切多小。
3. **要不要訂覆蓋率門檻**：門檻防止測試裸奔，但也會誘發刷數字；較穩健的作法是「新程式碼覆蓋率不下降」的棘輪原則。
