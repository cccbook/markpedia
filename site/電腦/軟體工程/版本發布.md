# 版本發布

> 隸屬：[維護與演進]　·　狀態：初稿

> 對應維基百科：[中文維基百科：軟件版本編號](https://zh.wikipedia.org/wiki/%E8%BB%9F%E4%BB%B6%E7%89%88%E6%9C%AC%E7%B7%A8%E8%99%9F)　·　[English Wikipedia: Software release life cycle](https://en.wikipedia.org/wiki/Software%20release%20life%20cycle)

版本發布（release，白話說就是「把開發到某個狀態的軟體打包、編號、交給使用者」）是 [維護與演進] 中把「做好的東西」變成「用得到的東西」的活動。它包含兩件事：**編號**（這一版和上一版差在哪，如何命名）與**流程**（從候選到正式上線要經過什麼檢查與發布階段）。

版本發布之所以需要工程方法，是因為它是**承諾的時刻**：使用者開始依賴這一版的行為，API 的參數、資料格式、設定檔都從此成為契約。隨意發布等於隨意改契約，下場是使用者的自動化流程悄悄壞掉、支援成本暴增。

## 版本編號與發布階段

- **語意化版本（SemVer）**：`主.次.修訂` 三段編號——主版升級代表**不相容**的介面變更，次版代表向下相容的新功能，修訂代表修 bug。2010 年代起成為開源生態的共同語言。
- **發布階段**：alpha（內部測試）→ beta（對外預覽、介面可能變）→ release candidate（候選，僅修致命問題）→ stable／GA（正式版）。
- **長期支援版（LTS）**：承諾數年的安全更新，供無法頻繁升級的使用者。
- **發布軌道**：nightly、canary、beta、stable 並行，讓新變更先被小眾使用者試煉。
- **變更紀錄（changelog）**：以使用者語言寫下每版改了什麼，是發布與溝通的交界。

## 範例

某 API 服務的發布實務：

1. **編號**：採 SemVer。`2.3.1 → 2.3.2` 修時區計算錯誤；`2.3 → 2.4` 新增批次查詢端點；`2 → 3` 移除舊版認證方式（不相容），提前六個月公告。
2. **候選流程**：功能凍結後切 `release/2.4` 分支，只允許修 bug；連續一週在預備環境穩定後標記 `2.4.0-rc.1`。
3. **發布檢查清單**：[持續整合] 全綠、資料庫遷移已演練、公告文件完成、[回滾] 步驟與判斷標準成文。
4. **漸進上線**：新版本先導 5% 流量，觀察錯誤率 24 小時，無異常再 50%、100%。
5. **事後**：發布時間、內容與問題記入發布日誌，成為下版排程依據。
6. **棄用週期**：`2.4` 同時公告 `2.2` 進入維護期、`2.1` 停止支援，讓依賴方的升級路徑永遠清楚。

這個流程的關鍵是**每一步都有得退**：rc 可棄、漸進可停、上線可回滾。

對內部使用者（其他團隊、其他服務）的發布也適用同樣紀律：內部函式庫的每一次版本升級都是一次介面變更，誰依賴你、你破壞了誰，都該在發布前有答案。內部介面的任意變更正是「微服務之間互相踩腳」的主要來源。

檢查清單中最容易被省略的是回滾步驟——它看起來是悲觀的儀式，卻是事故之夜唯一能照著執行的東西。壓力下的記憶不可靠，成文的步驟才是工程；這也是為什麼成熟團隊把「回滾手冊是否更新」列為候選版本的硬性條件，而非建議事項。

## 前因後果

1980 至 1990 年代軟體以實體媒介發行，版本週期以年計，「大版本、小版本」的命名直接對應磁片與手冊的批次。網際網路普及後，下載與自動更新把發布成本降為近零，版本週期縮短到月與週。

[敏捷] 方法與 [持續整合] 把「可發布」變成常態：每個構建都通過測試，發布從大事件變成按下按鈕。2010 年前後語意化版本標準化介面變更的溝通方式，解決了依賴管理工具爆炸後「裝了新版就壞」的亂象；持續交付更進一步主張**隨時可發布、發布與功能開關解耦**——新碼先上線但對使用者隱藏，開關打開才算功能發布。發布因此從「版本事件」演化為「流量與風險的漸進控制」。

## 與相鄰分類的關聯

- 隸屬 [維護與演進]，上游由 [持續整合] 供應已驗證的構件，下游交付給 [DevOps] 的部署與維運。
- 與 [版本控制] 的關係：發布對應特定標籤（tag）與分支策略，tag 讓任一歷史版本可精確重建。
- 與 [回滾] 的關係：每次發布必須附帶成文的回滾條件與步驟，否則不算發布完成。
- 與 [持續整合] 的關係：管線產生的構件編號與發布版本一脈相承，從提交到上線全程可追溯。
- 與 [需求工程] 的關係：發布範圍即承諾範圍，收尾階段的需求取捨直接決定使用者觀感。
- 與 [品質確保] 的關係：發布前的測試與審查構成「可發布」的證據鏈，缺一段承諾就變成賭注。

## 容易混淆之處

- **版本號不等於品質**：編號只溝通「變更的性質與相容性」，不保證穩定。
- **發布不等於部署**：部署是把構件放到環境，發布是讓使用者實際用到；持續交付把它們解耦。
- **LTS 不等於免升級**：LTS 承諾的是安全與修補，新功能仍需大版本升級。
- **beta 不等於免責聲明**：對外 beta 同樣累積依賴，貿然改介面的代價與正式版相同。
- **上線不等於發布完成**：公告、文件與支援準備缺一，使用者拿到的只是一個陌生的構件。

## 技術要點

1. 採用**語意化版本**並成文公告：什麼算不相容、什麼算修訂，團隊內先講清楚。
2. **功能開關**分離部署與發布：未完成功能不出現在 release 分支，或上線但隱藏。
3. 發布分支**只修不增**，避免候選版本一直延期。
4. 每次發布產出**三件套**：變更紀錄（changelog）、已知問題、回滾步驟。
5. 用**漸進發布**（金絲雀、百分比分流）控制爆炸半徑，監控指標先行。
6. 保留**可重建性**：任何歷史版本都能從 tag 與鎖定的相依完整重現。
7. 對外公告與對內紀錄**分開維護**：changelog 面向使用者，發布日誌面向團隊，內容與受眾都不同。
8. 棄用（deprecation）先公告、後移除：介面先標記棄用並保留至少一個次版週期，讓依賴方有時間遷移。

## 常見的論爭

1. **大版本發布還是持續發布**：大版本便於行銷與文件，但累積風險；持續發布風險小，但使用者難以跟上。多數產品採「持續部署＋定期對外大版本公告」。
2. **SemVer 是否務實**：批評者指出「什麼算不相容」在實務常有灰色地帶（修 bug 也可能破壞依賴方）；支持者認為標準的價值在於強迫團隊面對相容性問題。
3. **要不要支援舊版多久**：支援越久維護成本越高，棄之則強迫使用者升級；常見解法是明確公告的生命週期表（如 LTS 三年）。
4. **版本號要不要標預覽後綴**：`2.4.0-rc.1`、`2.4.0-beta.2` 這類後綴讓依賴工具能識別不穩定版，但增加解析複雜度；發布函式庫的專案幾乎都值得採用。
