# 觀察者

> 隸屬：[設計模式]　·　狀態：初稿

> 對應維基百科：[English Wikipedia: Observer pattern](https://en.wikipedia.org/wiki/Observer%20pattern)

觀察者模式（observer，白話說就是「訂閱—通知」：有人狀態一變，所有訂閱的人自動收到通知）是 [設計模式] 中的行為型模式。它定義一對多的依賴：主體（subject）維護一份觀察者名單，狀態改變時逐一呼叫它們的更新方法；觀察者之間互不認識。

觀察者要解決的是**耦合方向**的問題。若「狀態改變的人」必須知道「誰在乎這個改變」，每次新增關注者都要改主體程式碼，主體會被拉進所有人的業務裡。觀察者把方向倒過來：關注者自己來註冊，主體只認得一個抽象介面，完全不關心來了誰、走了誰。

## 典型實作

```python
class Subject:
    def __init__(self):
        self._observers = []

    def attach(self, observer):
        self._observers.append(observer)

    def detach(self, observer):
        self._observers.remove(observer)

    def notify(self, event):
        for observer in list(self._observers):
            observer.update(event)

class MailNotifier:
    def update(self, event):
        print(f"寄信通知：{event}")

order = Subject()
order.attach(MailNotifier())
order.notify("訂單 #1024 已付款")  # 觸發所有訂閱者
```

## 範例

某電商平台「訂單付款成功」的後續動作不斷增加：

- 起初：付款模組直接呼叫「寄確認信」函式，兩行搞定。
- 三個月後：加了會員積分、庫存扣減、簡訊通知，付款模組裡塞了四段與付款無關的呼叫，任何一段出錯都拖垮付款。
- 改法：付款完成只發出一個 `OrderPaid` 事件，信件、積分、庫存、簡訊各自註冊為觀察者，各自吞下與重試自己的錯誤。
- 結果：付款模組不再因新增功能而改動；積分系統故障時付款依然可用。

這個例子的核心收益是**新增動作不必修改付款程式**——這正是開閉原則的具體化。

## 與事件驅動架構的關係

觀察者是許多大概念的種子：

- **GUI 框架**的事件監聽（按鈕的 click handler）就是觀察者的直接應用，源自 Smalltalk-80 的 MVC。
- **訊息佇列與發布—訂閱**系統把同一思想放大到跨程序、跨機器：訊息中間商扮演主體，消費者扮演觀察者。
- **反應式程式設計**把「訂閱資料流」一般化，對連續變化的值做組合與過濾。

規模越大，觀察者的弱點越明顯：**通知順序、失敗處理與除錯難度**。同步呼叫的觀察者一個拋例外會打斷整條通知鏈；跨程序的發布—訂閱則要處理重複送達與順序保證。因此實務上常見的折衷是：程序內用觀察者，跨程序用帶有投遞保證的訊息系統。

## 前因後果

觀察者的思想隨 Smalltalk 的模型—視圖—控制器（MVC）在 1970 年代末成形：模型變動時通知視圖更新。GoF 在 [1994年] 把它正式收錄為 23 個模式之一。1990 至 2000 年代它成為 GUI 與桌面框架的標準配備。

2010 年代之後，微服務與事件驅動架構把觀察者的「進程內通知」升級為「跨服務事件」，同一模式承擔了系統間整合的重任。與此同時，它的管理成本（事件蔓延、難以追蹤誰訂閱了什麼）也催生了事件溯源、schema 登記等配套做法。觀察者因此是少數**從桌面時代一路用到雲端時代**而結構未變的模式。

## 與相鄰分類的關聯

- 隸屬 [設計模式] 的行為型分支，與 [策略] 同屬「用介面隔離變動」：策略替換演算法，觀察者廣播事件。
- 與 [軟體開發流程] 的關係：辨識事件（名詞＋過去式的狀態變化）常來自 [需求擷取] 階段對「之後要發生什麼」的追問。
- 與 [品質確保] 的關係：事件鏈的測試需要替身與捕獲機制，[單元測試] 時常用假的觀察者驗證通知是否發出。
- 與 [維護與演進] 的關係：訂閱關係若不集中管理，事件流向會成為難解的隱性知識。

## 容易混淆之處

- **觀察者不等於發布—訂閱**：前者主體與觀察者在同一程序且直接互動；後者多了訊息中間商，兩者解耦程度不同。
- **通知不等於保證送達**：同步觀察者沒有投遞保證，需要保證時要另外設計。
- **事件不等於命令**：`OrderPaid` 是「已發生的事實」，不指揮任何人做什麼；把它寫成「去扣庫存」就失去了解耦。
- **多一層間接不是免費的**：除錯時要跨訂閱關係追流程，小系統硬套反而更難讀。

## 技術要點

1. 觀察者清單的**增刪要在遍歷時安全**（快照或寫時複製），避免邊通知邊訂閱的例外。
2. 定義**通知內容的最小介面**：事件物件勝過一長串參數，日後加欄位不破壞簽名。
3. 明確**同步或非同步**：同步即時但相互拖累，非同步隔離故障但需處理順序與重試。
4. 設計**取消訂閱**機制，防止觀察者被主體永久持有造成洩漏。
5. 建立**事件清單文件**：哪些事件、誰發、誰訂，是維護事件系統的基本地圖。

## 常見的論爭

1. **事件要不要集中註冊**：集中可一目了然但重回中心化；各自註冊更解耦卻難追蹤。折衷是程式碼各自註冊、文件集中。
2. **同步鏈中觀察者出錯誰負責**：主體吞掉所有例外隔離故障，但會掩蓋問題；讓例外上浮則一顆老鼠屎壞一鍋粥。多數框架選擇「各自隔離＋記錄」。
3. **要不要上訊息佇列**：小系統用佇列是殺雞用牛刀；跨服務還用程序內觀察者則是埋雷。分界在於是否跨程序與需要幾個九的可靠度。
