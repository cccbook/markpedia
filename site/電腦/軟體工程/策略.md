# 策略

> 隸屬：[設計模式]　·　狀態：初稿

> 對應維基百科：[中文維基百科：策略模式](https://zh.wikipedia.org/wiki/%E7%AD%96%E7%95%A5%E6%A8%A1%E5%BC%8F)　·　[English Wikipedia: Strategy pattern](https://en.wikipedia.org/wiki/Strategy%20pattern)

策略模式（strategy，白話說就是「同一件事有好幾種做法，把每種做法包起來，用的時候挑一個」）是 [設計模式] 中的行為型模式。它把一組可互換的演算法各自封裝成獨立物件，共用同一介面，讓呼叫方可以在**執行期替換做法**，而不必修改自己的程式碼。

策略要解決的是「到處 if-else」的蔓延問題。當計價、排序、壓縮、路徑規劃這類邏輯隨業務演化出越來越多分支，條件判斷會滲透到各處，任何新增做法都要動多個地方。策略把分支收斂成**選擇**：新增一種做法只是新增一個類別，原有程式一行不改。

## 典型實作

```python
from abc import ABC, abstractmethod

class Shipping(ABC):
    @abstractmethod
    def fee(self, weight_kg: float) -> float: ...

class Standard(Shipping):
    def fee(self, weight_kg):
        return 60 + weight_kg * 10

class Express(Shipping):
    def fee(self, weight_kg):
        return 120 + weight_kg * 25

class Cart:
    def __init__(self, shipping: Shipping):
        self.shipping = shipping        # 注入策略

    def shipping_fee(self, weight_kg):
        return self.shipping.fee(weight_kg)

print(Cart(Standard()).shipping_fee(2.0))   # 80
print(Cart(Express()).shipping_fee(2.0))    # 170
```

## 範例

某物流系統的運費計算演變：

- 第一版：`if mode == "standard": ... elif mode == "express": ...`，兩個分支。
- 半年後：新增「離島加價」「低溫配送」「節日折扣」，同一函式膨脹到 180 行、7 層分支，改折扣卻誤傷低溫邏輯的事故發生兩次。
- 重構：抽 `Shipping` 介面，每種計費一個類別，折扣用**裝飾策略**疊在基本運費外層；`Cart` 只認介面。
- 結果：新增計費方式從「動核心 180 行」變成「新增 1 個檔案＋1 條測試」。

這個例子顯示策略的判準：**分支不是問題，跨分支的修改互相干擾才是**。只有兩三個穩定分支時，if-else 反而更簡單。

## 與函式和語言特性的關係

在有一級函式的語言中，策略常被簡化為**傳函式**：`Cart(shipping_fee=express_fee)`。GoF 時代需要完整類別階層，是因為當年的主流語言（C++、Java 早期）函式不能獨立傳遞。今日 Python、JavaScript、Kotlin 等語言裡，「策略模式」多半以 lambda 或函式引用的形態存在，樣板程式碼大減。

這也解釋了策略模式的定位爭議：它的**思想**（把變動的演算法隔離成可替換單元）是永恆的，它的**形態**（類別圖）則依附於語言能力。學這個模式學的是辨識「哪裡在變動」，而不是背類別圖。

## 前因後果

策略隨 GoF 在 [1994年] 的模式目錄正式命名，其前身是 1980 年代在圖形系統與排序程式庫中的「可替換演算法」慣用法。1990 至 2000 年代它與 [工廠]、依賴注入一起構成物件導向設計的主流手法，泛型與介面語法的普及進一步降低了實作成本。

2010 年代之後，函式式風格回歸主流，策略多以函式值傳遞；規則引擎與政策即程式碼（policy as code）則把「策略」提升到組態層——不重編譯就能換規則。模式因此完成了從「設計圖」到「常識」的沉澱。

## 容易混淆之處

- **策略不等於狀態**：策略由呼叫方挑選且互不知情；狀態模式由物件自己隨內部狀態切換行為。
- **策略不等於簡單的參數**：傳一個數字（折扣率）不算策略；傳一段可變的計算邏輯才是。
- **介面最小原則**：策略介面應只包含替換所需的操作，塞太多方法會讓新策略難以實作。
- **模式不是目的**：三個穩定分支硬抽成三個類別是過度設計。

## 技術要點

1. 先找**變動軸**：會隨時間增加選項的那個維度才值得抽策略。
2. 策略應**無狀態或明確宣告狀態**，共用時才安全。
3. 選擇邏輯集中在一處（組態、工廠或注入設定），不要散落各呼叫點。
4. 每個策略獨立測試，另加一條「選擇正確策略」的整合測試。
5. 語言支援一級函式時，優先用函式值；類別只在需要狀態或介面契約時使用。

## 常見的論爭

1. **類別策略還是函式策略**：類別版有契約與工具支援，函式版輕巧；爭點在策略是否需要多方法契約與可命名性。
2. **if-else 什麼時候該重構成策略**：常見判準是「分支數將繼續成長」或「不同分支由不同人維護」，分支固定且短則不動。
3. **要不要做成組態可換**：讓使用者免改程式即可換策略很誘人，但組態介面也是契約，會限制未來演化。
