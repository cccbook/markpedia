# 重構

> 隸屬：[維護與演進]　·　狀態：初稿

> 對應維基百科：[中文維基百科：重构](https://zh.wikipedia.org/wiki/%E9%87%8D%E6%9E%84)　·　[English Wikipedia: Code refactoring](https://en.wikipedia.org/wiki/Code%20refactoring)

重構（refactoring，白話說就是「程式的行為一點都不變，只把內部結構改得更好懂、更好改」）是 [維護與演進] 的核心技術。它與加功能、修 bug 並列為第三種改程式的方式：**不對外承諾任何新行為，只改善內部品質**。定義中的「行為不變」是硬性條件——如果對外行為變了，那不是重構，是修改。

重構要解決的是結構的**衰變**。程式碼每次修改都傾向於變亂：條件堆疊、職責黏連、命名失真。短期沒人付錢整理它，長期它卻決定一切改動的速度。重構的價值主張是：**花小錢維持改動成本低，勝過日後每個功能都加倍昂貴**。

## 常見重構手法

1. **擷取函式（extract function）**：把一段邏輯抽成命名函式，用名字代替註解。
2. **重新命名（rename）**：讓名稱說出意圖，是最便宜也最高效的重構。
3. **移動函式／欄位**：把資料與操作它的行為放回同一處，消解錯置的職責。
4. **以多型取代條件式**：長串 if-else 改為 [策略] 或查表，隔離變動軸。
5. **拆分類別**：一個類別管太多事時，按職責拆開。
6. **以查詢取代暫存變數**：減少中間狀態，降低理解負擔。

## 範例

把下列黏在一起的手續費邏輯整理成可擴充結構：

```python
# 重構前
def fee(amount, card):
    if card == "visa":
        return amount * 0.02 + 5
    elif card == "master":
        return amount * 0.018 + 5
    else:
        return amount * 0.03

# 重構後（行為不變，結構可擴充）
RATES = {"visa": 0.02, "master": 0.018, "default": 0.03}

def fee(amount, card):
    rate = RATES.get(card, RATES["default"])
    return amount * rate + 5
```

過程的三步紀律：先確認 `fee` 有覆蓋三種卡別的 [單元測試]；進行改寫；跑測試確認全綠。新增「聯名卡」時，重構前的版本要動 if-else 鏈，重構後只加一列對照表——**這就是重構買到的未來改動速度**。

## 前因後果

重構作為實踐存在已久，但直到 1990 年代才被系統化：Ralph Johnson 等人研究 Smalltalk 社群的整理慣用法；Martin Fowler 於 [1999年] 出版《重構》，命名並目錄化了 70 餘種手法，確立「小步、有測試保護、行為不變」的三原則。2000 年代 [敏捷] 把重構寫進日常節奏——「持續把系統設計保持乾淨」取代「預先完美設計」。

工具的演進同樣關鍵：IDE 內建安全的重新命名與擷取函式，把手工易錯的編輯變成一鍵操作；[持續整合] 則讓「每次重構都全量跑測試」成為習慣。2010 年代之後，微服務拆分、模組化改造與技術債償還都以重構為基本技術，重構從個人技藝升級為**組織的持續活動**。

## 與相鄰分類的關聯

- 隸屬 [維護與演進]，是償還 [技術債] 的主要手段，也是 [設計模式] 的應用現場——模式常是重構的**目標形狀**。
- 與 [品質確保] 的關係：測試是重構的安全網，[單元測試] 不足時的第一件事常是補測試而非動結構。
- 與 [軟體開發流程] 的關係：流程必須替重構保留容量，否則它永遠排在「下一個功能」之後。
- 與 [版本控制] 的關係：重構與功能變更**分開提交**，讓審查者能分別檢視「行為變了沒」與「結構變了沒」。

## 容易混淆之處

- **重構不等於重寫**：重寫拋棄既有行為累積，風險高得多；重構在既有行為保護下漸進改造。
- **重構不等於效能優化**：目標不同——重構求可讀可改，最佳化求速度；有時還互相衝突。
- **重構不等於加功能順手改**：混在同一提交裡，審查無法判斷行為變化從何而來。
- **行為不變需要證據**：靠測試與回歸驗證，不是靠「我很小心」。

## 技術要點

1. **先有安全網**：目標區域沒有測試就先補測試；[持續整合] 管線必須在跑。
2. **小步前進**：每步只做一個手法，每步都跑測試，壞了立即回退一步。
3. **提交分離**：重構提交不含任何行為變更，方便 [程式碼審查] 與 [回滾]。
4. **對症下藥**：從「修改頻率×修改難度」高的地方開始，而非逐檔洗程式碼。
5. **善用工具**：優先使用 IDE 的結構化重構，避免手工編輯引入拼字與參照錯誤。
6. **留下痕跡**：大型重構在 PR 描述寫明動機與前後對照，累積團隊的共同記憶。

## 常見的論爭

1. **預先設計還是持續重構**：前者先畫好再寫；後者先簡單實作再讓設計隨理解浮現。主流折衷是「夠好的初版＋持續重構」。
2. **重構要不要佔 sprint 容量**：不佔則永遠沒空；佔太多則產品方反彈。實務多以固定比例（10–20%）加「趁修改時順手重構」組合。
3. **大規模重構值不值**：模組化改造可能耗費數月並凍結功能；反對者主張等重大需求出現再動。判準是未來改動密度是否配得上投資。
