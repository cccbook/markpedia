# 程式碼審查

> 隸屬：[品質確保]　·　狀態：初稿

> 對應維基百科：[中文維基百科：代码审查](https://zh.wikipedia.org/wiki/%E4%BB%A3%E7%A0%81%E5%AE%A1%E6%9F%A5)　·　[English Wikipedia: Code review](https://en.wikipedia.org/wiki/Code%20review)

程式碼審查（code review，白話說就是「寫完的程式先讓別人看過再合併」）是 [品質確保] 中由**人**執行的檢查活動：作者以外的人逐行閱讀變更，找缺陷、問設計、傳遞知識。它與測試互補——測試驗證「程式照預期運作」，審查檢查「預期本身對不對、程式是否未來還讀得懂」。

審查的收益其實超過找錯。實務上它同時達成四件事：提前抓缺陷、**散播程式碼知識**（多人知道每段程式在做什麼， bus factor 下降）、統一風格與慣用法、以及建立團隊的技術對話文化。研究普遍指出，審查找到的問題中超過半數屬於「可維護性與理解性」，而非純功能錯誤——這正是自動化工具抓不到的部分。

審查同時是**組織記憶的傳承通道**：新人透過審查別人的程式碼學會團隊的慣用法與歷史決策，資深者透過被審查維持與現實的接觸。一個審查文化健康的團隊，知識流動是雙向的；審查淪為單向簽核的團隊，它很快就變成延遲合併的理由而已。

## 审查形態

- **正式檢視（inspection）**：角色分工（主持人、作者、審查者、記錄員）、會議逐條走查、收集缺陷密度資料。抓得多、成本高。
- **輕量走查**：作者帶著審查者走一遍變更，無嚴格角色，適合小型變更。
- **Pull Request 審查**：現代主流。變更以分支提出，審查者在工具上留言，作者修訂後合併，全程留下紀錄。
- **變更後追蹤審查**：合併後由維護者對熱點程式碼定期回看，補足單次審查的視野限制。
- **結對與集體審查**：寫的當下就有人看，事後審查負擔減輕。
- **工具輔助審查**：靜態分析與 AI 建議預先標註疑點，人類審查者聚焦設計與意圖。

## 範例

某團隊為 Pull Request 審查訂出可執行的規則，並觀察效果：

1. **規模限制**：單一 PR 變更不超過 400 行。研究顯示審查效益在超過這個規模後急劇下降。
2. **時限**：收到請求後 24 小時內至少完成第一輪回覆，避免積壓。
3. **檢查清單**：測試是否涵蓋新邏輯？命名是否不需註解就能懂？有無[技術債]未標記？錯誤處理是否吞掉例外？
4. **實測結果**（兩個月、217 個 PR）：審查留言中 41% 涉及命名與結構、23% 涉及潛在缺陷、18% 補測試要求、12% 風格、6% 文件。合併後兩周內的 hotfix 數量從平均每週 3.2 降到 1.4。
5. **教訓**：一開始審查者糾纏縮排與引號風格，導致作者反感；引入格式化工具自動處理風格後，審查對話才回到設計與正確性。

第 5 點的教訓具有普遍性：把「人類不必看的事」交給機器，不只是省時間，更是**保護審查的社會功能**——當審查留言大多是雞毛蒜皮，作者會開始敷衍，審查就失去信任基礎。

## 前因後果

1976 年，Michael Fagan 在 IBM 發表正式檢視法（Fagan inspection），用度量證明審查能在早期抓掉大量缺陷，此後審查成為高可靠軟體的標準配備。[1990年] 前後，輕量化的非正式審查在網際網路公司普及；開源社群以電子郵件補丁為媒介發展出「每行程式都有第二雙眼睛」的文化，Linux 核心的補丁審核流程即為代表。

2000 年代後期，GitHub 式的 Pull Request 流程把審查變成日常、低摩擦的活動。今天，自動化檢查（編譯、[單元測試]、靜態分析、格式化）被放在審查**之前**的自動管線裡，人類審查者聚焦在機器管不了的部分：設計、命名、可讀性與隱性風險。審查因此沒有被工具取代，而是被工具**聚焦**了。

## 與相鄰分類的關聯

- 隸屬 [品質確保]，是需求階段 [驗證] 活動在程式碼層的對應物。
- 與 [持續整合] 的關係：自動檢查在管線中先跑，審查在管線之後進行，兩者構成合併前的完整防線。
- 與 [測試驅動] 的關係：先有測試的變更，審查者可以直接從測試讀出行為意圖，審查重點轉向設計。
- 與 [單元測試] 的關係：審查者檢查的第一件事常是「測試有沒有跟著變更一起來、測得到新邏輯嗎」。
- 與 [維護與演進] 的關係：審查是阻止 [技術債] 進入主幹的第一道閘門，也是 [重構] 提案被討論的場所。

## 容易混淆之處

- **審查不是批鬥**：評論的是程式碼不是人，「這裡可以改成……」勝過「你怎麼又……」。
- **審查不等於風格檢查**：風格交給格式化工具，人類時間留給機器看不出的問題。
- **通過審查不等於正確**：審查者的注意力有限，測試仍是行為正確性的主要憑據。
- **作者不等於唯一負責人**：合併後程式碼是團隊共有，審查者同樣為品質背書。
- **留言被接受不等於被理解**：作者照辦卻不懂原因的審查，下一份 PR 會出現同樣問題；花一句話解釋理由，往往比重複審查便宜。

## 技術要點

1. 控制變更規模：小而頻繁的 PR 審查品質遠高於大型整批提交。
2. 提供**上下文**：PR 描述寫清楚動機與取捨，審查者才能判斷而非猜測。
3. 用**詢問句**提出疑慮（「這裡在並發時會不會有競爭？」），比斷言更促進討論。
4. 區分「必須改」與「建議」：標記等級讓作者知道哪些是合併條件。
5. 對熱點程式碼（經常改動、高風險）要求**兩名審查者**。
6. 記錄重複出現的審查意見，沉澱為團隊的編碼規範或 linter 規則。
7. 大型重構的 PR **分批提交**，每批可獨立理解，避免一次審查數千行。
8. 審查者不確定時**明說**：「我不確定這裡，請找更有經驗的人再看一眼」比沉默放行更負責。
9. 對同一段高風險程式碼的每次修改，都視為**新的審查對象**，不因「上次審過」而放行。

## 常見的論爭

1. **要不要強制每個 PR 都審**：強制保證品質一致但拖慢緊急修復；折衷是文件變更與極小變更豁免，程式碼一律審。
2. **審查多嚴格**：抓到越多缺陷的標準也越容易讓 PR 積壓、作者敷衍；嚴格度應按程式碼風險分級。
3. **AI 輔助審查的定位**：工具可預先標註疑點，但責任與最終判斷仍在人類審查者；反對者擔心淺層意見淹沒真正的設計討論。
4. **審查要不要計入績效**：以審查數量與速度衡量個人會扭曲行為（快而淺的放行）；主流立場是審查品質屬於團隊指標，不落入個人考核。
