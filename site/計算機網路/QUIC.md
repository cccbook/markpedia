# QUIC

> 隸屬：[計算機網路] › [傳輸協定]　·　狀態：初稿

> 對應維基百科：[中文維基百科：QUIC](https://zh.wikipedia.org/wiki/QUIC)　·　[English Wikipedia: QUIC](https://en.wikipedia.org/wiki/QUIC)

QUIC 是建構在 UDP 之上的**使用者空間傳輸協定**，它把可靠交付、加密與多路流整合進同一協定，並於 2020 年成為網際網路工程變遷組的正式標準。

QUIC 的誕生針對的是 TCP 在現代網路上的三個結構性缺陷：**頭部阻塞**（單一封包遺失會阻塞同一連線上所有後續資料）、**交握延遲**（TCP 需兩至三個往返，加上 TLS 交握共需二至三個往返）、以及**中間設備的僵化**（協定的位元組格式固化在核心與作業系統中，演進需等待作業系統更新）。QUIC 以使用者空間實作，讓協定可以隨瀏覽器與伺服器更新而演進。

## 技術與理論的關聯

- **多路流消除頭部阻塞**：QUIC 的一條連線包含多條獨立的有序流，每條流有各自的序號空間；某條流因遺失而等待重傳時，其他流不受影響。這是 QUIC 相對 TCP 最主要的結構性改進。
- **加密與傳輸整合**：交握過程同時完成版本協商、金鑰協商與傳輸參數設定，理想情況下可在一個往返內完成；連線遷移（位址改變）也因此得以在加密狀態下持續。
- **使用者空間的可演進性**：實作放在應用程式而非核心，使得新版本不必等待作業系統升級即可部署，代價是失去硬體卸载與核心層的流量觀測。
- **以 UDP 為基礎的取捨**：可穿透中間設備並易於部署，但 UDP 本身不提供流控與可靠性，QUIC 必須自行實作全部機制。
- **與 [演算法] 的關聯**：封包編碼與解碼、狀態機遷移、密鑰更新與重傳排程，都是使用者空間中的演算法工作；連線遷移還涉及跨位址的封包歸屬判斷。
- **與 [離散數學] 的關聯**：多流之間的相互獨立可用偏序與獨立性描述；序號空間的回繞處理則是有限狀態的典型問題。

## 範例

**範例：一次 QUIC 連線的建立與遷移。**

1. **初始交握**：客戶端送出一個帶有自身初始與最大加密參數的初始封包，伺服器回應版本資訊與加密握手資料。若金鑰已快取，握手可在單一往返內完成。
2. **連線建立**：客戶端驗證伺服器憑證並完成金鑰確認，此後雙方進入加密狀態。此過程把傳輸層的三次交握與 TLS 交握合併，減少了往返次數。
3. **多路流使用**：應用開啟多條流分別傳輸 HTML、樣式表、影像與 API 回應；各流有各自的可靠性狀態。
4. **單流遺失**：其中一條流的一個封包在網路上遺失；接收端在該流上回送遺失指示並等待重傳，但其他流的封包繼續正常交付並即時渲染——這正是 QUIC 解決 TCP 頭部阻塞的具體表現。
5. **連線遷移**：使用者的行動裝置從 Wi-Fi 切換到行動網路，來源位址改變。QUIC 以連線識別碼而非四元素組辨識連線，因此連線得以在加密狀態下持續，無需重新握手。
6. **0-RTT**：若金鑰與連線資訊已快取，客戶端可在握手完成前先送出「早期資料」；伺服器若接受則可節省一個往返，但須承擔重放攻擊的風險，故早期資料僅限於可容忍重放的請求。
7. **對照 TCP**：同樣的位址切換在 TCP 下會使連線中斷（位址四元素組改變），必須重新交握；同樣的單封包遺失則會阻塞整條連線的所有資料。

## 設計取捨

QUIC 的每一項設計都指向同一個目標：讓傳輸層能隨應用更新而演進。

## 實務觀察

QUIC 落地時最常見的挑戰不是協定本身，而是**中間設備的相容性**。部分企業網路的防火牆或深度檢測裝置會阻斷未知的 UDP 流量，導致 QUIC 連線在某些網路中失敗；而瀏覽器通常不會向使用者顯示原因，只會在偵測到失敗後自動退回 TCP——這造成「難以重現」的現象：同一個使用者在家中走 QUIC，在辦公室卻走 TCP。

第二個觀察是**連線池的設計影響握手收益**。QUIC 的交握成本低，但在每次連線都重新建立的情況下，優勢難以體現；應用透過在多個來源位址間預先建立連線並保持閒置，才能在需要時立即交出資料。這個「連線預熱」的做法把 QUIC 的低握手成本轉化為實際的延遲改善。

第三點是**可觀測性的取捨需要主動補償**。由於內容加密，網路側的封包統計仍可用（位元組數與封包時序可見），但無法看到應用層語意。因此以 QUIC 為基礎的服務通常需要在應用層自行暴露指標，才能維持與過去同等水準的服務可見性。

## 前因後果

- **前因**：2010 年代行動網路普及，TCP 在高遺失、高延遲變動的鏈路上體驗不佳；同時 HTTP/2 的多工仍建立在單一 TCP 連線之上，使其多工優勢被頭部阻塞抵銷。
- **後果**：QUIC 促成 HTTP/3 的部署，主流瀏覽器與內容分發網路幾乎全面支援；同時促成使用者空間協定這一新的演進路徑，也讓傳輸層的創新不必等待作業系統。
- **互相驅動**：[TCP] 的結構性限制促成 QUIC；[應用層協定] 中的 HTTP/3 直接建立在 QUIC 之上；而 QUIC 內建加密的特性也回應了 [資訊安全] 中核心無法觀測內容的問題。

## 容易混淆之處

- **QUIC 不等於 HTTP/3**：QUIC 是傳輸協定，HTTP/3 是其上的應用協定；兩者可分開使用。
- **QUIC 不等於「QUIC over UDP 的 QUIC」**：它確實跑在 UDP 上，但幾乎不使用 UDP 的語意，而是自行實作完整傳輸層。
- **使用者空間不代表沒有狀態**：狀態只是從核心移到應用程式，並未消失。
- **0-RTT 不等於零延遲**：仍需等待伺服器回應，且有重放風險。
- **連線遷移不等於 IP 位址不變**：位址確實改變，是協定以連線識別碼維持語意連續。
- **支援 QUIC 不等於使用 HTTP/3**：伺服器可同時提供兩種協定，由用戶端選擇。

## 技術要點

- 每條流有獨立的序號空間與重傳狀態，以消除跨流頭部阻塞。
- 連線識別碼與來源位址解耦，使連線可在加密狀態下遷移。
- 交握與加密整合，並支援金鑰更新以限制單一金鑰的暴露期間。
- 早期資料僅用於可安全重放的請求，並由伺服端以抗重放機制保護。
- 使用者空間實作放棄部分硬體卸载與核心觀測能力，代價需由應用自行補足。
- 0-RTT 與 1-RTT 資料路徑的延遲差異，應反映在連線池與預熱策略中。

## 常見的論爭

- **使用者空間與硬體卸载的取捨**：把傳輸移出核心提升了演進速度，代價是 CPU 使用與核心層流量可見性的下降。
- **中間設備的觀測困境**：加密的 QUIC 使網路設備難以辨識內容，威脅情報與流量分析的價值被重新評估。
- **0-RTT 的重放風險**：節省一個往返的代價是安全性上的不確定性，業界對其使用範圍仍有討論。
