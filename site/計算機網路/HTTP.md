# HTTP

> 隸屬：[計算機網路] › [應用層協定]　·　狀態：初稿

> 對應維基百科：[中文維基百科：超文本传输协议](https://zh.wikipedia.org/wiki/%E8%B6%85%E6%96%87%E6%9C%AC%E4%BC%A0%E8%BE%93%E5%8D%8F%E8%AE%AE)　·　[English Wikipedia: HTTP](https://en.wikipedia.org/wiki/HTTP)

HTTP 是**以取得資源為目的的應用層協定**：客戶端以方法與路徑描述想要什麼，伺服器以狀態碼與內容回應。它的設計原本極為簡單——「要求一個文件，給你一個文件」——但今日的 HTTP 承載了網頁、API、串流、檔案下載與事件推送。

HTTP 的兩次重大轉折值得注意：先是**以方法與狀態碼擴充語意**，讓同一路徑能表達讀取、寫入與刪除；再是**以版本演進語意**，第一版簡單到幾乎無法擴充，第二版引入主機標頭以支援多網站共用位址，第三版引入訊息框架與分塊傳輸，第四版（也就是今日的版本）則在語意上相容於第二版但改進了傳輸效率。這段歷史說明：應用層協定的相容性往往不是靠版本號，而是靠「是否保留舊的語意」來保證。

## 技術與理論的關聯

- **方法與狀態碼構成有限語意**：方法表達動作、狀態碼表達結果，兩者組合形成可推論的語意；狀態碼以首位數字分組，使未知狀態仍可被粗略分類處理。
- **快取驗證的條件式機制**：實體標籤與最後修改時間構成版本的指紋，條件式請求讓客戶端以一次往返確認副本是否仍新鮮，這是內容散發網路減少回源流量的核心。
- **內容協商**：同一路徑可依傳送標頭與接受標頭回應不同表示，語言與格式的選擇本質上是一個多目標最佳化問題。
- **冪等性與安全性的方法分類**：某些方法（如查詢）在語意上可重試，某些（如新增）不可；應用層的正確性取決於伺服器是否正確實作這些語意差異。
- **與 [演算法] 的關聯**：內容分發中的副本選擇、快取淘汰策略與預載預測，都是演算法問題。
- **與 [離散數學] 的關聯**：版本相容性矩陣與狀態碼的有限狀態結構，可形式化為偏序與狀態機。

## 範例

**範例：一次帶快取驗證的資源載入。**

1. **初次請求**：瀏覽器對某影像發出請求，伺服器回應 200，並附上實體標籤（例如內容雜湊值）、最後修改時間與快取期限。
2. **快取命中**：在同一快取期限內再次請求時，瀏覽器直接使用本地副本，不發出網路請求。快取期限由伺服器依內容的變動頻率決定。
3. **條件式請求**：期限過後，瀏覽器發出條件式請求，帶上先前取得的實體標籤。
4. **伺服器比對**：伺服器計算目前內容的標籤並與請求中的標籤比較；若相同，回應 304（未修改）且不含內容本體；若已改變，則回應 200 與新內容。
5. **成本意義**：304 回應的體積遠小於內容本體，因此在內容散發網路與瀏覽器間的往返成本大幅下降。
6. **版本相容**：若伺服器改版導致既有標籤失效，客戶端會收到新的 200 與新標籤，更新本地副本，過程對使用者透明。
7. **實務延伸**：現代伺服器常把內容雜湊直接嵌入資源網址，使快取鍵隨內容改變而變更，避免驗證往返；這是建置系統中最常見的快取策略之一。

## 前因後果

- **前因**：1990 年代初，為讓萬維網能在多台伺服器上共用同一個位址，HTTP 需要引入主機標頭；此後內容種類大增，促使語意擴充與傳輸效率都必須改善。
- **後果**：HTTP 成為網際網路最廣泛使用的協定，帶動內容散發網路、內容協商與快取體系的成熟；近年 HTTP/3 把它移植到 [QUIC] 之上，進一步降低多路傳輸與交握的成本。
- **互相驅動**：[TLS] 使 HTTP 得以在加密通道中安全傳輸；[DNS] 的名稱解析是 HTTP 運作的前提；[應用層協定] 中的其他成員也常透過 HTTP 與外界互動。

## 容易混淆之處

- **HTTP 不等於 HTTPS**：兩者是同一協定的兩種傳輸方式，安全性由承載層的 [TLS] 提供。
- **狀態碼 200 不代表一切正常**：業務層的錯誤常以 200 內的 JSON 欄位表達，監控若只看狀態碼會漏判。
- **快取標頭不是單一的**：不同來源（瀏覽器、中間快取、内容分发）適用不同的快取指示，組合起來行為複雜。
- **302 不等於 301**：前者是暫時性，後者是永久性，對搜尋引擎的處理不同。
- **POST 不必然不可重試**：是否可重試取決於伺服器端是否實作冪等，而非方法名稱本身。
- **HTTP/1.1 與 HTTP/2 的差異不在語意**：第二版的版本碼不反映其特性，這是版本編號設計的歷史包袱。
- **無狀態不等於沒有狀態**：伺服器通常以 cookie 或 token 維護應用狀態。

## 技術要點

- 對可快取的靜態資源使用內容雜湊作為網址的一部分，以完全避免驗證往返。
- 對動態內容使用適當的快取指示，並區分使用者專屬內容與共用內容的快取策略。
- 併發請求上限應與伺服器容量協調，避免大量並行請求形成自我造成的阻斷服務。
- 串流或長輪詢的連線應設定合理的連線逾時，避免佔用連線資源。
- 請求與回應的大小應設上限，並對輸入做驗證；這是 [資訊安全] 中應用層的常見弱點來源。
- 追蹤標頭應明確設定哪些欄位可以透傳，避免意外洩漏內部資訊。

## 常見的論爭

- **文字格式的效率**：二進位格式可節省頻寬並加速解析，但降低了可讀性與中間設備的相容性。
- **快取正確性與隱私的平衡**：共用快取若忽略使用者的隱私屬性，可能把某人的內容交給另一人看到。
- **版本相容的長期成本**：為維持舊用戶端相容而保留的邏輯，是應用層協定複雜度的主要來源。
