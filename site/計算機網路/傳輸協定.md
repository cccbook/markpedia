# 傳輸協定

> 隸屬：[計算機網路]　·　狀態：初稿

> 對應維基百科：[中文維基百科：传输层](https://zh.wikipedia.org/wiki/%E4%BC%A0%E8%BE%93%E5%B1%82)　·　[English Wikipedia: Transport layer](https://en.wikipedia.org/wiki/Transport_layer)

傳輸層是**端到端的交付語意層**：它把下層的不可靠分組服務，包裝成應用程式可以直接使用的抽象。同一段應用程式碼，在上層可以說「我送出一串位元組」，而不必處理封包遺失、重複、乱序與流量競爭。

傳輸層的設計要回答四個問題：**如何標定資料的邊界**（位元組串與分組的關係）、**如何處理遺失與亂序**（可靠性）、**如何避免接收端被淹沒**（流量控制）、**如何在共享鏈路上公平分配容量**（壅塞控制）。不同的答案組合，產生了今日的 [TCP]、[UDP] 與 [QUIC]。

## 技術與理論的關聯

- **抽象的必要性**：若每個應用程式都自行處理遺失與重組，相同的複雜邏輯會被重複實作無數次，且難以維護；傳輸層把這份複雜性集中在一處，這是分層的典型收益。
- **可靠性的代價**：可靠交付必然引入等待與重傳，因此「可靠」不是免費的。選擇 [TCP] 或 [UDP]，本質上是在延遲與完整性之間做取捨。
- **序號空間與回繞**：為偵測重複與亂序，序號必須足夠大以避免在連線生命週期內回繞，這是有限狀態機設計的典型問題。
- **流量控制與壅塞控制的區分**：流量控制保護接收端（避免接收緩衝區溢出），壅塞控制保護網路（避免把路由器與共享鏈路塞滿）；兩者使用不同的回饋訊號。
- **與 [演算法] 的關聯**：重傳逾時的推估、視窗的動態調整與多路徑的排程，都是演算法問題；並行的連線則提供了大量並行實驗的機會。
- **與 [離散數學] 的關聯**：序號比較、視窗的滑動與確認的累積關係，皆可形式化為偏序與狀態機。

## 範例

**範例：同一段影片串流，在三種傳輸協定下的差異。**

1. **使用 UDP 的即時串流**：應用把畫格直接切成封包送出，不等確認。封包遺失時，該畫格被丟棄，應用繼續往下送。延遲維持在低位，代價是偶爾的畫格破損與花屏。
2. **使用 TCP 的串流**：每個位元組都必須可靠送達。若某封包遺失，接收端在收到後續資料時發現序號不連續，會要求重傳；由於應用不能略過這段資料，後續畫格全部滯留在接收緩衝區等待。於是一次遺失造成數百毫秒的停頓——這就是 TCP 尾延遲的來源。
3. **使用 QUIC 的串流**：QUIC 在單一連線上提供多條獨立的有序流，各流之間互不阻塞。即使其中一條流因遺失而等待重傳，其他流仍可繼續交付，於是語音可持續、影片可續傳，互不牽連。
4. **場景切換**：若是檔案下載，需要的是完整與順序，此時 TCP 或 QUIC 的可靠流最合適；若是語音通話，寧可遺失也不願等待，此時 UDP 的不可靠交付最合適；若是同時有兩者需求，QUIC 的多流抽象正好同時滿足。
5. **共通的問題**：三種情況都共享流量控制與壅塞控制的問題。串流本身佔用大量頻寬，若不自我節制，會把共享鏈路的其他連線擠出；因此即使使用 UDP，應用層也必須自行實作速率限制，否則在 [阻斷服務] 與壅塞的邊界上會製造事故。

這個範例說明傳輸協定的選擇**不是優劣問題，而是需求匹配問題**。

## 前因後果

- **前因**：1970 年代 ARPANET 提供的服務既不可靠又會遺失分組，直接在其上建立應用極為困難；[倫納德] 與 [克恩] 因此把可靠性放到端點的傳輸層，這是端對端原則的具體化。
- **後果**：TCP 成為絕大多數應用的預設傳輸協定，帶動 HTTP、郵件、檔案傳輸等整個應用層生態；近年面對行動網路的高遺失與跨洲高延遲，[UDP] 與 [QUIC] 重新受到重視。
- **互相驅動**：[應用層協定] 的需求不斷逼出新的傳輸語意（多路流以支援 HTTP/3）；[無線網路] 的高遺失特性也直接催生了對抗 TCP 頭部阻塞的動機。

## 容易混淆之處

- **傳輸層與網路層不同**：網路層處理跨網路的轉送，傳輸層只處理端點之間的語意。
- **可靠與準時是對立的**：在多數鏈路上，強求可靠會增加延遲；要求低延遲就要接受遺失。
- **TCP 不等於快**：TCP 的目標是可靠與有序，在高遺失鏈路上它的表現可能比丟包更差。
- **UDP 不等於不可靠**：UDP 只是不提供可靠性，應用層可以自行實作。
- **傳輸層不等於應用層**：即使在同一個作業系統行程內，兩者仍是不同的抽象層。
- **多工不等於多執行緒**：傳輸層的多路流處理的是封包交錯，與 CPU 平行無關。

## 技術要點

- 每條連線都需要獨立的序號空間與狀態，核心不得依賴連線狀態以維持可擴充性。
- 確認訊號應支援累積確認，以一次確認涵蓋多個連續區段。
- 逾時值應依實測往返時間動態推估，並設定合理的最小與最大值。
- 接收端應宣告零視窗時也定期送出窗口更新，避免死鎖。
- 對多路流協定，每條流應有獨立的可靠性狀態與流控，避免頭部阻塞。
- 應用層的請求逾時必須大於底層可能的重傳累積時間。

## 常見的論爭

- **使用者空間協定的取捨**：把傳輸與加密移入使用者空間加速了演進，卻放棄了硬體卸载與核心可觀測性。
- **端對端加密對中間盒的衝擊**：加密普及削弱了網路核心的安全功能可用性，產業該補救還是放棄仍有爭議。
- **壅塞控制的公平性**：以往返時間推估带宽佔用，在路徑長度不均的網路上可能對某些連線不公平。
