# TCP

> 隸屬：[計算機網路] › [傳輸協定]　·　狀態：初稿

> 對應維基百科：[中文維基百科：传输控制协议](https://zh.wikipedia.org/wiki/%E4%BC%A0%E8%BE%93%E6%8E%A7%E5%88%B6%E5%8D%8F%E8%AE%AE)　·　[English Wikipedia: Transmission Control Protocol](https://en.wikipedia.org/wiki/Transmission_Control_Protocol)

TCP 是**提供可靠、有序、位元組串交付的傳輸層協定**。它的核心機制是：以序號標定位元組、以確認號回報已收到的最高連續位元組、以視窗控制流量、以逾時與快速重傳處理遺失。

TCP 的設計源於 1970 年代的實際問題：當時的網路會遺失、重複與亂序封包，而分時系統上的互動式工作需要正確的資料流。[倫納德] 與 [克恩] 的解法是把它交給端點處理——核心網路只需盡力交付。這一選擇成就了網際網路的可擴充性，也讓 TCP 成為歷史上部署最廣的協定。

## 技術與理論的關聯

- **位元組串抽象**：TCP 不保留訊息邊界，應用程式寫入的位元組在接收端是連續的流；這解耦了應用層的訊息封裝，也意味著接收端無法得知原始訊息大小。
- **確認與重傳構成可靠性的核心**：累積確認讓一次確認涵蓋多個區段；重傳逾時時間的推估必須在「過早重傳造成浪費」與「過晚重傳造成延遲」之間平衡。
- **快速重傳與避免重複**：連續三個重複確認被視為遺失的訊號，接收端立即重傳而非等待逾時，這把重傳延遲從一個往返時間降到數百毫秒。
- **滑動視窗的流量控制**：接收端在確認中宣告剩餘緩衝區大小，發送端據此限制在途資料量；這使快速接收端不會被慢速應用淹沒。
- **壅塞控制的必要性**：TCP 不知道瓶頸在哪裡，也無法直接測得可用頻寬，因此必須以遺失或延遲增加作為間接訊號，這是一種分布式推測。
- **與 [演算法] 的關聯**：重傳逾時的估計、視窗的動態調整與多連線的公平性，都是演算法問題；TCP 的設計本質上是一組分散式控制演算法。

## 範例

**範例：一次跨越遺失的可靠傳輸。**

1. **建立連線**：三次交握完成——發送端送出序號為零的同步、接收端回覆確認號為一的同步並附上自己的序號、發送端再確認接收端的序號。第三次確認讓雙方都知道對方已收到自己的起始序號，避免半開連線。
2. **傳送與確認**：發送端送出若干區段，每個區段帶有本身的序號；接收端回送確認號，代表「我已收到此序號之前的所有位元組」。確認可累積，因此不必對每段單獨回覆。
3. **遺失發生**：其中一個區段在路徑上遺失，但後續區段仍抵達接收端。
4. **偵測**：接收端發現序號不連續，重複回送目前收到的最後一個連續序號作為確認號，並對之後到達的重複區段持續回送同一確認號。
5. **快速重傳**：發送端連續收到三個重複確認，判定該區段遺失，不等待逾時即重傳該區段。
6. **恢復**：遺失的區段抵達接收端後，接收端確認號前進，發送端的確認累計也隨之更新；此後累積確認可一次涵蓋多段，確認流量因此大幅減少。
7. **流量與壅塞控制**：發送端的在途資料量受接收端視窗限制；若視窗滿，發送端停止新資料送出，待接收端釋出緩衝空間並以窗口更新告知後再繼續。
8. **連線關閉**：四次交握完成——一方送出關閉、對方確認；對方送出關閉、發送端確認；隨後進入等待時間以確保所有在途資料都已處理。

## 實務觀察

TCP 的效能問題在實務上常以「延遲」而非「頻寬」的形式出現。當團隊抱怨下載慢時，應先分辨是頻寬不足（吞吐受限）還是延遲過高或封包遺失（互動受限）：前者需要擴充容量，後者則要檢查路徑與重傳行為。兩者的處置方式完全不同，而混淆兩者是常見的誤判來源。

另一個常見的觀察是**慢啟動造成的初期緩慢**。一條新連線的傳送視窗從小開始逐步增加，因此在短時間的傳輸中可能遠未用滿可用頻寬；對單一大檔案影響不大，但對大量短連線（每條都需經歷慢啟動）就會顯著降低整體效率。這也是為何大檔案傳輸常以多條平行連線進行。

第三個實務重點是**逾時設定的深淺影響**。逾時過短會在正常抖動時就誤判為遺失而重傳，徒增流量並可能加劇壅塞；逾時過長則讓真正的遺失拖慢恢復。合理的做法是依實測往返時間設定並配合快速重傳，讓逾時只作為最後手段。

## 前因後果

- **前因**：早期 ARPANET 與分時系統的經驗顯示，錯誤的資料流比沒有資料流更糟，因此需要一個在端點確保正確性的機制。
- **後果**：TCP 讓網際網路承載了電子郵件、網頁、檔案傳輸與串流等幾乎所有應用；其設計也影響了後來的 [可靠傳輸] 研究與 [QUIC] 的取捨。
- **互相驅動**：[TCP/IP] 套組把 TCP 定位為網際網路的預設傳輸協定；[應用層協定] 中的 HTTP 在 TCP 之上運作；[無線網路] 的高遺失特性則持續挑戰 TCP 的效能極限。

## 容易混淆之處

- **TCP 不保證不重複**：在連線中重複出現的位元組會被接收端丟棄，但確認訊號可能重複。
- **TCP 不保留訊息邊界**：應用若需要訊息邊界必須自行加入長度前綴或分隔符。
- **TCP 的可靠是端到端的**：中間設備不做任何保證，這也意味著加密可穿透 TCP。
- **可靠不等於及時**：這是 TCP 在即時通訊中最常被詬病之處。
- **四次交握是四次封包，但狀態轉移有六種**：區分三-way 與四-way 的理由在於連線是全雙工的。
- **連線與位址綁定不同**：連線由四元素組識別，同一對位址之間可同時存在多條連線。

## 技術要點

- 確認訊號應支援累積確認，並在延遲確認與快速回應之間取得平衡。
- 重傳逾時時間依往返時間的估計值設定，並以指數退避處理重複的逾時。
- 連續三個重複確認即可觸發快速重傳，是降低重傳延遲的關鍵。
- 接收端必須維持廣告的視窗並在需要時送出窗口更新，避免發送端停滯。
- 慢啟動與壅塞避免必須實作為狀態機，否則新連線會瞬間淹滿瓶頸。
- 對長距離鏈路可啟用時間戳選項以精確測量往返時間，但需注意時鐘同步的風險。

## 常見的論爭

- **TCP 對行動網路的不適配**：在高遺失、高延遲變動的鏈路上，TCP 的可靠重傳機制造成的停頓被認為是主要瓶頸。
- **壅塞控制的公平性**：以往返時間推估帶寬佔用的做法，在非對稱路徑上可能偏袒某些連線。
- **中間盒的介入空間**：加密普及讓中間盒難以觀測內容，使其深度檢測能力大幅下降，相關取捨引發持續討論。
