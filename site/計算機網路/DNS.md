# DNS

> 隸屬：[計算機網路] › [應用層協定]　·　狀態：初稿

> 對應維基百科：[中文維基百科：域名系統](https://zh.wikipedia.org/wiki/%E5%9F%9F%E5%90%8D%E7%B3%BB%E7%BB%9F)　·　[English Wikipedia: Domain Name System](https://en.wikipedia.org/wiki/Domain_Name_System)

DNS（網域名稱系統）是**把易記的名字轉換成機器使用的位址與其他資源資訊的分散式資料庫**。它解決的是一個看似簡單、實際上極難的問題：位址本身是一串不具語意的數字，且會隨拓樸與營運商而變動；名稱則是人類可讀、可獨立於網路結構改變的識別碼。

DNS 的設計核心是**分層與委派**。整個名稱空間是一棵由根、頂級域、second-level 域組成的樹；權威伺服器各自負責自己那一段的資料，並以「委任」的方式把子樹的維護權交給下級。查詢因此可以沿樹往下走，而不必有任何單一節點保存全部資料。

它的傳輸則刻意簡單：查詢與回應通常是透過 [UDP] 進行的單一封包往返，因為名稱解析常位於使用者等待延遲的關鍵路徑上。可靠性與加密後來才被補上，形成 DNS 的三個世代：傳統的明文 UDP 解析、加上簽章驗證的 DNSSEC、以及以 [TLS] 加密的 DNS over TLS 與 DNS over HTTPS。

## 技術與理論的關聯

- **分層命名空間**：DNS 的樹狀結構把一個不可能集中管理的問題（全球名稱的唯一性）分解為多個可獨立授權的子問題，這是 [離散數學] 中分治思想在基礎設施中的體現。
- **遞迴與迭代查詢**：遞迴查詢讓查詢者只問一次、代為追查；迭代查詢讓查詢者依序詢問每一層。兩者的分工決定了查詢路徑的長度與權威伺服器的負載。
- **快取與失效**：每筆記錄帶有存活時間，解析器在有效期內直接回答；這是一個以過期換取延遲的經典取捨，也是快取投毒攻擊的入口。
- **快取鍵的正規化**：域名在語意上大小寫不敏感，但實務上多保留原始大小寫；現代實作會隨機化查詢中的大小寫以避免快取投毒。
- **與 [演算法] 的關聯**：解析器中的並行查詢、快取淘汰策略與位址選擇順序，都是最佳化與排程問題。
- **與 [資訊安全] 的關聯**：DNS 從純粹的目錄服務變成安全關鍵基礎設施——它決定了憑證驗證時要連到哪裡，因此其完整性直接影響整個加密信任體系的成立。

## 範例

**範例：一次 `www.example.com` 的解析過程。**

1. **應用發起查詢**：瀏覽器需要取得位址，先查自己的主機快取；未命中則把查詢交給作業系統的解析器設定，通常是一個本機或區域網路的遞迴解析器。
2. **遞迴查詢封包**：解析器構造一個 DNS 查詢訊息，其標頭含一個 16 位元的交易識別碼、旗標（此處要求遞迴）、一個問題節點（名稱、型別、類別）。名稱以標籤序列表示，例如「www、example、com、」再以零長度標籤結尾。
3. **快取檢查**：解析器依序檢查自己的記憶體快取與磁碟快取；命中且未過期則直接回應。這是延遲最主要的節省來源。
4. **根伺服器查詢**：若未命中，解析器向根伺服器發出迭代查詢。根伺服器回應中包含「委派」資訊，指出該頂級域的權威伺服器位址，但**不含**最終位址。
5. **頂級域伺服器查詢**：解析器再向頂級域的權威伺服器查詢，得到 `example.com` 的權威伺服器位址，仍不含最終位址。
6. **權威伺服器查詢**：向權威伺服器查詢，得到主機記錄，並在回應中附上此記錄的存活時間。此時解析器可回覆客戶端。
7. **回應與快取**：回應標頭中帶有「回應碼」（成功、格式錯誤、名稱不存在、不支援的型別）、權威答案區與額外資訊區；解析器將答案連同存活時間寫入快取。
8. **客戶端連線**：瀏覽器取得位址後，才能建立 [TCP] 或 [QUIC] 連線；若使用 HTTPS，還需完成 [TLS] 交握並驗證憑證——憑證中的名稱正是要和這次查詢的名稱比對。
9. **邊界情形**：若名稱不存在，名稱伺服器授權鏈會回應「名稱不存在」並附上權威伺服器的說明；解析器據此把負結果也快取一段較短的時間，避免反覆重複查詢不存在的名稱。
10. **快取陷阱**：若解析結果被快取過久，使用者可能在伺服器遷移後仍被導向舊位址；這是位址變更時必須同步更新 DNS 記錄的原因。

## 前因後果

- **前因**：1970 年代的網際網路最初使用容易記憶的位址清單，但主機數量成長後清單維護與位址分配都不可行，必須引入獨立的命名系統。
- **後果**：DNS 使網域名稱成為網際網路的通用入口，並隨後被擴充承載郵件交換、服務位置與驗證政策等紀錄類型；它也成為多數應用層服務的第一個網路請求。
- **互相驅動**：DNS 的可用性直接影響所有以名稱存取的服務，因此 [雲端與邊緣] 中的多區域部署必然伴隨名稱解析的可用性設計；而加密普及後，DNS 查詢也被迫納入加密範疇，催生了 DNS over HTTPS。

## 與相鄰分類的關聯

- 與 [HTTP] 的關係：HTTP 連線的前置條件是名稱解析；「網頁打不開」的第一診斷步驟就是確認解析是否成功。
- 與 [TLS] 的關係：以名稱驗證憑證需要先有解析結果，因此 DNS 的完整性是加密信任鏈的起點。
- 與 [UDP] 的關係：傳統查詢以單一 UDP 封包往返；當回應過大時，才會退回 [TCP]。
- 與 [路由] 的關係：根伺服器與頂級域伺服器數量極少且分散各地，其可達性高度依賴多供應商之間的骨幹互連與路由穩定性。
- 在上位子分類 [應用層協定] 中，DNS 提供的是**間接服務**——它不直接回應使用者的請求，卻是幾乎所有其他應用層協定的前提。

## 容易混淆之處

- **DNS 不是資料庫伺服器**：它是一個以分層授權維護的分散式目錄，且查詢語意極簡單，沒有關聯式查詢能力。
- **寄件與收件不同**：DNS 只記錄郵件應該送往哪台主機，實際的遞送由 [SMTP] 負責。
- **名稱伺服器與解析器不同**：權威名稱伺服器保存正式資料；遞迴解析器則替客戶端代為查詢並快取結果。
- **DNS 快取不保證即時**：記錄變更需要等各層快取過期才會全面生效。
- **有 IP 位址不等於能上網**：名稱只是識別，連線仍須經過路由與防火牆。
- **DNS 與hosts 檔案**：舊式名稱對應仍常被寫入作業系統的靜態檔案，排查時不可忽略。

## 技術要點

- 為解析器設定合理的存活時間上限，避免快取過舊導致服務遷移後連不上。
- 對外提供服務時應同時宣告位址記錄與其他必要記錄，並定期檢查記錄與實際設定是否一致。
- 域名結構應將註冊者控制的部分與機構控制的部分分開，便於委派與權限隔離。
- 對外查詢應啟用簽章驗證，讓驗證失敗無法偽裝成有效回應。
- 名稱伺服器應部署於多個不同網路，並以位址回應輪替機制分散查詢。
- 除錯時應區分「權威資料錯誤」與「解析器快取過期」，兩者的處置方式完全不同。

## 常見的論爭

- **集中式與聯邦式的取捨**：根伺服器數量極少且高度集中，其穩定性仰賴營運者之間的志願協作，是長久以來被批評的結構性風險。
- **隱私與可觀測性**：加密解析降低了 ISP 觀測使用行為的能力，相對地也讓惡意行為更難被偵測。
- **是否應由單一機構統一治理**：現行體系依賴多層委派與契約協調，有人主張應有更強的全球治理，也有人認為集中化會帶來更大的單點風險。
