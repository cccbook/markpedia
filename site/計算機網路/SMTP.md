# SMTP

> 隸屬：[計算機網路] › [應用層協定]　·　狀態：初稿

> 對應維基百科：[中文維基百科：簡單郵件傳輸協定](https://zh.wikipedia.org/wiki/%E7%AE%80%E5%8D%95%E9%82%AE%E4%BB%B6%E4%BC%A0%E8%BE%93%E5%8D%8F%E8%AE%AE)　·　[English Wikipedia: Simple Mail Transfer Protocol](https://en.wikipedia.org/wiki/Simple_Mail_Transfer_Protocol)

SMTP 是**用來在郵件伺服器之間傳遞郵件的應用層協定**，也是電子郵件三段架構中負責「遞送」的那一段。它的設計源於 1980 年代初的網際網路：那時網路是不可靠的、連線經常中斷的，而郵件必須能跨越數日的離線時間送達，因此協定本身設計成極簡的文字對話——用可讀的指令與回應碼逐行溝通。

SMTP 的核心特徵是**推送式（push）模型**。寄件者與收件者之間並不存在持續連線；郵件由寄件端的主動推送到收件端的伺服器，後續的收信、篩選與同步則由其他協定（郵件擷取協定與網頁式閱讀）負責。這個分工是歷史的產物：當時伺服器之間的連線成本高、不可靠，而使用者端幾乎沒有互動式能力。

今日的 SMTP 早已不是明文的 25 埠協定了。出於對抗垃圾郵件與竊聽的需要，郵件在中繼站之間普遍以加密通道承載，並加上來源驗證與傳送路徑紀錄等機制。

## 技術與理論的關聯

- **指令—回應的對話模型**：每條指令由一行 ASCII 文字構成，伺服器以三碼數字回應（如 250 表示成功、550 表示拒絕）。這是最簡單也最易於除錯的協定風格之一。
- **推送模型與離線容忍**：協議不假設雙方同時在線，讓郵件可以跨越數日的斷線後仍被送達，這是它與互動式協定的根本差異。
- **轉送鏈的信任問題**：郵件在伺服器之間可能經過多個中繼，每一站的加入政策都影響最終投遞率；這使電子郵件的送達性高度依賴全網的政策共識。
- **來源驗證**：因為寄件端身分在原始設計中完全由寄件人自稱，垃圾郵件得以橫行，促使 SPF、DKIM 等以 DNS 記錄為基礎的驗證機制出現。
- **與 [DNS] 的關聯**：郵件的目的地與寄件來源都靠 DNS 記錄描述——郵件交換記錄指定遞送站，來源驗證政策則以文字記錄宣告。
- **與 [資訊安全] 的關聯**：明文 SMTP 同時洩漏內容與帳密，是最典型的明文傳輸反例之一。

## 範例

**範例：一封郵件從寄件人到收件人的完整路徑。**

1. **寄件端提交**：使用者在用戶端編好郵件後，由用戶端以 SMTP 的「提交」用途連上寄件端伺服器（通常使用加密連線，埠號為 587）。
2. **HELO 與能力協商**：客戶端先送出 HELO 指令，宣告自己的名稱；伺服器回應 250，並列出支援的擴充功能（例如可支援的驗證方式、傳輸大小上限）。
3. **起始與寄件者宣告**：客戶端送出 MAIL FROM，宣告寄件人地址；伺服器以 250 接受。接著以 RCPT TO 宣告收件人地址，每個收件人各一條指令。
4. **資料內容**：客戶端以 DATA 指令進入資料傳送階段，逐行送出郵件內容，最後以單獨一行僅含句點結束；伺服器回應 250 表示已排入遞送佇列。
5. **本機投遞**：若收件人是本地使用者，伺服器直接寫入其信箱；若收件人位於其他網域，伺服器查詢 DNS 的郵件交換記錄，取得目的伺服器。
6. **中繼遞送**：伺服器與目的伺服器建立連線（通常是 25 埠，並以 STARTTLS 升級為加密），重複 HELO、MAIL FROM、RCPT TO、DATA 的流程。轉送鏈上每一站都可能加入自己的標頭，記錄路徑。
7. **延遲遞送與重試**：若目的伺服器暫時無法連線，寄件端依重試政策間隔遞增地重試，並最終退信通知寄件人。這個退避策略避免了對故障中的目的地形成持續壓力。
8. **拒絕與退信**：若收件人不存在或政策拒收，伺服器在接收 DATA 之前就以 550 之類的回應拒絕，此時尚未付出傳送內容的成本。
9. **收件端取得**：收件人使用郵件擷取協定或網頁介面讀取郵件；這些協定不在 SMTP 的範圍內。

這個流程說明：**SMTP 只負責從寄件端到收件信箱的遞送，「讀信」是另一套機制**——這是電子郵件使用中最常見的困惑來源。

## 前因後果

- **前因**：1970 年代末到 1980 年代初，ARPANET 與早期網際網路的使用者需要一種能跨越離線時間的訊息交換方式；既有的即時線路無法承擔。
- **後果**：SMTP 成為全球事實標準，並隨之帶來垃圾郵件、釣魚與追蹤等一整串治理議題；反垃圾機制最終多以 DNS 記錄為基礎，這是把兩個原本無關的系統綁在一起的結果。
- **互相驅動**：網際網路的普及帶來了郵件量的爆炸，迫使協定加入傳輸大小限制與投遞最佳化；而 [TLS] 的普及又讓郵件得以在加密通道中遞送，間接推動了使用者空間加密與憑證管理需求的成長。

## 與相鄰分類的關聯

- 與 [HTTP] 的關係：越來越多郵件服務以瀏覽器介面呈現，郵件內容的呈現與操作以 [HTTP] 為基礎，但遞送本身仍是 SMTP 的工作。
- 與 [DNS] 的關係：郵件交換記錄決定遞送目的；來源驗證政策也以 DNS 記錄發布，兩者讓 DNS 成為郵件生態系的基礎設施。
- 與 [TLS] 的關係：加密通道是 SMTP 今日的基本要求，同時也是憑證與名稱驗證的實踐場所。
- 與 [TCP] 的關係：SMTP 建立在具可靠有序交付的連線之上，郵件內容的長度可達數十兆位元組，因此必然需要分段與重組。
- 在上位子分類 [應用層協定] 中，SMTP 呈現的是**最古老的一種協定風格**：文字介面、逐行互動、狀態碼回應。

## 容易混淆之處

- **SMTP 不等於收信**：收信使用其他協定；SMTP 只做遞送。
- **25 埠與 587 埠用途不同**：25 埠供伺服器間轉送，587 埠供用戶端提交，投遞政策也不同。
- **寄件人欄位不等於真實寄件人**：寄件人地址可任意填寫，這正是來源驗證機制存在的理由。
- **收到郵件不等於郵件來自該網域**：驗證的是網域政策，而非人的身分。
- **加密連線不等於內容可信**：通道安全與內容真實是兩個問題。
- **退信不等於被刪除**：多數服務會提供短期暫存區，讓使用者仍有機會取回。

## 技術要點

- 伺服器應記錄每封郵件的完整轉送路徑，以支援追蹤與問題回溯。
- 對外開放的轉送埠應實施速率限制與收件人數量上限，避免被用作郵件炸彈。
- 提交介面應強制使用加密連線，並在連線前先完成帳密驗證。
- 應對延遲投遞採用指數退避，並在最終退信時向寄件人明確說明原因。
- 訊息大小與收件人數量應設上限，超限時應回應明確的拒絕碼而非直接中斷。
- 伺服器時鐘必須同步，因為許多判定與退信訊息都依賴時間戳。

## 常見的論爭

- **是否應保留明文傳輸以兼顧舊系統**：完全淘汰明文需要很長的過渡期，至今仍有地區與網域尚未完成遷移。
- **來源驗證的強制程度**：要求所有寄件方完成驗證會阻擋部分合法郵件，執行力道成為寄件方與收件方之間的拉扯。
- **追蹤與隱私的界線**：加入更多退信與追蹤標頭有助於治理，卻也增加了使用者資料的流動。
