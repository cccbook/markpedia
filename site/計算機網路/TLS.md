# TLS

> 隸屬：[計算機網路] › [應用層協定]　·　狀態：初稿

> 對應維基百科：[中文維基百科：傳輸層安全性協定](https://zh.wikipedia.org/wiki/%E5%82%B3%E8%BC%B8%E5%B1%A4%E5%AE%89%E5%85%A8%E6%80%A7%E5%8D%94%E5%AE%9A)　·　[English Wikipedia: Transport Layer Security](https://en.wikipedia.org/wiki/Transport_Layer_Security)

TLS（傳輸層安全性）是**在兩端點之間建立加密通道的協定**，它讓上層的應用程式可以用「一條可信的位元組流」取代明文的連線。TLS 的三個保證是：內容不被第三方讀取、內容不被第三方竄改、對端的身分可被驗證。

TLS 與其說是「加密協定」，不如說是一套**信任鏈的工程**。它的核心不是密碼學本身（密碼學由底層套件提供），而是「如何把一個離線的公鑰與一個具體的網站名稱綁在一起」——這件事由憑證鏈、憑證透明性日誌與瀏覽器內建的信任根共同完成。TLS 交握只是把這條信任鏈驗證給對方看。

TLS 1.3 是一次大幅簡化的重設計：移除了無法提供前向安全性的靜態 RSA 金鑰交換與 CBC 模式，改以橢圓曲線臨時金鑰交換為唯一路徑，並把交握往返次數由兩次壓縮到一次（以會話恢復與 0-RTT 為例則可更少）。同時，它把許多過去由擴充協定實作的功能（如伺服器名稱指示）併入核心規範。

## 技術與理論的關聯

- **認證加密的合併**：現代 TLS 只允許同時提供機密性與完整性的模式，例如以 AES-GCM 或 ChaCha20-Poly1305 實作；分開的「加密模式」與「雜湊模式」組合方式已被移除，因為它們曾產生 padding oracle 類的弱點。
- **臨時金鑰與前向安全**：每次連線都產生新的臨時金鑰，因此即使日後伺服器的長期私鑰外洩，先前錄下的流量仍無法被解密。這是「前向安全」在工程上的落實。
- **握手訊息與狀態碼**：TLS 以明確的握手類型（客戶端歡迎、伺服器歡迎、憑證、請求、finished）編號構成交握流程，並以警報代碼回報錯誤，格式上與 HTTP 的狀態碼屬於同一類設計。
- **憑證鏈與信任模型**：憑證由根憑證機構簽發、逐層簽署，客戶端驗證的是「這條鏈是否能連到我預設信任的根」。這是一個以 [離散數學] 中偏序與簽章結構表達的信任模型。
- **與 [DNS] 的關聯**：伺服器名稱指示讓伺服器在交握初期就知道要出示哪張憑證，而驗證端仍須自行查詢名稱以核對憑證中的名稱。
- **與 [資訊安全] 的關聯**：TLS 是「安全下沉」的典範——它不專屬於任何單一應用，而是讓所有承載其上的應用層協定自動獲得保護。

## 範例

**範例：一次 TLS 1.3 交握的時序。**

1. **TCP 交握**：客戶端先與伺服器完成三向交握。此步驟不可省略（除非承載於 [QUIC] 之上，因為 QUIC 把傳輸與交握整合）。
2. **客戶端初速**：客戶端發出初步握手訊息，內含支援的加密套件清單、一組臨時金鑰的公開部分、一個隨機值，以及支援的應用層協定指示（例如以 HTTP/2 或 HTTP/3 交握）。
3. **伺服器回應**：伺服器回覆其選定的加密套件與臨時金鑰公開部分，並送出具備數位簽章的憑證；簽章涵蓋前兩個訊息的內容，用以證明伺服器持有該憑證對應的私鑰。
4. **金鑰導出**：雙方各自以交握中的密碼學材料導出對稱金鑰。此金鑰用於後續記錄層的加密與完整性保護。
5. **驗證憑證**：客戶端驗證憑證鏈是否連到預設信任根、憑證是否在有效期內、憑證上的名稱是否與自己連線的目標名稱相符。若名稱不符，即使鏈有效也必須中止。
6. **完成訊息**：雙方各送出一則完成訊息，內含對交握全程的雜湊值，用來確認中途未被竄改。
7. **記錄層**：此後資料以記錄層傳送，每筆記錄含類型、版本、長度、加密後的內容與驗證標籤。
8. **交握完成後**：應用層資料（如 [HTTP] 請求）才開始流動；伺服器此時才會讀到請求內容。
9. **延遲的代價**：上述步驟在跨洲連線上會額外增加一個往返的時間，這正是 [QUIC] 把交握併入傳輸建立過程以降低首屏延遲的原因。
10. **續用與恢復**：後續請求若能重用既有連線或恢復先前的工作階段，便可完全跳過交握，這是瀏覽器開啟多個連線時的標準做法。

這個時序說明：**TLS 的成本集中在連線建立階段，而不是資料傳輸階段**，因此「能否重用連線」往往比「單次傳輸效率」更影響使用者感受。

## 前因後果

- **前因**：1990 年代的網際網路在企業與研究機構之外幾乎不使用；使用者無法放心地在網路上輸入帳號與信用卡號，商業化因此受到限制。
- **後果**：TLS 成為網際網路的預設配備，明文協定的支援逐漸被移除；同時它把憑證頒發機構、憑證透明性日誌與自動化驗證推成一整套供應鏈，也催生了對過期憑證、錯誤簽發與私鑰外洩等事件的高度關注。
- **互相驅動**：加密普及使網路核心無法觀測內容，直接削弱了中間設備的能力，這反過來促成 [QUIC] 把整個加密與傳輸層搬進使用者空間；[DNS] 的加密查詢則是把同一套信任鏈應用到名稱解析的結果。

## 與相鄰分類的關聯

- 與 [HTTP] 的關係：HTTP 幾乎總是在 TLS 之上執行，人們常說的「HTTPS」其實是 HTTP 承載於 TLS 通道。
- 與 [QUIC] 的關係：QUIC 以自己的方式實作加密並把交握與傳輸整合，其 TLS 1.3 子集只保留了交握所需的訊息類型。
- 與 [TCP] 的關係：TLS 1.3 在 [TCP] 之上運作時，交握佔去一個以上的往返；[UDP] 之上則無法直接使用同一套握手。
- 與 [DNS] 的關係：憑證中的名稱必須與解析結果相符，兩者的串接構成了整個加密信任的起點。
- 在上位子分類 [應用層協定] 中，TLS 是少數不對應特定應用功能、而是提供通用保護的成員。

## 容易混淆之處

- **TLS 不等於 HTTPS**：HTTPS 是 HTTP 在 TLS 上的應用；TLS 本身也可承載其他協定。
- **加密不等於驗證身分**：若用戶端未驗證憑證，連線仍可加密，但對端可能是任何人。
- **小鎖圖示不等於已驗證**：瀏覽器對部分內容只顯示提示而非明確標示，涉及憑證錯誤時尤其如此。
- **TLS 不保護使用者身分**：憑證驗證的是網站，不是使用者；使用者身分仍需由應用層的登入機制處理。
- **舊版協定不等於舊套件**：TLS 1.2 仍可安全使用，真正危險的是特定版本搭配特定套件。
- **交握時間長不等於頻寬不足**：兩者的瓶頸不同，診斷方向也完全不同。

## 技術要點

- 一律停用舊版協定與已知有問題的加密套件，並讓交握失敗時明確拒絕而非降級。
- 憑證應涵蓋所有實際使用的名稱，並以自動化方式監控到期日。
- 應啟用交握訊息加密，避免協商過程被中間人修改。
- 應啟用 session resumption 與 0-RTT，但須注意 0-RTT 資料具重放風險。
- 記錄層應採用對錯誤敏感的加密模式，並避免重複使用相同的初始化向量與金鑰。
- 應對連線與交握分別設定逾時，避免慢速攻擊佔用資源。

## 常見的論爭

- **加密普及削弱中間可見性**：對內容進行深度檢測的需求與端到端加密的原則相衝突，產業界與執法單位的立場長期分歧。
- **自動化的信任程度**：自動化憑證與自動續期大幅降低了成本，但也讓憑證失誤的影響範圍擴大到整批網站。
- **使用者空間協定是否應取代核心實作**：把加密與傳輸移出核心可加速演進，代價是失去硬體卸載與網路層的可觀測性。
