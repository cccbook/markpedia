# 應用層協定

> 隸屬：[計算機網路]　·　狀態：初稿

> 對應維基百科：[中文維基百科：應用層](https://zh.wikipedia.org/wiki/%E5%BA%94%E7%94%A8%E5%B1%82)　·　[English Wikipedia: Application layer](https://en.wikipedia.org/wiki/Application_layer)

應用層協定是**直接對應使用者需求的高層協定**。它們定義了資料的意義與格式：如何取得一個網頁、如何把名字解析成位址、如何寄送郵件、如何在兩端建立安全的通道。

與下層協定相比，應用層協定的特徵是它們**由具體的應用需求驅動**。[HTTP] 的存在是為了取得文件，[DNS] 是為了讓人記得住名字，[SMTP] 是為了把訊息送到收件人，[TLS] 則是為了讓其下所有的應用都能在不被人偷看的前提下運作。因此應用層協定的演化史，很大程度上就是使用習慣與商業模式的演化史。

## 技術與理論的關聯

- **自描述訊息與狀態碼**：多數應用層協定使用文字或半文字格式的訊息，理由之一是可讀性——代理、防火牆與人類都能理解它們；HTTP 的狀態碼分類（以首位數字分組）正是此設計的極致。
- **快取語意**：HTTP 的快取控制以「快取鍵」與「驗證條件」為核心，是內容散發網路能減少回源流量的基礎；它把一個分布式的問題（副本何時一致）化為可攜帶的宣告。
- **名稱與位址的分離**：[DNS] 把易記的名字與路由用的位址解耦，使得名稱可以獨立於拓樸變更；這是位址之外另設名字系統的根本理由。
- **安全作為基礎設施**：[TLS] 不專屬於任何一種應用，而是作為承載層保護所有上層協定，這種「安全下沉」的設計大幅降低了應用層的重複實作成本。
- **與 [演算法] 的關聯**：名稱解析的快取與排程、內容分發的一致性、路徑選擇，都是演算法問題。
- **與 [離散數學] 的關聯**：快取鍵與查詢的映射、狀態碼的有限狀態機、版本與相容性矩陣，皆可形式化。

## 範例

**範例：一次網頁載入牽涉的四個應用層協定。**

1. **名稱解析**：使用者輸入網域名稱，瀏覽器先查本地快取；未命中則向遞迴 [DNS] 伺服器查詢，該伺服器可能再向上游查詢並回應。回應中的位址依目前的位址族政策決定，可能包含多筆位址供客戶端選擇。
2. **安全通道**：瀏覽器與伺服器建立 [TLS] 連線，在此過程中驗證伺服器憑證、協商加密套件並建立金鑰。此步驟常佔首次載入延遲的大部分，QUIC 把它與傳輸交握合併正是為了壓縮此處成本。
3. **取得資源**：瀏覽器發出 [HTTP] 請求；伺服器回應狀態碼與內容。主頁通常還會引出數十個子資源請求（樣式表、指令碼、字型、影像），它們可被多工並行發出。
4. **郵件遞送**：若頁面含表單要寄信，郵件伺服器以 [SMTP] 遞送訊息。SMTP 的設計源於早期網際網路的批次式傳遞模型，如今多以加密通道承載。
5. **快取與一致性**：HTTP 回應中的快取標頭決定瀏覽器與中間快取是否直接使用既有副本；若副本過期，則以條件式請求（帶著實體標籤或最後修改時間）向來源確認。
6. **實際體驗**：上述四個步驟的延遲會疊加，而其中 DNS 查詢通常無法被瀏覽器最佳化（瀏覽器不知道目標位址之前無法連線）。這解釋了為什麼 DNS 快取與預解析是網站效能的重要手段。

## 實務觀察

應用層協定的維運難題，通常集中在**「看似簡單、實際不可控」的資源上**。以 DNS 為例，一次查詢的成本極低，但當查詢量足以影響解析服務時，就需要在架構層設計快取、預解析與用量控管；以 HTTP 為例，單一請求成本不高，但複數用戶乘以多個資源乘以重試，就足以形成壓力。這類「乘法效應」是應用層效能治理的主要對象。

另一個觀察是**版本的長尾**。任何一個仍在服役的應用層協定版本，都代表一份必須持續維護的相容邏輯與一組潛在的行為分歧；當產品線上同時存在多個版本時，除錯時必須先確定版本，才能正確解讀行為。良好的版本管理與版本可觀測性（能從日誌看出請求使用了哪一版）是應用層維運的基本功。

第三點是**降級路徑的必要性**。應用層協定幾乎都存在「舊版用戶端」與「受限網路」兩種情況；事先設計好降級行為，比在事故中臨機處置可靠得多。

## 前因後果

- **前因**：1980 年代末至 1990 年代初，TCP/IP 之上需要一套能讓非資訊專業人士使用的應用協定；電子郵件、檔案傳輸與新聞群組是當時最迫切的需求。
- **後果**：HTTP 與 DNS 的普及使網際網路從研究社群擴展為公共服務；TLS 的普及則把加密從少數專業領域推廣為網路基礎設施的預設。
- **互相驅動**：[傳輸協定] 的進步（例如 [QUIC]）直接改變應用層的可行方案，促成 HTTP/3；[無線網路] 的行動性也催生了對輕量與節省資料的應用層設計。

## 容易混淆之處

- **應用層不等於使用者可見的功能**：[TLS] 與 [DNS] 幾乎不會出現在畫面上，卻是典型的應用層協定。
- **HTTP 不只是取得網頁**：它也承載 API、事件串流與檔案傳輸，方法與狀態碼的組合遠多於日常瀏覽。
- **DNS 不等於只有一筆位址**：回應可含多筆不同類型的記錄，並可透過快取與預解析最佳化。
- **SMTP 不等於收信**：SMTP 負責遞送；使用者讀信通常使用其他協定，這是歷史上反覆出現的困惑來源。
- **TLS 不等於驗證身分**：TLS 提供加密與（可選的）伺服器驗證；用戶端身分需另外機制。
- **狀態碼不必嚴格遵守**：應用層協定的可擴充性正是靠「忽略不認识的狀態」來實現的。

## 技術要點

- 應用層訊息應自描述，並對未知欄位採忽略而非拒絕，以維持可擴充性。
- 快取控制應明確指定驗證條件，讓分散的副本能以一致方式更新。
- 對同一主機的請求應多工並行，並為資源設定合理的優先順序。
- 逾時應分階段設定：連線建立、位元組讀取與整體請求各有不同的合理值。
- 所有應用層協定都應假設中間設備存在，並設計能在其限制下運作的降級路徑。
- 版本協商應在連線初期完成，並保留對舊版本的相容路徑。

## 常見的論爭

- **加密普及造成的可觀測性下降**：當應用層內容加密，網路設備無法再看到內容，深度檢測與威脅情報的價值被迫重新定位。
- **文字格式的效率代價**：文字格式易讀但佔頻寬，對行動網路與物聯網的影響尤為明顯，是否改用二進位格式仍有討論。
- **協定膨脹與版本兼容**：長期演進使協定保留大量舊版相容邏輯，是複雜度的主要來源之一。
