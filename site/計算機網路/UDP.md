# UDP

> 隸屬：[計算機網路] › [傳輸協定]　·　狀態：初稿

> 對應維基百科：[中文維基百科：用户数据报协议](https://zh.wikipedia.org/wiki/%E7%94%A8%E6%88%B7%E6%95%B0%E6%8D%AE%E6%8A%A5%E5%8D%8F%E8%AE%AE)　·　[English Wikipedia: User Datagram Protocol](https://en.wikipedia.org/wiki/User_Datagram_Protocol)

UDP 是**極簡的傳輸層協定**：它只做一件事，把應用交來的資料封裝成封包並交給網路層，不提供可靠性、不保證順序、不做流量控制，也不回應確認。

UDP 的設計哲學是「**少即是多**」。它把位元組串抽象、序號、視窗與重傳計時器全部省去，換來的代價是應用層必須自行處理遺失、重複與亂序。這在某些情境下是明確的優勢：即時音訊、影片串流、線上遊戲、域名查詢與負載均衡探測，這些應用的共同特徵是「**過期的資料沒有價值**」——遲到的確認包與丟棄的畫格相比，並不更有用。

## 技術與理論的關聯

- **無狀態端點**：UDP 沒有連線狀態，伺服器可同時處理數十萬個用戶端而不維護連線表格，這是它能支撐高併發的原因。
- **應用層自行實作可靠性**：藉由選擇性確認、序號與重傳，應用可只為真正重要的資料付費；這是「端對端原則」最直白的實踐之一。
- **報文邊界的保留**：UDP 保留應用送出的訊息邊界，接收端每次讀取得到一個完整資料報；相較於 TCP 的位元組串抽象，這在協定設計上更貼近應用的心智模型。
- **多播與廣播的支援**：UDP 是 IP 多播與廣播的傳輸載體，這些在 [路由] 層有對應的機制，是 TCP 無法提供的。
- **與 [演算法] 的關聯**：應用層自行實作的可靠傳輸與速率控制，是 [可靠傳輸] 領域研究的原型。
- **與 [離散數學] 的關聯**：資料報邊界的保留使訊息單位保持離散，簡化了並發處理的組合性分析。

## 範例

**範例：線上遊戲的封包策略。**

1. **需求**：玩家的操作與伺服器的狀態更新必須盡快送達，遲到 100 毫秒的移動指令已無意義；但連線中斷時伺服器寧可推算位置，也不要讓玩家卡住等待重傳。
2. **選擇 UDP**：遊戲程式直接以 UDP 資料報送出操作，並在應用層自訂序號與時間戳；收到封包時，若序號比已處理的新且時間戳合理，即套用，否則丟棄。這正是「選擇性可靠」的典型實作。
3. **伺服器端**：伺服器同樣以 UDP 回送狀態更新，並以「快照 + 差分」的方式壓縮資料量，避免封包過大造成分片。
4. **併發多連線**：應用層使用多條 UDP 連線分別承載互動、語音與一般資料，避免單一流程的遺失拖累其他用途——這是應用層自行實現多路流的做法。
5. **速率控制**：應用層實作自己的速率限制，因為 UDP 本身沒有任何內建機制；若不限制，一個失控的客戶端即可對伺服器造成 [阻斷服務] 式的衝擊。
6. **安全性**：UDP 無連線狀態的特性使其容易被用來做放大攻擊，因此服務商必須限制回應大小與查詢速率；[DNS] 的遞迴查詢尤其需要這類防護。
7. **對照**：若改用 TCP，遺失的操作會被要求重傳，且 TCP 的連線建立握手在每次重新連線時都會增加延遲，整體互動體感明顯變差。

## 前因後果

- **前因**：1980 年代初，網際網路的應用多屬於「一次請求一次回覆」型態，對延遲敏感但對遺失容忍度高；同時網際網路社群擔心 TCP 的複雜狀態機會讓核心路由器不堪負荷，因此堅持把可靠性放在端點。
- **後果**：UDP 幾乎立刻成為域名解析、簡單網路時間協定、語音與多媒體傳輸的基礎；近年則因 [QUIC] 以 UDP 為基礎重新獲得重要性，成為整個傳輸層革新的支點。
- **互相驅動**：[TCP] 的頭部阻塞問題促成 QUIC 選擇以 UDP 承載；[應用層協定] 中的即時性需求則推動應用層自建可靠機制。

## 容易混淆之處

- **UDP 不等於不可靠的網路**：UDP 只是不提供可靠性，底層網路該遺失還是會遺失。
- **UDP 不等於無連線**：應用可自行維護邏輯上的「連線」概念。
- **UDP 不保證送達也不保證不重複**：這兩點常被混淆，實際上 UDP 連「不重複」都不保證。
- **UDP 不支援多工**：一條 UDP 連線不能同時處理多個應用流程，這需要應用層自行以埠號區分。
- **UDP 與 DTLS 配合才安全**：單獨使用 UDP 沒有機密性與完整性，需搭配其他機制。
- **DNS over UDP 不等於 DNS 全部**：較大的回應會改用 TCP 或以加密通道傳輸。

## 設計取捨

UDP 與 TCP 的選擇，本質上是「把複雜性放在哪裡」的選擇。

## 實務觀察

在生產環境中選用 UDP 時，最容易被忽略的一點是**應用層的隱藏成本**。以 UDP 實作「選擇性可靠」並不困難，但把它做對需要處理：序號回繞、封包重複、乱序到達、時鐘偏移造成的時間戳不可比、以及多條流之間的公平性。缺少任何一項，都可能在高負載或長連線下出現難以重現的異常。

另一個實務重點是**觀測性**。UDP 沒有內建狀態，網路設備與負載均衡器難以依連線追蹤流量；因此以 UDP 為基礎的服務通常需要在應用層自建指標（例如自行追蹤遺失率與重傳率），並讓這些指標成為告警的主要依據。相較之下，TCP 的狀態可被中間設備直接觀測，這在除錯時是實質的優勢。

第三點是**傳輸安全性必須另外安排**。由於 UDP 本身不提供機密性與完整性，任何以它為基礎的對外服務都必須明確決定是否搭配加密層；若答案含糊，通常就是安全 posture 最薄弱的環節。

## 技術要點

- 應用層必須自行處理序號、重複與時間戳，才能達到選擇性可靠。
- 資料報應控制在路徑最大傳輸單位以下，避免 IP 分片帶來的額外開銷與風險。
- 多工由應用以不同來源埠號或明確的協定識別解決。
- 伺服器端須實作速率限制與查詢大小上限，防止被用作放大攻擊的跳板。
- 若需機密性與完整性，應搭配 DTLS 或在應用層自行加密。
- 對即時資料應設定有效的生命週期，過期封包直接丟棄而非排隊等待。

## 常見的論爭

- **是否應保留 UDP**：隨著 QUIC 與 DTLS 的成熟，UDP 已不只是「簡單協定」，但其缺乏內建安全與流控的特性仍讓部分工程師認為易被誤用。
- **由誰負責速率控制**：UDP 把負擔推給應用，這在分散式系統中難以強制落實。
- **放大攻擊的責任歸屬**：反射與放大現象根源於網際網路設計，業界對是否應在核心層強制過濾仍有分歧。
