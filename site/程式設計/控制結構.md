# 控制結構

> 隸屬：[程式設計]　·　狀態：初稿

> 對應維基百科：[中文維基百科：控制流程](https://zh.wikipedia.org/wiki/%E6%8E%A7%E5%88%B6%E6%B5%81%E7%A8%8B)　·　[English Wikipedia: Control flow](https://en.wikipedia.org/wiki/Control_flow)

控制結構是**決定程式執行路徑的語言機制**：順序執行是預設，分支讓程式「依條件選路」，迴圈讓它「重複直到滿足條件」，遞迴讓它「以自我呼叫分解問題」，例外處理讓它「在錯誤發生時改道」。1968 年 [狄克斯特拉] 的〈Go To 語句有害論〉把這個領域從雜亂的 goto 自由帶進「結構化程式設計」的紀律——任何程式都可以只由順序、分支與迴圈三種結構組成，且每種結構只有一個入口與一個出口。

## 技術與理論的關聯

- **結構化定理**：Böhm–Jacopini（1966）證明任何可計算函式都可只用順序、選擇與迴圈表達；這為 goto 的退場提供了理論依據，也奠定了第三層四個孫分類（分支、迴圈、遞迴、例外處理）的分類框架。
- **分支與迴圈互為底層**：組合語言層次只有條件跳躍（branch）與無條件跳躍（jump）；高階語言的 `while` 迴圈就是「條件成立時跳回開頭」的語法糖。
- **遞迴與迴圈可互相轉換**：任何遞迴皆可改寫成以明確堆疊（stack）驅動的迴圈；尾遞迴（tail recursion）是兩者完全等價的特殊情況，支援尾呼叫最佳化的語言可把它編譯成跳躍。
- **例外處理是「非局部跳躍」的受控形式**：它取代了 C 風格的錯誤碼回傳檢查（每個呼叫點都要 `if (err != NULL)`），把錯誤路徑從正常路徑中分離；代價是控制流圖變得不顯而易見。
- **結構化控制是多典範的共同底座**：函式式的 `map`/`filter` 是「不寫出來的迴圈」，SQL 的 `WHERE` 是「不寫出來的分支」；典範可以改變控制結構的寫法，但不改變其語意角色。
- **迴圈不變量是正確性工具**：證明迴圈正確的標準方法是找出一個每次迭代前後都成立的性質；這也是 [演算法] 分析與程式驗證的核心技巧。

## 範例：同一個搜尋的四種控制寫法

需求：在已排序陣列中找目標值（二分搜尋）。

**迴圈版**：

```
def binary_search(a, target):
    lo, hi = 0, len(a) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if a[mid] == target:
            return mid
        elif a[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1
```

**遞迴版**：

```
def search(a, target, lo, hi):
    if lo > hi:
        return -1
    mid = (lo + hi) // 2
    if a[mid] == target:
        return mid
    if a[mid] < target:
        return search(a, target, mid + 1, hi)
    return search(a, target, lo, mid - 1)
```

**例外驅動版**（失敗以例外表達）：

```
class NotFound(Exception):
    pass

def search_or_raise(a, target, lo, hi):
    if lo > hi:
        raise NotFound(target)
    mid = (lo + hi) // 2
    if a[mid] == target:
        return mid
    ...
```

呼叫端用 `try/except` 把「找不到」與正常流程分開。三個版本同為 $O(\log n)$ ，但控制形態不同：迴圈版狀態顯式、遞迴版狀態在參數中（更貼近數學定義、易證明）、例外版把異常路徑推向語言機制。何者最宜，取決於語言的尾呼叫支援、團隊慣例與錯誤的「常態或異常」定性。

## 前因後果

- **前因**：早期組合語言以 goto 自由跳躍，程式一大，控制流圖變成「義大利麵條」；結構化程式設計運動以「單一入口、單一出口」的方塊取代跳躍，使程式可由上而下閱讀與驗證。
- **後果**：結構化控制成為所有主流語言的預設；例外處理把錯誤管理從「回傳碼紀律」升級為語言機制；函式式組合子（map、reduce）進一步把常見迴圈模式收進函式庫。控制結構的紀律化也直接支援了 [軟體工程] 的程式碼審查與靜態分析——可審的控制流圖才能被機器檢查。

## 與相鄰分類的關聯

- 與 [語言典範] 的關係：命令式直接寫控制結構；函式式與宣告式把它們藏進組合子與引擎，但語意等價。
- 與 [型別系統語法] 的關係：現代語言把分支與型別結合——列舉型別加窮舉 `match`，讓「新增一種情況而忘記處理」從執行期 bug 變成編譯期錯誤。
- 與上位概念 [程式設計] 的關係：控制結構是程式行為的最小積木；無論抽象多高，執行本體終究是這幾種結構的組合。

## 容易混淆之處

- **break/continue 會破壞「單一出口」**：它們是結構化紀律的局部讓步，多數語言接受，但多重出口會增加推理負擔。
- **遞迴深度不是無限的**：每層呼叫占用堆疊，Python 預設深度約一千層；深遞迴應改迴圈或提高堆疊上限。
- **例外不等於流程控制**：用例外處理「可預期的常態分支」（如以 try/except 檢查鍵是否存在）在效能與可讀性上皆劣於分支。
- **do-while 與 while 的差異在首輪**：前者保證至少執行一次，條件翻譯錯誤常藏在這裡。

## 技術要點

- 三種基本結構（順序、選擇、重複）加單一出口，即可表達一切可計算函式（Böhm–Jacopini）。
- 迴圈三要素：初始化、繼續條件、推進；漏掉任何一項即死迴圈或漏處理。
- 尾遞迴在支援尾呼叫最佳化的語言（Scheme、Kotlin 的 `tailrec`）中與迴圈同效。
- 例外處理的成本在「拋出」與「堆疊解開」，不在 try 本身；熱路徑中避免以例外為常態。
- 多層巢狀是可讀性殺手：提早返回（early return）、衛語句（guard clause）與提取函式是標準解法。
- 迴圈不變量既是證明工具也是除錯工具：把「迭代前後應成立的性質」寫成斷言（assert），可在測試中自動檢查。

## 常見的論爭

- **goto 是否全然有害**：狄克斯特拉的論文引發數十年辯論；C 語言中 goto 用於錯誤清理仍是 Linux 核心的慣例，說明「有害」針對的是無紀律跳躍，不是關鍵字本身。
- **例外 vs 回傳錯誤碼**：Rust 以 `Result` 型別（一種型別層的錯誤碼）取代例外，主張錯誤路徑應顯式可見；Java 與 Python 陣營則認為例外減少噪音。兩派各有支援者。
- **遞迴教學地位**：函式式陣營視遞迴為思考問題結構的利器；工業陣營指出多數語言無尾呼叫最佳化，實務應以迴圈為預設。
