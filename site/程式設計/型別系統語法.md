# 型別系統語法

> 隸屬：[程式設計]　·　狀態：初稿

> 對應維基百科：[中文維基百科：類型系統](https://zh.wikipedia.org/wiki/%E9%A1%9E%E5%9E%8B%E7%B3%BB%E7%B5%B1)　·　[English Wikipedia: Type system](https://en.wikipedia.org/wiki/Type_system)

型別系統是**語言用來給值分類、並在分類上做正確性檢查的規則集**：它替每個值貼上「這是整數」、「這是文字」、「這是會拋例外的動作」之類的標籤，然後拒絕讓不相容的標籤組合在一起。型別系統的本質是一份機器可檢查的規格——程式師把「這個函式不接受字串」這類意圖寫進型別，編譯器或直譯器就在每個呼叫點免費驗證一次。

## 技術與理論的關聯

- **檢查時機劃分兩大陣營**：靜態型別在程式執行前檢查（編譯期），動態型別在執行中檢查（執行期）；差別不是「有無型別」，而是錯誤被發現的時間點與代價。
- **理論根據是 Curry–Howard 對應**：型別對應命題、程式對應證明；「通過型別檢查」因此是一種（有限的）自動證明。這讓 [數學] 與程式設計在型別理論上直接交會。
- **型別推論讓靜態語言擺脫冗長註記**：ML 家族證明編譯器可從用法反推型別（Hindley–Milner 演算法）；現代語言的 `auto`、`var`、`let` 皆是其餘緒。
- **泛型是「對型別的抽象」**：寫一次 `List<T>` 的程式碼，對所有元素型別都安全可用；實作方式分為編譯期單態化（C++ 模板、Rust）與執行期抹除（Java 型別抹除）。
- **強弱與動靜是兩個正交的軸**：Python 動態但強（不會悄悄把字串變整數），C 靜態但弱（指標可任意轉型）；四個象限各有代表語言。
- **漸進型別（gradual typing）是當代折衷**：TypeScript 與 Python 的型別提示（type hints）允許同一專案「關鍵部分有型別、邊角部分無型別」，反映工程現實的異質性。

## 範例：同一個錯誤在靜態與動態下的遭遇

需求：把兩個數相加。假設某處誤傳了字串。

**靜態型別（Rust）**——編譯期拒絕：

```
fn add(a: i64, b: i64) -> i64 {
    a + b
}

fn main() {
    let x: i64 = 10;
    let s: &str = "oops";
    // add(x, s);  ← 編譯錯誤：expected `i64`, found `&str`
    println!("{}", add(x, 5));
}
```

**動態型別（Python）**——執行期才爆炸：

```
def add(a, b):
    return a + b

x = 10
s = "oops"
print(add(x, 5))    # 15，正常
print(add(x, s))    # 執行到這行才拋 TypeError
```

**漸進型別（Python 型別提示 + 靜態檢查器）**——兩者之間：

```
def add(a: int, b: int) -> int:
    return a + b

add(x, s)  # mypy 在執行前報錯，但直譯器仍可運行未檢查的部分
```

三段程式展示了型別系統的真正交易：**錯誤發現時間**提前（省下線上事故）換取**書寫約束**增加（要標型別或說服檢查器）。型別推論與漸進型別正是為了降低後者的成本而生。

## 前因後果

- **前因**：1950 年代的 Fortran 與 Lisp 已有原始型別（整數、浮點、串列），但真正把型別變成理論體系的是 1960–70 年代的 ALGOL 68、ML 與 Curry–Howard 對應的研究；驅動力是「編譯器能否自動抓錯」。
- **後果**：靜態型別使大型重構成為可能——改一個函式簽名，編譯器指出所有受影響處；泛型使標準函式庫（容器、演算法）得以安全泛化；漸進型別讓 JavaScript 生態（TypeScript）與 Python 資料科學生態在不受重寫成本拖累下逐步加固。

## 與相鄰分類的關聯

- 與 [語言典範] 的關係：函式式典範的函數組合依賴型別簽名可推導；物件導向的多型本身就是一種型別機制（子型多型）。
- 與 [控制結構] 的關係：型別決定控制結構的合法形狀——例如 Rust 的 `match` 要求窮舉所有列舉變體，把「漏處理一種情況」變成編譯錯誤。
- 與上位概念 [程式設計] 的關係：型別系統是「寫下來的程式確實是我想寫的程式」的第一道機器可驗證防線。

## 容易混淆之處

- **靜態不等於強**：兩個軸正交；C 是靜態弱型別，Python 是動態強型別。
- **型別註記不等於測試**：型別能抓「形狀錯誤」，抓不到「商業邏輯錯誤」（如年齡被設成負數，除非用 refinement type）。
- **泛型不等於巨集**：C++ 模板雖以文字展開實作，語意上是型別層的抽象；兩者的錯誤訊息與除錯體驗截然不同。
- **動態型別不等於較慢**：JIT 可消除大部分動態派送成本；效能差異主要看實作，不看動靜。

## 技術要點

- 靜態檢查在執行前完成，代價是更多前置註記與較慢的建置；動態檢查在執行中完成，代價是錯誤後置。
- Hindley–Milner 推論可在不寫任何型別標註下完全推導，是 ML 與 Haskell 的基石。
- 泛型兩大實作路線：單態化（每型別各生一份機器碼，快但二進位大）與抹除（共用一份碼，省空間但失去執行期型別資訊）。
- 結構型別（structural，TypeScript）與名目型別（nominal，Java）決定「兩個型別何時相容」的判準。
- 型別系統的表達力有上限：完整型別檢查不可判定，實用系統選擇「可判定但保守」，寧可拒絕部分正確程式也不放進錯的。
- 漸進型別的設計核心是「任何標註都不改變執行期行為」，讓型別可以漸進採用。

## 常見的論爭

- **靜態 vs 動態**：長達數十年的陣營之爭；近年共識趨向「依專案規模與變更頻率選擇」，漸進型別則試圖直接終結爭論。
- **型別註記是文件還是噪音**：一派認為簽名是最可靠的自動更新文件；另一派認為推論已足、註記只增加維護面積。
- **型別系統該多強**：Coq/Agda 的依值型別可證明任意性質，但學習與生產成本高；工業語言停在「抓常見錯誤」的性價比點，界線持續右移。
