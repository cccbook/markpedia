# 開發方法

> 隸屬：[程式設計]　·　狀態：初稿

> 對應維基百科：[中文維基百科：软件开发过程](https://zh.wikipedia.org/wiki/%E8%BD%AF%E4%BB%B6%E5%BC%80%E5%8F%91%E8%BF%87%E7%A8%8B)　·　[English Wikipedia: Software development process](https://en.wikipedia.org/wiki/Software_development_process)

開發方法是**讓一群人持續、可靠地改同一份程式碼的組織技術**：它不回答「怎麼寫這行程式」，而回答「先寫測試還是先寫實作」、「改動如何合併」、「誰在合併前看過這段碼」。當程式從個人作品變成團隊產物，錯誤的傳播速度與合併衝突的頻率成為主要瓶頸；版本控制、測試驅動、程式碼審查與敏捷流程就是針對這些瓶頸的四件標準配備。與偏重流程與管理面的 [軟體工程] 相比，本子分類聚焦在工程師每天的具體操作。

## 技術與理論的關聯

- **版本控制是一切的地基**：以不可變的提交（commit）圖記錄歷史，使「回到過去」與「平行開發」成為可能；Git 的分散式模型把「誰有權威版本」的問題交給了社會流程而非技術。
- **測試驅動開發（TDD）反轉寫作順序**：紅（寫失敗的測試）→ 綠（寫最少程式讓它通過）→ 重構；測試從「事後檢查」變成「事前規格」。
- **程式碼審查是品質與知識的雙重通道**：研究與業界經驗一致顯示，審查抓到的多數不是 bug 而是可讀性與設計問題；審查同時是團隊知識傳播的主要手段（見 [程式碼審查]）。
- **敏捷是對瀑布式流程的回應**：需求會變，因此以短週期迭代取代一次性的長期計畫；[敏捷] 宣言的四條價值（個體互動、可運作的軟體、客戶協作、回應變化）都是針對「計畫趕不上變化」的對症下藥。
- **持續整合（CI）把「合併」變成日常**：每次提交都自動建置與跑測試，使整合痛苦從「數月一次的大爆炸」變成「每天數次的小打小鬧」。
- **方法與工具互相塑形**：分支策略（如主幹開發）影響合併衝突頻率；測試金字塔影響 CI 時長；工具反過來約束了方法的可行形態。

## 範例：一個改動在四件配備下的完整生命週期

需求：在購物車加入「滿額折扣」功能。

**第一步：版本控制——開分支**：

```
git switch -c feature/bulk-discount
```

**第二步：測試驅動——先寫失敗的測試**：

```
def test_discount_applied_over_1000():
    cart = Cart()
    cart.add("書", price=600)
    cart.add("筆", price=500)
    assert cart.total() == 1050   # 1100 打 95 折
```

**第三步：最小實作讓測試通過**：

```
def total(self):
    raw = sum(i.price for i in self.items)
    return round(raw * 0.95) if raw >= 1000 else raw
```

**第四步：提交並發起審查**：

```
git commit -am "購物車滿額折扣"
git push -u origin feature/bulk-discount   # CI 跑全部測試
```

**第五步：審查與合併**：同事在 Pull Request 上留言「折扣率 0.95 應設為常數並可設定」，作者修改後 CI 重跑轉綠，審查者核准，合併回主幹。

這五步把四件配備串成一個循環：版本控制隔離變更、TDD 定義規格、CI 自動驗證、審查傳播知識。敏捷迭代（通常一至兩週）只是把這個循環包在固定的交付節奏裡。

## 前因後果

- **前因**：1960–70 年代的「軟體危機」——專案超時、超支、品質失控——暴露了「英雄式個人寫作」的極限；[高德納] 與 [狄克斯特拉] 等人率先把程式設計當作可分析的工程活動討論，實務端則由軍方與 IBM 的品管程序累積出最初的方法論。
- **後果**：版本控制演化出開源協作模式（fork、Pull Request），反過來重塑了整個軟體產業的分工；CI/CD 與 DevOps 把開發與維運合流（更完整的流程觀點見 [軟體工程]）；而測試與審查的資料累積，正成為 AI 輔助編程（自動修 bug、生成測試）的訓練素材。

## 與相鄰分類的關聯

- 與 [軟體工程] 的關係：開發方法是軟體工程在「工程師日常」層次的落實；軟體工程談專案生命週期，本子分類談提交、測試與審查的具體循環。
- 與 [控制結構] 的關係：可測試性取決於控制結構的形態——單一出口與少量巢狀的函式易於單元測試，深巢狀與多出口則讓測試案例指數成長。
- 與上位概念 [程式設計] 的關係：本子分類把「寫好程式」延伸成「持續把程式寫好」，是程式設計的時間維度。

## 容易混淆之處

- **敏捷不等於沒有計畫**：敏捷把計畫縮短且高頻重估，不是取消計畫；無計畫的「敏捷」只是混亂。
- **TDD 不等於覆蓋率**：先寫測試的價值在「以測試驅動介面設計」，不在衝高覆蓋率數字；覆蓋率 100% 的專案仍可能處處測錯方向。
- **版本控制不等於 Git 命令背誦**：核心是提交圖與不可變歷史的概念模型；理解模型後命令只是介面。
- **審查不等於刁難**：審查的對象是程式碼不是人；把審查當成地位競賽是團隊失效的常見原因。

## 技術要點

- 提交應小而聚焦：一次提交對應一個意圖，回滾與審查的成本才可控。
- 測試金字塔：單元測試多而快、整合測試適中、端到端測試少而關鍵；倒金字塔（多數為端到端）是 CI 慢的常見病因。
- 主幹開發與短生命週期分支可降低合併衝突；長期分支是衝突的主要來源。
- 語意化提交訊息與分支命名是最低成本的團隊溝通協定。
- 審查回饋應在數小時到一天內完成，拖延的審查比沒有審查更打擊士氣。
- 「紅—綠—重構」中的重構步驟不可省略：TDD 的長期收益主要來自持續重構而非測試本身。

## 常見的論爭

- **TDD 是否處處值得**：支持者視其為設計工具；反對者指出在探索性原型或以資料為中心的程式中，先寫測試反而拖慢迭代，實務上多採「核心邏輯 TDD、外圍彈性處理」。
- **敏捷是否已被官僚化**：原始宣言反對繁文縟節，但大型組織的「敏捷儀式化」（無盡的站會與看板）被批評為換湯不換藥的流程主義；「重新敏捷」是近年業界持續的自省。
- **審查的嚴格程度**：嚴格審查提高品質但拉長週期、可能壓抑新手；寬鬆審查加快交付但累積技術債。沒有普適答案，只有與團隊風險承受度匹配的平衡點。
