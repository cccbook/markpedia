# 語言典範

> 隸屬：[程式設計]　·　狀態：初稿

> 對應維基百科：[中文維基百科：编程范型](https://zh.wikipedia.org/wiki/%E7%BC%96%E7%A8%8B%E8%8C%83%E5%9E%8B)　·　[English Wikipedia: Programming paradigm](https://en.wikipedia.org/wiki/Programming_paradigm)

語言典範是**組織程式的基本世界觀**：它決定程式的基本單位是「指令序列」、「物件」、「函數」還是「事實與規則」。典範不是語法風格，而是關於「狀態放在哪裡、如何被改變、如何被觀察」的根本決定。同一個問題在不同典範下會被拆成完全不同的零件；選典範，就是選擇你希望程式師用什麼概念來思考。

## 技術與理論的關聯

- **命令式的理論基礎是圖靈機**：狀態（紙帶）加上改變狀態的指令（讀寫頭動作），對應到程式裡的變數與賦值；[圖靈] 的模型直接塑造了馮·諾伊曼架構及其上的語言。
- **函式式的理論基礎是 λ 演算**：Church 的 λ 演算證明「僅用函數定義與套用」就足以表達一切計算；不變性（immutability）與純函數由此而來。
- **物件導向的核心理念是封裝**：把可變狀態圈進物件邊界，用訊息傳遞取代全域共享；Simula（1967）首創，Smalltalk 發揚，Java 普及。
- **宣告式的承諾是「描述結果而非過程」**：SQL、HTML、Prolog 與正規表示式都只說「要什麼」，執行策略交給引擎；這也是查詢最佳化與約束求解得以存在的空間。
- **典範可混用**：現代主流語言幾乎全是多典範——Python 支援命令式、物件導向與部分函式式；Rust 融合命令式與函式式；混用時的紀律需靠團隊慣例與工具維持。
- **典範影響可測試性**：純函數天然易測（輸入決定輸出），可變狀態則需要 mock 與狀態重置；典範選擇實質上預付或省下了測試成本。

## 範例：用四種典範處理「員工調薪」

需求：把薪資低於 40,000 的員工調升 5%。

**命令式**：

```
for e in employees:
    if e.salary < 40000:
        e.salary = e.salary * 1.05
```

**物件導向**（行為封裝進物件）：

```
class Payroll:
    def __init__(self, employees):
        self.employees = employees
    def raise_low(self, floor, rate):
        for e in self.employees:
            e.apply_raise(rate) if e.below(floor) else None

class Employee:
    def below(self, floor):
        return self.salary < floor
    def apply_raise(self, rate):
        self.salary = round(self.salary * (1 + rate))
```

**函式式**（不修改原資料，產生新清單）：

```
def raised(employees):
    return [
        e if e.salary >= 40000
        else {**e, "salary": round(e.salary * 1.05)}
        for e in employees
    ]
```

**宣告式（SQL）**：

```
UPDATE employees
SET salary = ROUND(salary * 1.05)
WHERE salary < 40000;
```

四個版本語意相同，但承諾不同：命令式原地改狀態；物件導向把「怎麼調薪」藏進 `Employee`，日後可換計算規則而不動呼叫端；函式式留下原始資料、便於復算與並行；宣告式把「怎麼更新」完全交給資料庫引擎，由它決定鎖與索引策略。

## 前因後果

- **前因**：1950 年代的高階語言全是命令式的，因為它們直接對映馮·諾伊曼硬體；當程式規模成長到數萬行，「全域可變狀態」成為錯誤的主要來源，典範分化正是對這個瓶頸的回應。
- **後果**：物件導向馴服了 GUI 與大型企業系統的複雜度；函式式的不變性思想滲入並行程式設計與分散式系統（如 MapReduce）；宣告式則撐起了資料庫、設定檔與 [資料科學] 的工具鏈。典範之間也互相借用——主流語言如今都同時支援多種典範。

## 與相鄰分類的關聯

- 與 [程式語言的演進] 的關係：演進提供載體，典範決定寫法； Lisp 之於函式式、Smalltalk 之於物件導向，都是「為典範造語言」的例子。
- 與 [型別系統語法] 的關係：函式式典範與強型別互相強化——型別使「函數組合」可被編譯器驗證。
- 與上位概念 [程式設計] 的關係：典範是「怎麼想」的層面；控制結構是「怎麼執行」的層面，兩者正交。

## 容易混淆之處

- **物件導向不等於有類別**：JavaScript 的原型鏈、Go 的介面隱含實作，都無傳統類別仍是物件導向；核心是封裝與多型，不是 class 關鍵字。
- **函式式不等於不用變數**：它禁止的是「修改已綁定的狀態」，不是命名本身。
- **宣告式不等於沒有演算法**：SQL 查詢背後仍有查詢計畫與索引選擇，只是把演算法選擇權移交給引擎。
- **多典範不等於隨意混用**：在同一模組內混用三種典範通常比單一典範更難讀；混用需要邊界紀律。

## 技術要點

- 命令式：語句改變狀態，與硬體對映最直接，效能可控性最高。
- 物件導向：封裝、繼承、多型三支柱；繼承在實務中常被組合取代（「組合優於繼承」）。
- 函式式：純函數、不可變資料、高階函數、閉包與遞迴；副作用被推到系統邊界。
- 宣告式：描述結果性質，執行策略交給引擎；最佳化空間最大、控制力最小。
- 多型（polymorphism）是跨典範概念：物件導向的子型多型、函式式的參數多型（見 [泛型]）同源。
- 選型準則：狀態多且互動複雜者宜物件導向；轉換與管道為主者宜函式式；資料查詢宜宣告式。

## 常見的論爭

- **物件導向是否過度吹捧**：批評者（如「Null 參照是十億美元的錯誤」作者霍爾的同行論戰）指出深繼承層級與可變物件圖是大型系統的亂源；支持者則強調封裝邊界對團隊分工不可取代。
- **純函式式是否務實**：Haskell 社群主張純度帶來可推理性，工業界則多選擇「函式式核心、命令式外殼」的折衷。
- **典範教學順序**：先教命令式打底，還是先教宣告式避免養成「手動迴圈」直覺，教育界長期未有定論。
