# 邏輯與電腦

> 隸屬：[邏輯學]　·　狀態：初稿

> 對應維基百科：[中文維基百科：邏輯與電腦](https://zh.wikipedia.org/wiki/%E8%AE%A1%E7%AE%97%E6%9C%BA%E9%80%BB%E8%BE%91)　·　[English Wikipedia: Formal verification](https://en.wikipedia.org/wiki/Formal_verification)

邏輯與電腦處理的是同一個理想：把「什麼必然成立」交給機器處理。它們的交會處有三條主線——**定理證明**（以邏輯驗證數學）、**形式化驗證**（以邏輯驗證軟硬體）、**型別系統**（以邏輯約束程式語言）。

三者的共同骨架是 Curry-Howard 對應：命題對應型別、證明對應程式、推導對應程式執行的型別檢查。

## 一、三條主線

| 主線 | 對象 | 代表系統 | 產出 |
| --- | --- | --- | --- |
| 定理證明 | 數學命題 | Coq、Lean、Isabelle | 已驗證的定理庫 |
| 形式化驗證 | 軟體與硬體 | seL4、CompCert、Frama-C | 可信程式與硬體 |
| 型別系統 | 程式語言 | Haskell、OCaml、Rust | 型別安全的程式 |

**範例**：seL4 是一個已形式化驗證的核心作業系統核心，其正確性證明以 Isabelle 完成，並可被獨立的小型核心重現。這是「邏輯取代測試」最完整的案例。

## 二、Curry-Howard 對應

| 邏輯 | 程式 | 說明 |
| --- | --- | --- |
| 命題 $A$ | 型別 $A$ | 兩者的推論規則一致 |
| 證明 $A$ | 值 $a : A$ | 證明即具體實例 |
| $\Gamma \vdash A$ | 型別檢查通過 | 推導即檢查 |
| $\wedge$ | 序對 $(a, b)$ | 兩者都給出兩種成分 |
| $\to$ | 函式 $a \to b$ | 函式即蘊涵 |
| $\top$ | 單位元 `()` | 皆為無資訊的建構 |
| $\bot$ | 無中止型 | 皆表示不可能 |

**範例**：在 Curry-Howard 下，「若 $P$ 則 $Q$ 」對應到函式型 $P \to Q$ 。因此一個型別為 $(A \to B) \to A \to B$ 的值，就是一個「把函式套用到引數」的普通函式——邏輯的假言推理在程式中就是函式的套用。

## 三、驗證的分工

| 性質 | 手段 | 例子 |
| --- | --- | --- |
| 型別安全 | 型別檢查 | 沒有把整數當字串用的錯誤 |
| 記憶安全 | 借用檢查或邏輯框架 | Rust 的借用檢查器 |
| 功能正確性 | 定理證明 | 排序演算法輸出排序後的序列 |
| 迴圈終止 | 變分法或邏輯 | 迴圈必定終止的證明 |

**範例（迴圈不終止的經典反例）**：

```text
while (x != 0) { x = x - 1 }
```

若 $x$ 為整數則終止，但若 $x$ 為實數則不終止——**型別資訊直接決定了終止性**，這是用邏輯（型別系統）處理可判定性問題的漂亮例子。

## 四、從測試到證明

| 面向 | 測試 | 形式化驗證 |
| --- | --- | --- |
| 覆蓋 | 抽樣 | 全稱（對所有輸入） |
| 失敗資訊 | 反例 | 反例＋證明 |
| 成本 | 低 | 高 |
| 適用 | 一般軟體 | 核心演算法、系統底層 |

**範例**：對排序演算法做隨機測試，只能增加信心；對排序演算法做形式化證明，則得到「對任意輸入，輸出皆為原輸入的排列且長度相同」的定理——兩種證明的強度完全不同。

## 五、工業化現實

1. **半自動為主**：Lean 與 Coq 的成功模式是「人選策略、機器做細節」，見 [自動定理證明]。
2. **假設—保證**：因 [不完全性定理] 的限制，驗證通常聲明前提假設而非聲稱全面正確。
3. **可信核心**：核心越小越易審查，這是 Galois、CompCert 等專案的核心設計原則。
4. **工具鏈整合**：從建模語言到驗證器的串接，使驗證得以進入日常開發流程。

**範例**：CompCert 用 Coq 證明一個 C 編譯器的正確性，並以「大部分程式碼經由已驗證的編譯器產生」的方式獲得可信性——這是「可信子集」策略的經典案例。

## 六、與相鄰分類的關聯

- [定理證明器]：整合型證明系統。
- [形式化驗證]：軟硬體的機器證明。
- [型別系統]： Curry-Howard 對應的工程實例。
- [程式驗證]：最貼近工程應用的一環。
- [自動定理證明]：自動化引擎。

## 七、容易混淆之處

- 型別檢查通過**不等於**程式正確，只涵蓋型別系統表達的性質。
- 「已驗證」指**特定性質**被證明，不等於沒有任何缺陷。

## 七、邏輯與電腦的驗證光譜

| 性質 | 工具 | 自動化 | 成本 |
| --- | --- | --- | --- |
| 型別安全 | 型別檢查 | 全自動 | 低 |
| 資源安全 | 借用／線性型別 | 全自動 | 低 |
| 局部性質 | 斷言與靜態分析 | 半自動 | 中 |
| 路徑性質 | 符號執行 | 半自動 | 中 |
| 功能正確性 | 定理證明 | 半自動 | 高 |
| 時序性質 | 模型檢查 | 全自動 | 隨狀態空間變動 |

**範例（成本與價格的取捨）**：一個支付系統若只用型別檢查與單元測試，成本極低但無法排除演算法層次的錯誤；加入對核心金額計算的定理證明，成本大幅上升卻能排除一整類錯誤。工程判斷的核心是「哪些性質值得多少成本」。

- [程式驗證]：最貼近日常軟體的應用。
